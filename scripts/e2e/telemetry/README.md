# Broker telemetry fixture

This test fixture retains the reviewed TF1 reporter, relocated OTLP v1.9.0 bindings and host-listener correction. The reporter implements MetricsReporter and ClientTelemetryExporterProvider; it receives exporter push-interval context. It is not a client runtime dependency.

Select one file, `docker-compose.telemetry.yml`, with project `kafkajs` under the local live guard. CI uses a unique `COMPOSE_PROJECT_NAME` on each ephemeral runner. Bootstrap on `localhost:19092`, `localhost:19095` and `localhost:19098`; Metadata must return those same host endpoints. The published bindings use IPv4 loopback. The test socket uses IPv4 explicitly for these fixture hostnames, records the actual remote address and port, and refuses every other endpoint before dialing. This test choice does not change the library socket default. TLS/SASL host listeners are not published by this fixture and are not part of this plaintext fixture proof.

Every broker mounts the matching reporter jar, with `metric.reporters=org.countly.kafkajs.telemetry.CountingTelemetryReporter` and `telemetry.max.bytes=4096`. `fixtures/manifest.json` records exact source, jar, proto, compiler, image and corrected compose identities. The four retained reporter and Java client jars are committed as checksum-pinned test fixtures and excluded from the npm tarball. CI never rebuilds them. `run.sh verify <line>` checks all four jars offline against the manifest before startup; changed or missing bytes fail readiness. `build.sh` records historical build provenance and is not a runtime preparation command. `fetch.sh` separately downloads and checksum-verifies pinned decoder dependencies into `TF1_CACHE` before startup. Broker start uses the already prepared image and never builds or fetches fixture inputs. The independent decoder uses protobuf-java 3.25.5, the pinned Kafka client jar and relocated bindings in the reporter jar. Set `TELEMETRY_JAVA_CACHE` to the same directory as `TF1_CACHE`: it holds the `jars/` directory. Missing or changed inputs fail readiness.

`run.sh verify 4.3.1` checks the retained manifest, compose, source, build script and all four retained jars. `run.sh decode 4.3.1 /absolute/raw.bin` also verifies the Java cache and independently decodes one decompressed payload of at most 4096 bytes. Both commands are offline and require a private `TMPDIR`. The runtime observer decompresses captured Push bytes using Node built-ins with an output cap, then matches their SHA-256, UUID and node to the broker sink and successful Push response. A capped sink record alone cannot prove all metric values: full decoding is mandatory when detail is truncated. Zero-byte Push has no exporter record and must be proved from the wire.

Each run gets a fresh `TELEMETRY_EVIDENCE_DIR`. The reporter queue holds at most 128 entries and each broker file at most 2 MiB; a record holds at most 4096 bytes of JSON detail. Any OVERFLOW marker, sequence gap, decode failure, stub, unmatched accepted Push or observer limit breach fails the fixture. Readers retain a cursor for each broker independently. Archive completed evidence before clearing the sink after the brokers stop; never clear or rotate an active sink.

The maintained runtime subscription is `metrics=org.apache.kafka.`, `interval.ms=1000`, with an anchored match for the run's four client IDs. Create, list, describe, delete and read back through the completed public CLIENT_METRICS APIs. Every auxiliary admin has telemetry disabled. The preparation-only narrow Java subscription and two-file negative capture are historical evidence, not runtime invocation forms.

CI selects the same file for startup, readiness, inspection, evidence verification and teardown. The `telemetry-reporter` lane runs two top-level tests, `reporter export` and `reporter no-resource control`, on the configured fixture for Kafka 4.3.1 and 4.2.2. The `telemetry-base` lane runs `reporter no-plugin control` on the unchanged base fixture for Kafka 4.0.2, 4.1.2, 4.2.2, 4.3.1 and 4.4.0. Development CI runs exactly three rows on Node 24: configured 4.3.1, base 4.3.1 and base 4.4.0. The existing exit gate calls the same reusable telemetry workflow with the full 21-row catalogue: on each of Node 22, 24 and 26, configured 4.3.1/4.2.2 plus base 4.3.1/4.2.2/4.1.2/4.0.2/4.4.0. This full catalogue runs on non-draft pull requests (opened, synchronize, reopened, ready_for_review), pushes to master and manual exit-gate dispatch, through the gate's existing non-draft plan condition. Drafts receive the three development rows; ready PRs also receive the full exit gate. The 4.4.0 base rows are additional coverage. All rows exit naturally. Producer, classic consumer and admin connects must succeed in every base row; ShareConsumer must preserve its specific capability refusal on 4.0.2/4.1.2. Matching failures on enabled and disabled clients cannot pass compatibility.

The local nine `test:e2e:telemetry-*` scripts call the reviewed live guard directly and select one exact Jest file and title; the controller supplies P9_CLUSTER_GUARD and KAFKA_VERSION. CI instead uses the isolated ownership contract in `ci.js`: an explicit unique project, empty container/network/volume preflight, bounded startup/test/verification/cleanup, and `down -v --remove-orphans` followed by proof of removal of all three resource kinds. It records project, image digests, configuration hashes, start/stop times and removal proof in an uploaded ownership receipt. Cleanup shares one monotonic budget: diagnostics stop after 25 seconds, teardown has its own reserve through second 65, and removal queries stop at second 130, leaving 20 seconds before the outer timeout for receipt persistence. Known resource IDs are saved before inspections. An incomplete ownership journal always fails removal certification, even when labelled inventories are empty. No local guard path is required by CI.

The positive case requires four distinct stable UUIDs. A bounded read-only admin `describeConfigs` discovery installs topology before the controlled request. Ordinary REQUEST events on every client join independently to captured socket requests; setup-only foreground connections count in the connection Sum, while bootstrap requests cannot invent node gauges. Full descriptor and point cardinalities and every applicable node window are checked against those observations. Each accepted Push is decoded and consumes its sink identity once, with later assertions reusing the cached result.

After natural client and observer cleanup, each scenario archives immutable raw files, full decoded JSON, sink rows, load proofs, request/connection arithmetic and observer cleanup receipts. Stamped evidence references relative paths, sizes and SHA-256 digests. `evidence.js` verifies the exact required scenario catalogue, sidecar manifest, the complete normal Push stream (including rejected or unanswered windows), sink/decode/request source-node joins, arithmetic and the mandatory admin control: the complete joined ordinary request set in the next two Pushes followed by a quiescent third Push before teardown while brokers remain up. The final cleanup manifest links the stamped scenario files to the ownership receipt after project removal. Captured transmitted payloads are saved immediately, independently of decode success. After all cleanup attempts, failures retain an immutable archive and a structured `failed-attempt.json` with the stage, original failure, cleanup causes and available sidecar catalogue. Failed stamped records use a separate `-failed` filename and cannot satisfy the exact passing scenario catalogue. Their payloads and diagnostics remain in the uploaded directory. Never treat a configured exporter with no matching subscription as a no-plugin broker.
