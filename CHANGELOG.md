# Changelog

All notable changes to `@countly/kafkajs` are recorded here. The fork starts from kafkajs 2.2.4 (Feb 2023).
Versions before 3.0.0 are internal alpha tags and are not published.

## Unreleased — 3.0.0

### Phase 9F — Client telemetry

#### Additions

- Implement the two flexible telemetry protocol codecs with capability-qualified compatibility output.
- Add bounded numeric Gauge and monotonic BigInt Sum collection and snapshot registration internally.
- Expose client telemetry options, stable instance IDs and numeric metric snapshots on all client kinds.

#### Tooling

- Add independent telemetry request/response vectors and strict wire fixtures.
- Verify normal physical connections and completed-request observations independently.
- Add independently generated and decoded OTLP metric vectors.
- Exercise subscription updates and isolated bounded error recovery with fake transport handles. Verify Broker framing/quota propagation, transport negotiation and authentication, queue commit refusal, and omission-warning boundaries through the real network stack.
- Add a pinned broker metrics reporter fixture with independent OTLP export and push-interval verification.
- Retain checksum-pinned telemetry fixtures and verify complete export evidence and isolated CI ownership receipts.
- Harden telemetry cleanup deadlines, complete Push and controlled RTT evidence verification, failed-capture archives, and development/exit-gate matrix scheduling.
- Verify captured telemetry request identities and complete bodies, startup-failure cleanup, concurrent public commits and original rejection outcomes. Run optional OpenTelemetry containment against the byte-identical packed client in CI.
- Add deterministic lifecycle, shutdown and observer-failure schedules for client telemetry.
- Bound telemetry schedule cleanup and await operation settlement before lifecycle assertions.
- Measure telemetry observation, bounded serialization and end-to-end overhead with independent work and identity controls.
- Defer telemetry benchmark payload decoding and capture hashing until after delivery timing, and verify inherited consume bytes through frozen manifest inputs.
- Verify client telemetry updates, custom metrics, payload limits, Java interoperability, unsupported brokers and unchanged foreground outcomes.
- Verify every captured telemetry exchange, exact close cancellations, broker-qualified cache retirement, share acknowledgements and complete Java export semantics.
- Require complete post-recovery telemetry exports, distinguish share fetch and acknowledgement statuses, and pin archive negative controls to their intended diagnostics.
- Verify bounded telemetry resources, repeated reopen and natural shutdown under subscription and connection churn.
- Prove twenty close-and-reopen rounds for each client kind through versioned, segmented observer evidence (89 fixed segments in two bounded files each, unchanged observer, sink and archive caps), shared broker log windows with the old connection's exact cache retirement, immediate public reconnect ordering, and quiet-resource baselines.
- The resource job records stamped per-arm memory measurements, validates them with `scripts/e2e/telemetry/resourceArtifact.js` and uploads them even on failure. Telemetry memory is judged as an increment over a same-process telemetry-disabled control (RSS and external peaks at most 64 MiB above it, setup at most 96 MiB, the whole arm at most 160 MiB, from the kernel high water), and the hundred-cycle schedules complete real per-kind foreground work on an opt-in bounded capture mode of the lifecycle and scripted-wire helpers. The artifact replays each child's issued identity, its output catalogue, the disconnect receipt and reopen order witnessed in the public disconnect continuation, the registered descriptor population and every native reading and pending window; the hundred-cycle schedules judge owners, listeners and timers by identity and count a share record only once its acknowledgement is confirmed.
- The churn lane is a parent-coordinated, segmented run: four one-client workers join each tick in stages, every lifecycle is a sealed observer segment, selected Pushes are decoded by the parent with the pinned Java reporter, the ordinary and share oracles use measurement-only corpora, resident size is judged against a same-process telemetry-disabled control, and the verifier recomputes the whole verdict from the archive.
- The churn verifier now replays more of the run: the terminal lifecycle's final is decoded by the parent after the worker exits; share exchanges are archived as hashed protocol facts and re-derived per acquisition; custom identity changes are fenced by observer cursors with no time grace; every segment's request, error and cancellation stream is accounted; and the stage schedule is replayed from parent and worker receipts on one mapped clock. Resource evidence uses a versioned reading catalogue with arithmetic, collection and native-work facts. Failed or inconclusive attempts keep their partial worker evidence, also when the case's own bound expires first, and a cancelled worker is asked to stop and, if it is still running after its natural-exit bound, killed and joined within a bound, its row failed. The close-and-reopen lane compares exact resource, listener and pending-call identities after its quiet window.
- Every churn lifecycle whose selection is nonempty when its close begins must hold exactly one final, written inside the close, answered with error 0 and fully decoded; one under an empty selection must hold none. Cancellation allowances come from the scheduled retirements, not the transcript; each worker's driver source is joined to the run's tree; the share exchanges are archived once and joined by hash; each worker's native journal must cover every compressed Push; and each parent decoder child's memory is reported separately from `/proc`, or explicitly as unavailable. The close-and-reopen lane closes every kind, admin included, with the inherited 3000 ms budget, adds an admin zero-timeout arm (89 segments), bounds the admin blackhole cleanup by the smaller of 1000 ms and its finite remaining budget plus 100 ms, and links its fixed strict seams for private waiter, queue, snapshot and listener release.

#### Behavior changes

- Keep observational telemetry errors in the `applicationRecoverable` category regardless of a wrapped cause's transaction or configuration category; foreground clients remain usable.
- Keep telemetry suspended after failed consumer startup, retain request latency observation across crash restarts, and wait for supported telemetry connection setup when requesting an instance ID. Contain all recognized share option accessors before construction; disabled disconnects retain their original scheduling.
- Broker client metrics (KIP-714) are available with `enableMetricsPush: true`; the default remains false. Kafka-wide defaults can be overridden on producer, consumer, admin and share consumer.
- Enabling broker telemetry can open one additional broker connection per client and send GetTelemetrySubscriptions/PushTelemetry traffic. Unsupported brokers quietly leave foreground operations usable.
- Telemetry includes only applicable rack/group/static-member/current-member/transaction identity attributes, library scope/version and per-node metric labels.
- Each client exposes an asynchronous stable `clientInstanceId({ timeout })`; disabled/unsupported/closed/unavailable calls reject with `KafkaJSTelemetryError`.
- A `clientInstanceId()` caller whose own timeout has passed gives up its waiting slot when the next caller is admitted, without waiting for a timer; a new caller is refused with `limit` only while 64 unexpired callers wait.
- A subscription response with more than 128 compression codecs, 256 requested-metric prefixes, 256 bytes in one prefix or 16384 prefix bytes is refused while it is decoded, before any array or string is built; telemetry stops for that client and foreground work continues.
- Applications may register/unregister finite numeric Gauge and monotonic BigInt Sum snapshots for broker subscriptions.
- Disconnect sends a best-effort terminating telemetry push on an active connected subscription, for at most 1000 ms within the existing close budget; timeout0 sends no final.
- Preserve shared foreground SASL renewal when an individual caller expires; contain private telemetry commit and logging failures, retry transient socket failures, and retire expired telemetry work.
- Positive telemetry push intervals below 100 ms are clamped to 100 ms locally; nonpositive intervals use 300000 ms.
- Telemetry buffers, metric identities, labels and timers have fixed bounds; `telemetryMaxBytes` may lower the 1 MiB default. Small limits may omit metrics or send an empty blob. Only written included baselines advance; a rejected written sample can be lost from later deltas.
- Telemetry payloads over1000 bytes use mutually supported built-in ZSTD/GZIP in broker order; NONE is always available. Producer codec registrations are unchanged.

### Phase 9E — Share groups

#### Behavior changes

- No existing public API, option default, event or runtime behaviour changes in this phase.

#### Additions

- Implement the seven released share-group wire codecs: ShareGroupHeartbeat v1, ShareGroupDescribe v1, ShareFetch v2, ShareAcknowledge v2, DescribeShareGroupOffsets v1, AlterShareGroupOffsets v0 and DeleteShareGroupOffsets v0. Each is flexible with nested tag buffers, keeps int64 offsets and lag as exact decimal strings and passes broker error codes through as data. They are checked against independent Apache Kafka message vectors.

- Route `ShareFetch` and `ShareAcknowledge` over a connection pool's data socket, each API counted by its own socket's generation, and add the seven share-group `Broker` methods. Add `KafkaJSShareGroupsNotSupportedError`, a `KafkaJSServerDoesNotSupportApiKey` subclass whose `reason` (`api-not-advertised`, `api-version-range`, `feature-disabled` or `refused-by-broker`) and `shareVersion` say why a cluster cannot run share groups. A capability check judges a broker by its advertised ranges and its finalized `share.version` (level 1 or above, including level 2 on Kafka 4.4).

- Add `admin.describeShareGroups`, `listShareGroupOffsets`, `alterShareGroupOffsets` and `deleteShareGroupOffsets` for Kafka 4.2+ share groups, each taking the admin `apiTimeout`. Every call goes to the group coordinator. `describeShareGroups` sends one request per coordinator, relocates a moved group once and returns one row per requested id in caller order, with the raw signed `authorizedOperations` mask. The offset methods return exact decimal-string offsets and lag (unknown lag is `null`), check every offset to alter before any request, and keep a partition's or topic's error as data while a group-level error throws. A coordinator that cannot run the API rejects with `KafkaJSShareGroupsNotSupportedError`. Share-group deletion stays `admin.deleteGroups`; no `deleteShareGroups` is added, and against Kafka 4.4 `deleteGroups` negotiates DeleteGroups v3, so each result carries the broker's `errorMessage`.

- Add the share-group membership: one generated member ID per run, heartbeats that send only changed fields, topic-ID assignments applied at once with unknown topic names resolved under a guarded retry, and the existing heartbeat manager reused for scheduling. Coordinator errors keep the membership, fenced members rejoin with the same ID, and `GROUP_ID_NOT_FOUND` (69) ends a membership as non-retriable unless it answers that member's own leave. The consumer-protocol heartbeat backoff moved to its own module without changing. No public share API uses the membership yet.

- Add exact record-range walking and compact acknowledgement outcomes with `KafkaJSShareAcknowledgementError`. Acquired records are classified through exact int64 offsets without expanding ranges; control and missing offsets become gaps, and the undecoded remainder after a decode failure is released rather than rejected. Per-partition acknowledgement ledgers keep automatic ranges compact, hold each decision until its handler completes, check a request against the broker's batch rules before a frame is built, and settle every outcome once. Lock deadlines count from the time the fetch was written; no timer is added. Only the error class is exported; the walk and ledger are internal and no public API uses them yet. An internal-API benchmark compares the walk with a per-offset expansion control.

- Add the share-group node loop: one serialized request queue and one non-prefetching fetch loop per leader node, so a node sends no second fetch until every handler of its previous answer has returned. Acknowledgements piggyback on the next fetch; ShareAcknowledge carries only flushes, renewals and the final close. A partition is forgotten in the same frame as its last acknowledgement, or in the first fetch after a flush or renewal, and a partition that still holds undelivered records is never forgotten. Session resets (122, 123, and 133 on fetch) never replay an old acknowledgement, a request written without an answer is never resent, and fetch and acknowledgement errors are classified separately, with leader hints, metadata refreshes and a fatal path for authorization and corrupt records. Empty rounds are paced at 50 ms and `record_limit` is bounded per node. Internal only: no public share API uses the loop yet.

- Add `Kafka.shareConsumer` with implicit or explicit acknowledgements, handler-driven renewal and bounded disconnect. Share isolation defaults to read_uncommitted and is configured per group; share groups require Kafka 4.2+.

- Document share-consumer boundaries and offset-reset recipes, including compact acknowledgement events and the share-span boundary.

- Add deterministic share membership, session and acknowledgement fault matrices, with captured shutdown authority, exact record outcomes and resource cleanup checks.
- Verify share delivery, acknowledgement types, locks, isolation, membership, recovery, shutdown and administration against live brokers.
- Verify share capability refusals, broker-bounce recovery, Java interoperability and diagnostics channels.
- Verify that an idempotent batch whose answer is lost across a leader change is re-sent with the same producer ID, epoch, sequence and bytes, and that no later batch of the partition is written before it is acknowledged. A broker that lost the producer's state can still append that re-send a second time; the client cannot detect it, as with the Java producer.

#### Fixes

- A connection closed without an error is now detected immediately instead of after the request timeout. In-flight requests fail with the same retriable connection-closed error as a socket end, and share sessions reopen on the next round.
- A broker restart no longer crashes a share consumer with "Metadata discovery completed" when a metadata notification starts a new fetch loop. Rebootstrap and request-queue-size listeners, and the queue's pending-check timer, also run independently of the publishing discovery or admin invocation.
- A share answer that arrives from a replaced connection pool is discarded and the session reopens on the next round, instead of ending the run and losing unrelated acquisitions.
- A failed share heartbeat preserves the healthy data socket and its acquisitions while the coordinator reconnects.
- A share consumer now leaves its group on disconnect even after its coordinator connection was re-established.

- Prepared share renewals retain their own compact acknowledgement error when a routing change or shutdown retires their wait; callers retired before preparing a ticket receive a local refusal.

- Share-consumer closes honor a disconnect deadline supplied during a stop and detach captured sockets when their shared close budget expires.

- Unimplemented request slots throw `KafkaJSNotImplemented` with a diagnostic message instead of a `TypeError`.

#### Tooling

- Add share-consumer soak and benchmark gates with separate batch and message identity controls. The short/full soak profiles use 32/64-second slots and 960/1920-second profiles, 1020/1980-second inclusive child budgets and 1440/2400-second cold caps. Both retain thirty cycles, ten resets and separate 5000 ms per-cycle and final observations, with configuration, heartbeat and cycle-step evidence. These are declared bounds; live acceptance and measured performance remain unverified.

- Track the seven released share-group APIs (keys 76–79 and 90–92) in the Kafka 4.4.0 and 4.3.1 message snapshots and regenerate their protocol compatibility inventory. Source inventory alone does not add share-group support.
- Add a Java share-consumer interoperability member and classpath probe.
- The Java message-vector generator writes 46 share-group vectors (24 requests, 22 responses), including Records bytes, unknown tagged fields at every nesting and Java's own acknowledgement batching; they need `KAFKA_CLIENTS_VERSION=4.4.0`.
- Add share-group fixtures, finalized feature captures and configuration-readback checks.
- Add independent wire pairs for ShareGroupHeartbeat v1, ShareFetch v2 and ShareAcknowledge v2, a `share` scripted-cluster profile and literal-row `shareScript`, checked against the Java message vectors.
- Add independent wire pairs for ShareGroupDescribe v1, DescribeShareGroupOffsets v1, AlterShareGroupOffsets v0 and DeleteShareGroupOffsets v0, checked against the Java message vectors, so every pair the `share` scripted-cluster profile advertises has one. Share administration is covered over real Brokers on that profile, including the complete frame and connection slot of all seven share requests.

### Phase 9D — Client, security and admin breadth

#### Behavior changes

- SASL failures and token-admin diagnostics omit credentials and sensitive broker payloads. Error classes and fixed message prefixes remain stable. Built-in SASL exchange wrappers preserve fixed, library-authored SCRAM validation reasons; other failures use the canonical protocol-code description or `Error` instead of broker or supplier text.

- Admin operations after disconnect reject without dialing until an explicit connect opens a new lifecycle.

- A `GROUP_ID_NOT_FOUND` answer to a transactional offset commit makes the transaction abortable, like `STALE_MEMBER_EPOCH`, where it was a producer-fatal `applicationRecoverable` error; on every other request it keeps its category. A broker that answers `UNKNOWN_TOPIC_ID` to a v6 commit makes the producer refresh its metadata before the existing bounded retry; that refresh never asks the broker to create a topic and adds no topic to the producer's targets. A v6 answer that cannot be matched to its request (a duplicate, foreign or missing topic or partition) makes the transaction abortable, so the producer survives, and stages nothing.

- **Idle connections are closed after 9 minutes** (540 000 ms, Java's `connections.max.idle.ms`; 2.2.4 never closed them) and reopened by the next request, with one more ApiVersions round trip: "Connections idle for 9 minutes are closed by default; the next request reconnects. This is below the default broker idle timeout but does not guarantee close ordering or eliminate races. `connectionsMaxIdle: 0` keeps connections open as before."

- Admin calls take an `apiTimeout` (default 60 000 ms) and reject with `KafkaJSTimeout` when it passes; a mutation may have been applied. Retries are unchanged, unlike Java's unbounded retries inside the deadline. Existing broker-side `timeout` keeps its meaning.

- `connectionTimeout` defaults to 10 000 ms and grows per node, with jitter, up to `connectionTimeoutMax` (30 000 ms) while a node keeps failing; it resets when the node is ready. A value you set stays flat. Java's `socket.connection.setup.timeout.ms` (KIP-601).
- A broker must be ready (TCP, TLS, ApiVersions, SASL) within the setup timeout; a stalled ApiVersions or SASL exchange no longer waits for `requestTimeout`.
- `authenticationTimeout` now bounds the SASL exchange (it only sized the blackout before). A token callback slower than 10 s needs a larger value.
- Pool replacement during API-version renegotiation retains `KafkaJSConnectionClosedError` and does not advance reconnect backoff.
- Reauthentication on an established, negotiated connection uses this SASL cap without restarting the connection setup timeout, preserving non-retriable provider failures.
- Reconnects to a node whose connection failed wait 50 ms, growing to 1 000 ms; `reconnectBackoff` and `reconnectBackoffMax` tune it.
- Timeouts now require positive integral values. Some legacy authentication values and fractional connection values could work. Invalid values throw `KafkaJSInvalidConfigurationError`; existing numeric strings remain accepted.

- SCRAM authentication refuses a non-extending nonce, a non-integer or above-1 048 576 iteration count, and compares the server signature in constant time.

- Against Kafka 4.4 brokers ApiVersions v5 checks the cluster and node ids (KIP-1242); `metadataRecoveryStrategy: 'none'` turns it off.

#### Fixes

- Preserve concurrent admin/producer/consumer connects over a shared cluster and decimal-string timestamps from consumed messages in `fetchTopicOffsetsByTimestamp`.

- `admin.describeReplicaLogDirs` tolerates repeated replica locations during a directory move instead of throwing `KafkaJSInvariantViolation`. As in Java, the last partition entry within each directory is projected; repeated current or future locations replace that location and its lag in response order. The result fields are unchanged.

- SASL GSSAPI follows the native `kerberos` 7.0.0 contract. Its step answers `null` when it has no output token, which the adapter failed to encode; it now responds with no data, as RFC 4752 asks. Its wrap takes a boolean `protect` and the authorization identity as `user`, where the adapter passed a number and put the identity in the data.
- A failed GSSAPI exchange names its step (`stage=exchange:1`, `exchange:2`, `exchange:final`) and, for a library or built-in programming error, its class, with a protocol error's `type` and `code`; the failure's text is still never published.
- `admin.deleteGroups` names the group id it refuses (`Invalid groupId name: 1`); it printed `true`.
- `KafkaJSNumberOfRetriesExceeded` names itself on the first line of its stack. It printed `KafkaJSNonRetriableError` there, its parent class, because the name was assigned after the stack was built (also in kafkajs 2.2.4).
- A commit the broker refuses names the refused partition: the error carries `topic` and `partition`, as a refused Produce does.
- `admin.deleteGroups` no longer sends a group again that a coordinator already answered. When one coordinator's request failed with a stale-coordinator error, 2.2.4 threw the other coordinators' answers away and resent every group, so a group it had deleted could come back as `GROUP_ID_NOT_FOUND`. Every coordinator request now settles before the retry, the retry sends only the groups no coordinator has answered, and each row is kept for the result.

#### Additions

- `admin.disconnect({ timeout })` closes by the deadline.

- `admin.describeLogDirs`, `alterReplicaLogDirs`, `describeReplicaLogDirs`; `fetchTopicOffsetsByTimestamp` accepts `'maxTimestamp'`, `'earliestLocal'`, `'latestTiered'` and `'earliestPendingUpload'`; `alterPartitionReassignments` accepts `allowReplicationFactorChange`.

- `admin.describeClientQuotas`, `alterClientQuotas`, `describeUserScramCredentials`, `alterUserScramCredentials` and the four delegation-token methods.

- Admin clients can delete committed group offsets with deleteOffsets and read several groups with fetchOffsetsForGroups. fetchOffsets accepts requireStable; its default remains false.

- `admin.describeProducers`, `describeTransactions`, `listTransactions` (with the KIP-1152 `transactionalIdPattern` filter, a RE2 string evaluated by the broker), `abortTransaction` and `fenceProducers`; `forceTerminateTransaction` is `fenceProducers({ transactionalIds: [id] })`.

- `connectionsMaxIdle`.

- `AdminConfig.apiTimeout` and a per-call `apiTimeout`; `includeAuthorizedOperations` on group descriptions and `includeTopicAuthorizedOperations` on topic metadata. Requested supported masks retain the raw signed INT32 value; an absent, unsupported or unrequested mask is `null`.

- New client options `connectionTimeoutMax`, `reconnectBackoff` and `reconnectBackoffMax`; `authenticationTimeout` is now enforced.
- `oauthBearer.clientCredentials`, `jwtBearer`, `fileToken` and `signAssertion` build the existing `oauthBearerProvider` callback with a single-flight token cache; recipes for discovery, token exchange, mTLS and KMS-held keys are in `docs/OAuth.md`.

- Admin topic-offset reads accept an optional isolationLevel, defaulting to read_committed; read_uncommitted reads the high watermark. Legacy alterConfigs errors and KafkaJSCreateTopicError expose broker errorMessage separately from their stable messages.

- `admin.electLeaders`, `describeFeatures`, `updateFeatures`, `listConfigResources`; `describeCluster` gains `includeAuthorizedOperations` and `includeFencedBrokers` and uses DescribeCluster when asked.

- `sasl: { mechanism: 'gssapi' }` over the optional peer `kerberos` 7.0.0, loaded on first use; credentials come from the process environment, with no `kinit` and no subprocess.

- `kerberos` is declared an optional peer dependency pinned to 7.0.0 and is never installed with the package.

- DeleteGroups v3 returns `errorMessage` per group; the error table gains `GROUP_DELETION_FAILED`, `STREAMS_TOPOLOGY_DESCRIPTION_UPDATE_FAILED` and `CONTROLLER_ID_NOT_REGISTERED`; the compatibility baseline moves to Kafka 4.4.x

- `rackId` and `rackAware` producer options (KIP-1123): with `rackAware: true` and a non-empty `rackId`, the built-in partitioners (the default `UniformStickyPartitioner`, `DefaultPartitioner` and its alias, `LegacyPartitioner`) prefer the partitions whose leader is in that rack for records without a key, and fall back to every partition with a leader when none is. A record with a `partition` or a key keeps its partition, and a custom `createPartitioner` is given the same arguments as before. Without the opt-in nothing changes.

- TxnOffsetCommit v6 uses cached topic IDs on capable brokers (KIP-1319), with the existing named-topic fallback and commit-only offset publication. A topic with no partition is left out of the v6 request and of the answer it expects, as the broker answers only the topics it forwards.

### Phase 9C — Consumer parity

#### Behavior changes

- **A commit error that a handler lets escape no longer costs a member its membership after a rejoin.** The commit retrier re-wraps an `ILLEGAL_GENERATION` answer it will not retry, and the wrapper kept `type` and `code` but not the private record of the generation, membership and group instance the request was sent under. The staleness checks read none, so an answer to a commit sent before a rejoin, delivered after it, read as news about the current generation and ran a lost-membership round: `onPartitionsLost`, discarded uncommitted offsets and an extra join. The checks now read that record through the wrapper's `cause` chain, so such an answer is dropped as stale; an `ILLEGAL_GENERATION` for the generation the member holds still ends its membership.

- Under `groupProtocol: 'consumer'`, a heartbeat answer, success or fencing error, to a request built before the member began joining anew is discarded. It no longer installs the old epoch over the join's zero, settles the join, or fences it, so the member sends its epoch-0 heartbeat after a fencing it learned from an offset commit.

- Under `groupProtocol: 'consumer'`, assigned topics outside the round subscription are filtered without `RECEIVED_UNSUBSCRIBED_TOPICS` or its warning; a debug message records them. Classic behavior is unchanged.

- `consumer.committed()` returns `metadata: null` whenever `offset` is null. A committed offset retains its stored metadata, including the empty string.

- **The classic `sessionTimeout` defaults to 45 000 ms** (was 30 000). `sessionTimeout` and `heartbeatInterval` are now validated: integers, `sessionTimeout` 1 to 2 147 483 647, `heartbeatInterval` lower than it; a JoinGroup the broker refuses as outside its session-timeout bounds fails with an actionable error

- **A paused consumer resumes at once and an idle consumer stops at once**: `resume()`, `seek()`, an assignment change and `stop()` end the idle wait instead of waiting out `maxWaitTimeInMs` (default 5 000 ms), which is unchanged

- **Pause state follows the subscription and the topic's incarnation**: it still survives a rebalance, but a pause on a topic that is deleted and recreated no longer applies to the new topic, and pause entries for topics that left a subscription are dropped

- Completed admin offset operations release their idle group-cache and ledger holders when the last overlapping operation for that group settles. Other participants, pending operations and reset tables retain their existing ownership protections.

- **The classic leader assigns the union of every member's subscription**: a topic only a non-leader member subscribes to is now assigned in the round, not left unassigned until a subscribed member leads. A custom assigner still receives `topics` unchanged and may read the new `groupTopics` and `groupTopicMetadata`

- **Classic consumers retain the member id received in `MEMBER_ID_REQUIRED` across retried JoinGroup requests.** Retriable transport failures, coordinator rediscovery and join-round expiry keep the id for the same active local membership. A consumer that restarts after a join or sync round expired rejoins under that id as well. `UNKNOWN_MEMBER_ID` clears it; `ILLEGAL_GENERATION` alone does not. Local leave, stop, disconnect or rebuild discards it, and `FENCED_INSTANCE_ID` remains fatal. This prevents these retries from creating additional abandoned members that delay rebalances until their session timeouts.

- **The KIP-848 leave builder supplies only member identity; other fixed wire fields carry no-update defaults** (group, member id, epoch −1 or −2, instance id); it used to also send the subscription, the rebalance timeout and an empty partition list

- **A named topic a KIP-848 member is assigned before its name is known is found promptly**, instead of up to `metadataMaxAge` later

- **Under `groupProtocol: 'consumer'`, `subscribe` to a literal topic that does not exist yet resolves** instead of rejecting with `UNKNOWN_TOPIC_OR_PARTITION` (automatic creation off). The name stays a desired subscription, the coordinator assigns the topic once it exists, and the member names it through the by-topic-id metadata path at once, not at `metadataMaxAge`, then registers it as a metadata target. `INVALID_TOPIC_EXCEPTION` and `TOPIC_AUTHORIZATION_FAILED` still reject. Classic is unchanged: it rejects as in 2.2.4.

- Consumer-protocol consumers retry their own connection and coordinator outages without spending the fetch loop's retry budget. A learned fence or fatal error, poll expiry and explicit stop still end or replace membership; no client-side session timeout is inferred from the classic configuration.

- `consumer.partition_halted` gains a discriminated offset shape and the reasons `'no-offset'` and `'offset-out-of-range'` (used only with `offsetReset: 'none'`). No-offset uses offset null; out-of-range uses the known decimal offset or null. Existing corrupt/decode offsets stay decimal strings and retain their decode fields. TypeScript ≥4.1 is now required for the duration template-literal type.

- **A topic recreation's offset reset stays owed until a confirmed commit.** A local resolution, a seek with autoCommit disabled and a published sentinel boundary no longer settle it; stop/run, a crash restart or an assignment rebuild before the first confirmed commit of the new topic resolve the reset again instead of resuming the old topic's committed offset. A failed, stale or unconfirmed commit settles nothing, and a partial or empty assignment no longer deletes a debt another partition of the topic still owes.

- `subscribe` rejects a non-boolean `fromBeginning` and an explicit `fromBeginning` that conflicts with `offsetReset` (none, by_duration, or the opposite of earliest/latest) with `KafkaJSNonRetriableError`, before any subscription state changes.

- The partition-halt error log reads `Halted a partition; seek it to resume`, for every halt reason.

- **A `RegExp` subscription is re-evaluated at every metadata refresh**: topics created later that match join, topics deleted leave, internal topics (`__consumer_offsets`, …) are no longer matched by `/.*/`, and a `g` or `y` flag no longer drops matching topics. **A consumer that subscribes a pattern refreshes metadata for all topics** (as the Java client does); a literal topic subscribed beside a pattern is not auto-created by that consumer. A post-initial addition without a usable topic ID waits for metadata to establish its incarnation before Fetch or OffsetFetch

- **A consumer built without a `groupId` no longer throws at construction**; the first call that needs a group (`subscribe`, `commitOffsets`, `committed`, `describeGroup`, `groupMetadata`, a `rebalanceListener`, `enforceRebalance`) throws the same message. An empty-string or non-string `groupId` still throws at construction. Without a group, `autoCommit` defaults to false and `autoCommit: true` is rejected.

- No-group CRASH and partition-halted event payloads use groupId null. Existing corrupt/decode payload fields and decimal offsets are preserved.

- OffsetFetch v8/v9 answers for a different group are refused with KafkaJSInvariantViolation naming requested and returned groups; matching responses and older versions are unchanged.

- The handler async context now carries the identity of the run that delivered the batch, and `seek`, `position`, `assign`, `unsubscribe`, `commitOffsets`, `subscribe`, `run`, `connect`, `pause`, `resume`, `stop` and `disconnect` called from a handler of a retired run reject with `CONSUMER_STOPPING` instead of acting on a replacement run.

- With an automatic commit interval or threshold set, batch-end automatic commits now follow either eligible condition at processing/check opportunities. With neither set, per-batch behavior remains. Classic stop, disconnect and unsubscribe add a final automatic commit attempt when automatic commits are enabled and group identity, ownership, eligible progress, halt bounds and remaining close time allow it. Fewer commits can increase crash redelivery after the last broker-confirmed offset.
- `consumer.connect()` and `consumer.run()` called while an earlier `disconnect()` of the same consumer is still closing now wait for that close to finish, so the close can never disconnect the connection that replaces it (a forced `timeout` bounds the wait; `disconnect()` then `connect()` always ran in that order). A call made from a handler or rebalance callback of the run being closed does not wait. A `disconnect()` asked after the waiting call makes it reject `CONSUMER_STOPPING`.

- **A leaderless partition no longer stalls the consumer**: one partition with no leader used to make every fetch round of every broker fail and request a rejoin, so no partition was fetched until a leader appeared; now only that partition waits.
- **A leaderless partition no longer crashes the consumer**: the fetch loop's metadata refresh named the subscribed topics, so a partition with no leader failed it with `LEADER_NOT_AVAILABLE` until its retries ended, twice in a row, and the consumer crashed and restarted about 20 seconds after the leader was lost. The refresh now keeps that partition at leader -1, so routing skips it as described above; the first refresh at `connect()` still waits for a leader.

- Preferred-replica routing now tests the preferred replica ID against offlineReplicas and falls back to the leader when that replica is offline.

- Fetch sessions (KIP-227) are opt-in; set `fetchSessions: true` to enable them.
- **`stop()` and `disconnect()` end a handler's API authority at once, so a handler's explicit `commitOffsets()` that is still waiting for the group coordinator when the stop begins can reject with `CONSUMER_STOPPING`.** In 2.2.4 such a commit could still finish while the stop waited for the batch. Now the rejection gives no promise that the commit completed, and an uncaught rejection is the handler's error, so the batch can be redelivered. Offsets committed before the stop began stay committed. A commit from outside the handlers and one made by an authorized close hook may still complete. To require that a commit finishes, drain the handlers and await the commit before calling `stop()` or `disconnect()`.

- When a broker joins or leaves, the consumer no longer pauses every fetcher until all in-flight long polls end: surviving brokers keep fetching, a new broker gets a fetcher at once and only a departed broker's fetcher stops (2.2.4 drained and recreated all fetchers).

- While a broker is unreachable, only its fetcher backs off and retries; the consumer keeps fetching from the other brokers (2.2.4 stopped and restarted every fetcher on each retry). Outage limits, warnings and events are unchanged.

#### Fixes

- A consumer's position derived from a reset policy (`earliest`, `latest`, duration, sentinel seek, or the `none` policy's local position) stays private to that consumer instead of being written into the group's shared committed-offset cache, so two consumers of one group with different reset policies no longer overwrite each other's starting position; real commits stay shared.

- On Node 22, a truncated zstd record batch is now refused as `KafkaJSCorruptRecordError` (reason `decompression`), as on Node 24.20+ and 26.6+, instead of decoding as fewer records. Node 22's `zlib` does not reject truncated zstd input (nodejs/node#64593), so the codec checks the first frame's blocks and checksum itself on every Node version.
- An ordinary `consumer.disconnect()` called from a `CRASH` listener no longer cancels the automatic restart, as in 2.2.4, which emits `CRASH` before it arms the restart timer. The restart waits for that close to finish its cluster and group cleanup, then starts a new run. A forced close (`disconnect({ timeout: 0 })`), a close whose `timeout` expires, and any `stop()` or `disconnect()` asked after the restart is armed still cancel it, as does an explicit `run()`, which supersedes a pending restart. A cancelled restart clears its timer at once and holds no listener or connection lifetime.
- Fence unknown-target metadata responses before cache installation and keep periodic naming attempts after the fast discovery budget.

- Use one membership-staleness predicate for ownership loss and rebalance verdicts; a consumer epoch change does not retire a current ownership token.

- **A classic leader now notices a partition added to a topic only other members subscribe to.** The union it assigned from was read once, during the sync, so a topic subscribed only by a follower could never make the leader rejoin (Java's leader compares its assignment snapshot with its metadata snapshot and rejoins on drift). The leader now rereads those topics with a bounded, non-installing Metadata request, at most once per `metadataMaxAge`, and asks for the ordinary stale-assignment rejoin when one gains partitions, including a topic that did not exist at assignment. The watch stops when leadership is lost, a new round starts or the consumer stops, never creates a topic, never adds to the leader's own targets, and costs a leader whose members share its subscription one property read per fetch round.

- A topic recreation's reset can no longer be lost across stop/run, a crash restart or an assignment rebuild: the consumer no longer resumes the deleted topic's committed offset in the new topic.

- Fence retired consumer cleanup, pending starts, restart decisions and detached callbacks so they cannot change a replacement run or send requests with its identity. Retain valid-prefix automatic progress below a corrupt or unreadable batch during graceful close.
- A consumer-protocol close now bounds and fences the final commit that precedes the leave. Under `consumer.disconnect({ timeout })` the coordinator lookup, the OffsetCommit write and the local publication all belong to the close: once it expires, a late lookup sends no frame, a late response records no cache entry, debt or `consumer.commit_offsets` event, and the abandoned leave reports no revocation and changes no membership state. A runner retired by a forced close also refuses any pre-release commit it still has in flight.
- A public `consumer.connect()` that a forced close ended no longer publishes `consumer.connect`; it rejects with `CONSUMER_STOPPING`, and the connect's retries end with the close. An old `disconnect()` that settles late releases only the topic-recreation listener, reset debt and discovery scope its own connection registered, never a replacement's. The calls in flight and the late crash of a closed run belong to the connection that started them, so a forced close or a stale crash cannot retire or stop the run that replaced it.
- A forced close (`consumer.disconnect({ timeout: 0 })` or an expired `timeout`) now stops the run's fetchers. Retiring the run latched its stop but left them running, and with the run stopped every fetch returned empty in microtasks, so each fetcher looped on `setImmediate` for the life of the process, keeping a core busy and the process from exiting.
- An idempotent producer no longer bumps its epoch again for a partition the previous bump already moved: when a batch written under an older epoch expires on such a partition, the partition restarts at sequence 0 under the current epoch, and one recovery pass bumps at most once. Under sustained delivery timeouts the producer used several extra epochs.
- A `consumer.assign()` or `consumer.subscribe()` that was still waiting when a forced close (`disconnect({ timeout })`) ended its lifetime no longer reconnects, writes Metadata or changes the cluster's target topics afterwards: the call rejects with `CONSUMER_STOPPING` (a plain close also ends an `assign`; `assign` has no `retry.maxTotalTime` deadline of its own). An `assign` that begins while a close is running now waits for that close, as `connect()` and `run()` do, and one made after a completed close starts a lifetime of its own.
- A classic heartbeat that was still awaiting its coordinator lookup when its run was retired now sends nothing, on both the timer path and the `heartbeat()` path.
- A commit whose caller timed out locally, and that the coordinator then answers with a membership loss for the same membership, still fences that membership and requests the rejoin. The caller still receives its own timeout, and an answer about a replaced membership still changes nothing.
- That loss is learned only when the call's own `retry.maxTotalTime` deadline expired; an OffsetCommit answered after its run was retired or force-closed publishes no ownership loss, commit error or rejoin.
- A commit retried under the natural wait (`retry.maxTotalTime` unset) now sleeps on a timer its call owns, so a close that retires the call removes the pending backoff timer at once.
- `consumer.stop()`, `consumer.disconnect()` and `consumer.unsubscribe()` called from a rebalance callback now settle on the next microtask (they settled on a later turn of the event loop). The cleanup, its logged failure and an outside caller's wait for the whole close are unchanged.
- Disposing a consumer that borrows its creator's cluster (the temporary consumers of `admin.setOffsets` and `admin.resetOffsets`) now asks a start that is still connecting to stop first, so it never joins the group, instead of waiting for it to join and then leaving.
- A batch fetched before its topic was deleted and recreated no longer resolves offsets into the new topic. Its remaining records are not delivered, its offsets are dropped, and neither an automatic, a final nor an explicit `commitOffsets` from its handler can commit them. Before, a handler finishing old records after the recreation resolved their offset into the new incarnation's cell, and the close's final commit then wrote that offset (for example 8 against a new log of 0..2) and settled the reset the new incarnation still owed. A handler already running may finish.

- Keep incremental Fetch state bound to its run and broker, preserve recorded topic IDs when forgetting partitions, decode sparse replies against the complete request map, and bound best-effort session closes within the captured close budget.

- Round-robin group assignment now sends a valid empty assignment to each member that receives no partitions, including groups with more members than partitions.

- A classic consumer crashes and restarts when a join or sync round outlasts the rebalance timeout; the restarted consumer now rejoins under the member id the expired round held, instead of asking the coordinator for a new member and leaving the old one to expire with its session. A restart after any other crash still joins as a new member, and an id the coordinator no longer knows is dropped by the rejoin, which asks for a fresh one.

- `consumer.commitOffsets()` answered with `REBALANCE_IN_PROGRESS` still rejects with that error, and now also asks the group to rejoin, as the same answer to a heartbeat already did.

- Consumer: one group-coordinator lookup per membership. While a heartbeat's FindCoordinator is pending, concurrent explicit `commitOffsets()` calls, automatic commits and joins now wait for that one lookup instead of each starting their own (N commits made N lookups), for the classic and the consumer group protocol. Each caller keeps its own deadline and close; one caller giving up does not cancel the others, and the lookup ends when its last caller or its membership does. A stop sends no frame for a pending lookup, and an answer for a retired membership is installed for no one. A handler's explicit commit that is still waiting on the lookup when a stop begins rejects with `CONSUMER_STOPPING` and gets no promise of completion (see Behavior changes); a commit from outside the handlers and an authorized close-hook commit may still complete through that lookup. Internal change (`src/consumer/coordinatorLookup.js`); no public API change. Closes the RB-07 duplicate-coordinator-load finding.

### Phase 9B — Producer parity: delivery deadline, memory bound, request size, partitioner, codecs, lifecycle

#### Behavior changes

- **Producer sends now have a delivery deadline: `deliveryTimeout` defaults to 120 000 ms, counted from the `send()` call, and producer retries are bounded by that time, not by a count of 5.** The producer's retry backoff starts at 100 ms and is capped at 1 000 ms (Java's `retry.backoff.ms` and `retry.backoff.max.ms`) when you set none. An explicit `retry.retries`, `retry.maxTotalTime` or backoff setting is honoured. A send that used to give up after the five default retries now keeps retrying until its deadline (two minutes by default) and then rejects with `KafkaJSDeliveryTimeout` (its `cause` is the last error, and it carries that error's `type` and `code`). An unset deadline is raised to `linger + requestTimeout` when that is larger; an explicit one below it is rejected

- **A queued or on-wire send now rejects at its delivery deadline, even while the operation it awaits has not returned.** A late answer cannot settle the send again. Expiry fences later writes and reconciles the batch's sequence state; it does not cancel a request already written. A timeout is `outcome: 'unsent'` only when no attempt carrying the records could have been written, and `outcome: 'unknown'` otherwise, including an earlier write followed by a retriable answer. Resending an unknown delivery may duplicate records. There is no escape to the old late-settlement behavior.

- **`send()` now has a memory bound: `bufferMemory` (32 MiB) and `maxBlockMs` (60 000 ms).** Sends are admitted in order; a send that cannot be admitted within `maxBlockMs` rejects with the retriable `KafkaJSBufferExhaustedError`, a send that cannot be admitted before its delivery deadline passes rejects with `KafkaJSDeliveryTimeout` (`'unsent'`), a send that cannot fit at all with `KafkaJSRecordTooLargeError` (`reason: 'bufferMemory'`). Inside a transaction each of these refusals **arms the transaction as abortable** while the send keeps its own error. The bound is a charge for what the producer retains, not a limit on the process's memory

- **`maxRequestSize` (1 MiB) bounds every Produce request, measured on the encoded frame.** A record that cannot fit rejects its `send()` at admission, before anything is queued or written, with `KafkaJSRecordTooLargeError` (non-retriable, `type` `MESSAGE_TOO_LARGE`); a `send()` of several records larger than one request is split at record boundaries, admitted whole and delivered per chunk: if one chunk fails the send rejects with that error and chunks already delivered stay written; a request whose compressed frame would exceed the limit is refused before that write and its never-transmitted records are repartitioned (a chunk that was already transmitted keeps its grouping, and if its retry would exceed the cap it fails locally without another write, which does not show that the earlier attempts were unsent). Inside a transaction a size refusal **arms the transaction as abortable** while the send keeps its own error. A send that fits one request is unchanged

- **When `createPartitioner` is omitted, keyless records now use the uniform sticky partitioner (KIP-794) instead of per-record round robin** (plain uniform sticky: adaptive weighting by partition queue depth is opt-in, `UniformStickyPartitioner({ adaptive: true })`, until the release's measured gate passes). Keyed records and explicit partitions map exactly as before; the "KafkaJS v2.0.0 switched default partitioner" warning is gone

- **Snappy is built in** (decode and encode, Kafka's xerial framing) instead of throwing `KafkaJSNotImplemented`. A codec you register at `CompressionCodecs[CompressionTypes.Snappy]` still takes precedence

- **Decompression is bounded for every codec (`maxDecompressedBatchBytes`, default 1 GiB), and a batch past the bound, a corrupt compressed stream, an impossible record count, or a record count past the derived ceiling halts only that partition**: the records before it are delivered, `consumer.partition_halted` fires with the reason, `codec`, `limit` and (when a validated batch boundary exists) `nextOffset`, and the partition is not fetched again until `consumer.seek`. Before, **a record-level decode error after decompression** (for example valid decompressed bytes that did not parse as records) was swallowed as a truncated tail and the partition silently made no progress; other decompressor errors were not swallowed there

- **A record batch whose CRC32C does not match (`checkCrcs`, on by default) now halts its partition like any corrupt batch, instead of crashing the consumer.** Other partitions keep delivering

- **`producer.disconnect()` aborts an open transaction, accepts `{ timeout }`, and a second call does nothing; `producer.flush()` is new.** With `timeout`, at the deadline unsent sends reject with `KafkaJSProducerClosedError` (`outcome: 'unsent'`), sent ones with `outcome: 'unknown'`, pending retries are cancelled, no new connection is opened by an old operation, and the connections close; a commit whose outcome is unknown stays unknown and no abort is sent. A second `disconnect()` after the first completed no longer re-sends a pending commit; a later `connect()` starts a fresh producer lifecycle

- **A producer forgets the metadata of topics it has not produced to, and has no work for, for `metadataMaxIdle` (300 000 ms)**, so an application that produces to many changing topics no longer asks for all of them at every refresh

- **The fields of a record are read once, when `send()` or `sendBatch()` is called**: changing a record object, its headers, a header-value array or a `Date` or `Long` timestamp after the call no longer changes what is sent. **Validation, including the missing-value and timestamp checks, uses that owned snapshot, so changing accessors are not re-read.** The **bytes** of a `Buffer` value are not copied (as before) and still reach the wire if you change them, except a `Buffer` that is a small view of a large backing store, which is copied

- **A producer fenced by its initial InitProducerId response (`INVALID_PRODUCER_EPOCH` or `PRODUCER_FENCED`) now rejects with `KafkaJSApplicationRecoverableError` and remains unusable.** Its `cause` preserves the protocol error; create a new producer instead of retrying initialization on that object. After a producer has become unusable, `connect()`, `send()`, `sendBatch()`, `transaction()` and `flush()` reject with that same error object, also after `disconnect()`, which stays callable; work already under way on that producer, a send, a transaction call or a pending initialization, ends with the same error object and nothing is written for it afterwards

#### Fixes

- A KIP-848 consumer no longer sends a heartbeat for a membership that was replaced while its coordinator lookup was still running. The late lookup used to finish, publish its coordinator and send a heartbeat carrying the replacement's member epoch, and a failed late lookup recorded a heartbeat backoff on the replacement. A lookup that outlives its membership now does nothing more: it sends nothing, publishes no coordinator and records no backoff, and its error is dropped as obsolete.

- `producer.transaction()` and a transactional producer's first `InitProducerId` no longer fail on one reset or lost connection while looking up the transaction coordinator. In 2.2.4 that lookup ran inside the first `send()` of a transaction, under the producer's `retry` settings; an earlier 3.0.0 pre-release moved it into `transaction()` with no retry, so a single `ECONNRESET` rejected `transaction()` with a bare retriable `KafkaJSConnectionError`. The lookup is now retried while it fails retriably, under your `retry` settings (the same ones `commit()` and `abort()` use for their coordinator lookup), also for the lookup of an owed epoch bump; a producer that is disconnected or fenced meanwhile stops at once. If the retries run out, `transaction()` rejects with `KafkaJSNumberOfRetriesExceeded`. If `retry.maxTotalTime` runs out first, it rejects with `KafkaJSDeliveryTimeout`. The `cause` is the connection error (`retriable: true`) and the producer stays ready. The rejection itself is not `retriable`. A failure that is not retriable (a refused lookup, `KafkaJSGroupCoordinatorNotFound`, a fenced or unusable producer) still rejects at once, as before. Consumers and admin, which share the group-coordinator lookup, are unchanged.

#### Additions

- Producers accept optional `compressionLevels: { gzip, zstd }` and direct broker Produce requests accept `compressionLevel`. Codec defaults are unchanged. LZ4 levels are unavailable in `lz4-napi` and are rejected.

- `KafkaJSDeliveryTimeout` accepts optional `outcome: 'unsent' | 'unknown'` and copies its cause's `type` and `code` when present. An absent `outcome` says nothing about delivery; retry exhaustion, connection errors, configuration errors and broker answers do not receive it.

- **`maxDecompressedBatchBytes`**, a new `Kafka#consumer` option (an integer from 1 to 2 147 483 647, default 1 073 741 824): the most one record batch may decompress to, in bytes, for every codec, and the source of the derived ceiling of `max(1, floor(value / 512))` records per batch. `KafkaJSCorruptRecordError` gains the reasons `checksum`, `decompressed-size` and `decompression` and the optional `codec`, `limit` and `nextOffset`; `consumer.partition_halted` carries `codec`, `limit` and `nextOffset` when the error has them; `Broker#fetch` accepts the option; a codec registered in `CompressionCodecs` now receives the bound as `decompress(buffer, { maxOutputLength })`. These optional event fields are copied from the `KafkaJSCorruptRecordError`; the existing groupId, memberId, topic, partition, offset, reason and error fields are retained.

- The type of `ProducerConfig.deliveryTimeout` documents its default of 120 000 ms and its precedence over `retry.maxTotalTime`.

- `KafkaJSBufferExhaustedError` (retriable; `reason` `'timeout'` or `'queue-full'`, with `requested`, `available`, `capacity` and `waitedMs`) and `KafkaJSRecordTooLargeError` (non-retriable; the `type` `MESSAGE_TOO_LARGE` and `code` 10 of the broker's error, with `reason: 'bufferMemory'`, `scope`, `size`, `limit` and `topic`) are exported from both entry points, with their types; the producer options `bufferMemory` (default 33554432 bytes) and `maxBlockMs` (default 60000 ms) bound what a producer holds for its sends and how long a send waits for room.

- The producer option `maxRequestSize` (default 1048576 bytes, Java's `max.request.size`) bounds every Produce request on its encoded frame, an integer from the smallest request the producer's `clientId` and `transactionalId` allow to 2147483647; `KafkaJSRecordTooLargeError` gains `reason: 'maxRequestSize'` for a record no request can carry, and for a refused write that cannot be divided.

- `Partitioners.UniformStickyPartitioner({ adaptive })` weighs each pick of a partition by the batches waiting for it (KIP-794's adaptive partitioning; a boolean, default `false`); the sticky partitioner now counts each record's wire size, leaves a partition that lost its leader, and forgets topics idle for 300 000 ms; built-in partitioners are attached to the producer's queue depths and broker racks (the KIP-1123 seam; no rack-aware choice).

- Producers accept `metadataMaxIdle` (default 300000 ms, range 5000–2147483647 ms) and retain metadata for topics while pending work owns it.

- `producer.flush({ timeout })` waits for sends made before the call, without replacing each send's own result.

- `producer.disconnect({ timeout })` bounds shutdown and fences work from the closed lifecycle.

- `KafkaJSProducerClosedError` carries required `outcome: 'unsent' | 'unknown'` transmission evidence.

### Phase 2 — bug fixes and dead-path cleanup

#### Behavior changes
- Request versions below the Kafka 4.0 floors (KIP-896, KIP-724) are no longer implemented: Produce v0–2, Fetch v0–3, ListOffsets v0, OffsetCommit v0–1, CreateTopics v0–1, DeleteTopics v0, DescribeAcls/CreateAcls/DeleteAcls v0, DescribeConfigs v0. A 4.x broker never negotiates them. The MessageSet (magic 0/1) *read* path is kept because old segments can still be served inside Fetch ≥ v4.
- The pre-KIP-152 raw SASL token path (used only when a broker lacked `SaslAuthenticate`) is removed; every mechanism goes through `SaslAuthenticate`.
- Version negotiation now rejects an API whose broker range does not overlap the client range with `KafkaJSServerDoesNotSupportApiKey` (message names both ranges) instead of sending a version the broker rejects or selecting one the client does not implement.
- `retry.restartOnFailure`, when supplied, is now consulted for every terminal consumer crash, retriable or not — previously it was only invoked for errors KafkaJS considered retriable, so a callback returning `true`/`false` was silently ignored on non-retriable errors. Callers who never set `restartOnFailure` see no change: the default remains "restart on retriable errors, stop on non-retriable ones". If the consumer is stopped or disconnected while the callback is still deciding, no restart is scheduled.
- A broker whose SASL authentication just failed (`SASL_AUTHENTICATION_FAILED`, code 58) is now blacked out for `max(authenticationTimeout, 1000ms)` before the next (re)authentication attempt, instead of being retried immediately — this avoids a reconnect storm against a broker that will keep rejecting the same credentials. `authenticationTimeout` defaults to 10000ms, so the out-of-the-box window is 10s, not 1s. The blackout only gates an attempt that would actually (re)connect or (re)authenticate: an already-connected, already-authenticated connection, and any request sent over it, is unaffected during the window. An attempt refused by the blackout throws the same non-retriable `KafkaJSSASLAuthenticationError` the original failure did, carrying that failure's broker message (e.g. "Invalid username or password"), so retriers stop immediately instead of exhausting their budget into `KafkaJSNumberOfRetriesExceeded`. The blackout itself survives a `BrokerPool` connection-pool rebuild (seed broker rotation, illegal SASL state recovery).
- A consumer configured with `groupInstanceId` (static membership, KIP-345) no longer sends LeaveGroup on `consumer.disconnect()` — it keeps its slot and assigned partitions in the group until `sessionTimeout` elapses, instead of triggering an immediate rebalance for every replica of a rolling restart. **Operational impact:** any caller already passing `groupInstanceId` (previously inert — see Additions below) will see every `disconnect()` stall the group's rebalance until `sessionTimeout` expires. To make a static member leave at once, pass `{ leaveGroup: true }` to `consumer.disconnect()` (see Phase 8, Additions); otherwise mitigate by lowering `sessionTimeout` for that consumer, or by not passing `groupInstanceId`. A rolling restart that rejoins under the *same* `groupInstanceId` before `sessionTimeout` expires is unaffected by the stall — the new instance takes over its partitions immediately (no rebalance), and it is the *old*, now-superseded process that gets fenced (`FENCED_INSTANCE_ID`, code 82) and crashes without restarting. Adopts the plumbing half of upstream PR #1594 (KIP-345); `OffsetCommit`/`DescribeGroups`/admin `removeMembersFromConsumerGroup` (the rest of that PR) are deferred (see Additions).
- `maxInFlightRequests` (producer and consumer) now defaults to `5` — Java's `max.in.flight.requests.per.connection` — instead of unbounded, so a broker connection queues client-side once 5 requests are outstanding rather than sending an unlimited number at once. Pass `maxInFlightRequests: null` to restore the previous unbounded behavior. No ordering guarantee is claimed by this change.

#### Fixes
- Request queue: an idle, unthrottled queue no longer re-arms a timer after every response (hundreds of wakeups per second at idle, `TimeoutNegativeWarning` on Node ≥ 24). Informed by upstream #1755, #1768, #1667, #1572 (issues #1704, #1751, #1556); implementation follows the Countly production patch and keeps the 10 ms re-check for a queue blocked by the in-flight limit. Retires Countly patch 1a.
- SyncGroup gets its own request timeout derived from `rebalanceTimeout` (or `sessionTimeout`) plus 5 s, as JoinGroup already did, so a rebalance whose assignment takes longer than the client-wide `requestTimeout` no longer dies with `KafkaJSRequestTimeoutError` and loops. No upstream issue exists for this; retires Countly patch 1b.
- The consumer's cached group coordinator is now re-discovered (via `FindCoordinator`) instead of being reconnected under its old, possibly stale, node id, so a coordinator failover no longer leaves `commitOffsets` looping forever on `NOT_COORDINATOR_FOR_GROUP`/`GROUP_COORDINATOR_NOT_AVAILABLE`. The consumer also now treats `GROUP_LOAD_IN_PROGRESS` (code 14) as a rebalance condition, so a JoinGroup against a still-loading coordinator retries the join instead of failing the consumer. Adopts upstream PR #1779 (issues #1536, #1630, #1654); retires Countly patch 2b. Alongside this, the dead string-based matches on the legacy error names for codes 14/15/16 in the idempotent producer's `sendOffsets` and in `admin#deleteGroups` are replaced with code-based matching, making their retry/coordinator-refresh branches reachable for the first time.
- CRASH now fires exactly once for every terminal death of the consumer runner, even when the cleanup `disconnect()` call inside the crash handler itself throws (e.g. the broker connection is already gone) — previously that rejection was unhandled and swallowed the CRASH event entirely, leaving the consumer silently dead with `consumer.run()` already resolved and nothing to observe it. The runner's crash-handling `.catch`/`start()` paths now `await` the crash handler and log (rather than drop) any error it still raises. Informed by upstream issue family #659, #1513; retires Countly patch 2a.
- The consumer runner now tells apart membership *lost* (`ILLEGAL_GENERATION` 22, `UNKNOWN_MEMBER_ID` 25, `FENCED_INSTANCE_ID` 82) from partitions *revoked* (every other rebalance-class error: `REBALANCE_IN_PROGRESS` 27, `NOT_COORDINATOR_FOR_GROUP` 16, `GROUP_LOAD_IN_PROGRESS` 14, ...) on both the heartbeat and fetch paths. Previously `ILLEGAL_GENERATION` was lumped in with the revoked cases and auto-committed on the way out, so a stale generation kept retrying a commit the broker would reject forever — the "Specified group generation id is not valid" crash loop — while `UNKNOWN_MEMBER_ID`/`FENCED_INSTANCE_ID` left their resolved offsets in place for a later commit under a dead generation instead. On a LOST error the consumer now discards its uncommitted offsets (`ConsumerGroup#discardUncommittedOffsets`) and rejoins without committing (member id is only reset for `UNKNOWN_MEMBER_ID`, since `ILLEGAL_GENERATION` doesn't invalidate the member id itself, and a fenced static member does not rejoin at all); on every REVOKED error — the same set `isRebalancing` always matched, minus the LOST codes, so no case silently loses its commit — the final commit is unchanged, and the `REBALANCING` instrumentation event still fires on the fetch path for both LOST and REVOKED errors as it always did. Informed by upstream #1712, #1466, #1527, #1009.
- With a preferred read replica active (KIP-392, consumers configured with `rackId`), a follower `OFFSET_OUT_OF_RANGE` now retries the fetch from the leader before resetting offsets, instead of always resetting — the guard in `ConsumerGroup#recoverFromOffsetOutOfRange` checked `typeof === 'number'` against the stored `{ nodeId, expireAt }` object, which is never a number, so the leader-retry branch was dead code.
- `KafkaJSError` and `KafkaJSNumberOfRetriesExceeded` now carry the wrapped protocol error's `type`/`code` instead of dropping them, so a rebalance error re-thrown from `ConsumerGroup#joinAndSync` (and its subclass `KafkaJSNonRetriableError`, including a fenced static member, code 82) stays typed all the way to user code instead of only being distinguishable by string-matching the message. No new error classes; message/name/behavior otherwise unchanged. Retires the error-taxonomy half of Countly patch 2d/2j (the heartbeat-starvation half is Phase 6).
- The idempotent producer no longer stays poisoned after a transient `InitProducerId` failure: previously `connect()` would reject with the producer id never set, and every later `send()`/`sendBatch()` produced without one until the process restarted. `send()`/`sendBatch()` now lazily re-run `InitProducerId` whenever the producer isn't yet initialized, sharing one in-flight request across concurrent calls. Retires the init-retry half of Countly patch 2g (the KIP-360 epoch-bump half is Phase 7).
- `sendOffsets()`'s `AddOffsetsToTxn` call is now wrapped in the same retrier `initProducerId` already uses, so `CONCURRENT_TRANSACTIONS` (code 51) — Kafka's expected response while a prior transaction on the same transactional id is still completing — is retried instead of failing the transaction outright.
- `THROTTLING_QUOTA_EXCEEDED` (code 89) is now a known, retriable protocol error instead of decoding as `KAFKAJS_UNKNOWN_ERROR_CODE` (non-retriable), so a quota-throttled request retries instead of failing outright. Adopts upstream PR #1695.
- Every fixed-width and length-prefixed read in the protocol decoder is now bounds-checked, so a truncated or corrupt broker response throws the existing `KafkaJSPartialMessageError` instead of Node's `ERR_BUFFER_OUT_OF_BOUNDS` or returning silent garbage. Legitimate null/empty encodings (null strings/bytes/arrays, empty compact arrays, empty tagged fields) are unaffected. Informed by upstream #1374, #1153. A negative declared length other than the null sentinel (-1) now throws the same error instead of silently rewinding the offset.
- The idempotent producer's "Limiting retries for the idempotent producer may invalidate EoS guarantees" warning now only logs when the configured `retry.retries` is below `5` (the non-idempotent default), not for every finite value — a user who deliberately sets a high, finite `retries` (e.g. `Number.MAX_SAFE_INTEGER`) no longer gets warned on every producer construction. The hard error for `retries < 1` is unchanged, and no default changed. Retires Countly patch 2i.
- Metadata refresh (`BrokerPool#refreshMetadata`) now retries `UNKNOWN_TOPIC_OR_PARTITION` when `allowAutoTopicCreation` is true (the default for producers and consumers), instead of failing on the first attempt — KRaft answers this error while it creates the topic asynchronously through the controller, where ZooKeeper-era brokers answered `LEADER_NOT_AVAILABLE` and created it inline. With `allowAutoTopicCreation` false the error still surfaces immediately. `kafka.admin()` always runs with it false, so `admin.fetchTopicMetadata()` does not retry `UNKNOWN_TOPIC_OR_PARTITION`: it rejects with it at once. Adopts upstream PR #1558 (issues #815, #1752); retires quarantine row R1.
- Help URLs in error messages now point at this repository's docs instead of kafka.js.org (which documents upstream kafkajs 2.2.4).

#### Additions
- New producer instrumentation event `INITIALIZED` (`producer.events.INITIALIZED`), emitted for idempotent producers once a producer id has been obtained — i.e. once it's safe to `send()` — whether that happens during `connect()` or via the lazy re-init path above; not emitted for non-idempotent producers. `CONNECT` keeps firing exactly where it always has.
- New `AUTHENTICATION_FAILURE` instrumentation event (consumer/producer/admin), emitted when a broker rejects SASL authentication with `SASL_AUTHENTICATION_FAILED` (code 58). Payload: `{ broker, mechanism, errorMessage }`, where `errorMessage` is the broker's own `error_message` when it sent one.

- New consumer option `groupInstanceId` (KIP-345 static membership), now actually plumbed through to JoinGroup v5 / SyncGroup v3 / Heartbeat v3 / LeaveGroup v3 — the codecs already encoded it, but no caller ever passed it, so it was silently inert. A duplicate `groupInstanceId` on the same group admits the new consumer immediately and fences the *existing* one with `FENCED_INSTANCE_ID` (code 82) on its next heartbeat instead; the fenced consumer's `CRASH` event now reports `restart: false` unconditionally (it would otherwise loop, immediately re-fenced). The `HEARTBEAT` instrumentation event's payload also gains `groupInstanceId` (`string | null`), for every consumer, not only static ones. #### Performance
- `arrayDiff` now builds a `Set` from the second array once and does an O(1) membership check per element, instead of an `indexOf` scan of the second array for every element of the first (O(n·m)). It's on the hot path for `ConsumerGroup#checkForStaleAssignment`, `BrokerPool#refreshMetadata`, and rebalancing, so this matters most on high-partition-count topics. Behavior is unchanged except for `NaN` (`Set#has` uses SameValueZero, `indexOf` uses strict equality), which never appears in a topic name, partition id, or broker id. Adopts upstream PR #1738.
- `groupMessagesPerPartition` now pushes each message onto its partition's array in place instead of spreading the whole array into a new one per message (`reduce` + `[...current, message]`, O(n²) for n messages landing on the same partition). Grouping, order and the plain-object return shape are unchanged. A throwaway benchmark (messages into a single partition) measured roughly 480× faster at n=32 000 (590ms → 1.2ms; 2 000: 4.0ms → 0.2ms, 8 000: 27.8ms → 0.2ms). Adopts upstream PR #1576.
- The idempotent/transactional producer's per-broker mutex (the one behind `KafkaJSLockTimeout`, ~65.5s) is now observable: `Lock` optionally takes a `description` and an `instrumentationEmitter` and emits the new `LOCK_TIMEOUT` producer event when a waiter times out, so contention on this mutex can be measured with real traffic instead of only inferred from a `KafkaJSLockTimeout` crash. The mutex itself, its timeout, and the error it throws are unchanged; removing it is planned for a later release.

### Phase 4 — flexible protocol foundation

#### Behavior changes
- The client now negotiates **ApiVersions v4** instead of v2 and identifies itself to the broker as `countly-kafkajs` with this package's version (KIP-511). Operators see it on the `kafka.server:type=socket-server-metrics,clientSoftwareName=…,clientSoftwareVersion=…` gauge and in the request log, where kafkajs previously appeared as `unknown`/`unknown`. Asking for v4 rather than v3 also means the broker's `SupportedFeatures` list is complete (v0–v3 responses omit any feature whose minimum supported version is 0 — KAFKA-17011).
- Two error-class changes fall out of the KIP-511 negotiation rewrite below. If every version the broker offers still fails after the one retry, the client now lets the underlying `KafkaJSProtocolError` ("The version of API is not supported", `type: 'UNSUPPORTED_VERSION'`, `code: 35`) propagate instead of wrapping it in `KafkaJSNonRetriableError('API Versions not supported')`. And when the broker answers `INVALID_REQUEST` (42) — rejecting the client's software name or version — the client now closes the connection and throws a `KafkaJSNonRetriableError` (carrying the original `type`/`code`/`cause`) instead of the previous behavior of rethrowing the raw `KafkaJSProtocolError` on the first attempt with the connection left open. Code that does `instanceof KafkaJSNonRetriableError` or `e.type === 'INVALID_REQUEST'` around `connect()` should account for both.
- API version negotiation now happens once per **broker connection pool**, not once per `Broker` object: `broker.connect()` re-runs ApiVersions whenever `Broker#connect()` finds that the broker's pool has been (re)established since the last negotiation — either of its two sockets being new counts; a fetch socket the pool re-establishes on its own while the other socket stays up keeps the current table until the next `connect()` — and rebuilds the request-version lookup table from the answer, which is then shared by both sockets (KIP-35 rule 7). Previously the versions learned on the first connection were cached for the object's lifetime, and the seed broker's table was copied to every other broker in the cluster, so a rolling broker upgrade or downgrade left the client negotiating against stale information. The cost is one extra round trip per (re)connect per broker.
- `Broker#isConnected()` (part of the published type surface — `Cluster#findBroker`/`findControllerBroker`/`findGroupCoordinator` hand `Broker` objects to user code) now also requires that ApiVersions has negotiated at least once, not just that the pool's socket(s) are up and authenticated where required. Making every reconnect re-negotiate (the KIP-35 rule 7 change above) reopened a window — previously near-zero-width for a `BrokerPool`-seeded broker's first connect, since it used to skip negotiation entirely — where the socket is connected but the ApiVersions round trip is still in flight; a caller outside `connect()`'s lock that only checked `isConnected()` (`BrokerPool#connectBroker`, deciding whether to call `connect()` at all) could see that window as "ready," skip connecting, and crash the first request on `lookupRequest`'s placeholder ("Broker not connected"). This can only ever turn a previously-incorrect `true` into a correct `false`: a broker `isConnected()` already reported connected for is unaffected, and a reconnect that leaves a stale-but-still-valid table in place while re-negotiating in the background does not fail this check, since the placeholder is only ever in effect before a `Broker`'s very first successful negotiation.
- Metadata requests are now sent at **v12** instead of v6, the first pilot of the flexible (KIP-482) encoding on a hot path. The client still asks by topic name — from v10 the request carries the all-zero topic-id sentinel next to the name — and still asks for no authorized-operations data. The decoded metadata gains `topicId` and `topicAuthorizedOperations` per topic and `leaderEpoch` per partition; nothing routes on them yet. The top-level `clusterAuthorizedOperations` this client's v8 codec started returning (always `-2147483648`, since it is never requested) disappears from `cluster.metadata()`'s result at v11+, since that field's own version range closes at v10 (KIP-700 moved cluster-authorized-ops to DescribeCluster) — nothing in this client reads it.
- Record-batch CRC32C checksums are now verified on the consumer path, controlled by the new `checkCrcs` consumer option, **default `true`** (Java's `check.crcs`). Previously the CRC was read and discarded, so a corrupt batch was handed to the application as if it were valid. A mismatch is now a **non-retriable** error: no message from that batch reaches `eachMessage`/`eachBatch`, the consumer crashes with `KafkaJSPartialMessageError` marked with a new `crcMismatch: true` property (distinguishing it from an ordinary truncated fetch tail, which is still tolerated silently as before; the `CRASH` event's `restart` follows `retry.restartOnFailure`, as for every other non-retriable error), and the offset is **not** advanced past the corrupt batch, so a restart re-reads it rather than skipping data. Pass `checkCrcs: false` to restore the previous behaviour. `Broker#fetch`'s published type also gains the same `checkCrcs?: boolean` option, for consistency with the consumer-facing one. Cost measured on this release: CRC32C is an O(batch size) full-buffer scan the decoder previously skipped entirely, so its cost scales with batch size rather than record count — with the slicing-by-8 implementation below (~1.1 GB/s), an isolated decode-loop microbenchmark measured +0.6µs on a 481B/10-record batch, +19µs on a ~21KB/100-record batch, and +225µs on a ~250KB/500-record batch (median of 3 runs, 100-2000 iterations each). As a fraction of decode-loop time alone that is 17-160%, growing with batch size; against real end-to-end fetch latency (network round trip plus broker-side I/O, not isolated here) it is expected to be far smaller, but that end-to-end number was not measured for this release.

#### Fixes
- `Decoder#readUVarIntBytes` returned one byte too many for every COMPACT_BYTES field: it correctly advanced the offset by the payload length (compact prefixes encode *length + 1*) but sliced `length + 1` bytes, so the returned buffer carried the first byte of whatever followed — or, at the end of a frame, silently came back short, because the bounds check only covered the payload. No shipped codec read a non-empty compact bytes field, so nothing decoded wrongly in 2.2.4; the flexible codecs added in this release do.
- `Decoder#readTaggedFields` now returns the tagged values (`Map<number, Buffer>`, unknown tags kept as raw bytes) instead of an empty object, skips each value by its true raw length, and rejects a section whose tags are out of order or duplicated with `KafkaJSPartialMessageError`. Previously it discarded every value and mis-skipped every non-empty one, so the first broker response carrying a real tagged field would have desynchronised the decoder.
- Request and response header versions are now chosen per `(apiKey, apiVersion)` from the message's declared flexible versions (KIP-482): a flexible version gets request header v2 and response header v1, everything else keeps header v1/v0, and the ApiVersions response is always read with header v0 so the UNSUPPORTED_VERSION downgrade stays parseable. `client_id` remains a classic two-byte-length string in header v2, as `RequestHeader.json` requires. Previously the client only ever wrote header v1 and only ever read header v0.
- `alterPartitionReassignments` and `listPartitionReassignments` no longer hand-roll the flexible request/response header inside their message bodies. They were written before the client could produce request header v2, so they emitted the header's tag buffer as the first byte of the body and consumed the response header's tag buffer inside their decoder; both now go through the shared header path. The bytes on the wire are unchanged.
- On `UNSUPPORTED_VERSION` from ApiVersions the client now reads the `api_keys` array the broker sends with the error (KIP-511) and retries once at `min(ourMax, brokerMax)`, instead of blindly stepping down one version at a time and discarding the hint — the v0 decoder used to throw before reaching the array. An empty array (pre-2.4 broker) falls back to v0, and `INVALID_REQUEST` (42) — the broker rejecting the client software name or version — now closes the connection instead of leaving it open.
- `Connection#connect()` no longer lets a reconnect race the previous socket's own asynchronous teardown. Every socket event handler (`onConnect`/`onData`/`onEnd`/`onError`/`onTimeout`) is now tied to a per-attempt token taken before the socket is created, so a handler still attached to a socket a later attempt has superseded recognises this and does nothing — the remote FIN for a just-disconnected socket can arrive after a new socket has already been created for the same `Connection`, and used to let the stale handler call `disconnect()`, tearing down the brand-new socket instead; this surfaced as a `KafkaJSConnectionClosedError` immediately after a disconnect-then-reconnect against a real broker. `disconnect()` also now detaches the socket's `data`/`end`/`timeout` listeners before closing it (an inert `error` listener stays attached so a post-close error can't become an uncaught exception), and explicitly rejects an in-flight `connect()` attempt it supersedes instead of leaving the caller to its own timeout. Concurrent `connect()` calls on the same `Connection` — reachable from the request path, since `ConnectionPool#getConnection` has no lock — now share one underlying attempt and settle together, rather than each racing to create its own socket. The reconnect re-negotiation added in this phase relies on reconnecting safely, so this fix is a prerequisite for it rather than a separate one. Two more overlap windows in the same mechanism are closed: `disconnect()` now captures the socket it owns and the attempt epoch it belongs to *before* its own internal wait for pending requests to drain, so an overlapping `disconnect()` call — e.g. a broker FIN's `onEnd` racing an application-level `disconnect()` — acts on the socket and status it actually owns rather than one a concurrent `connect()` installed while it was draining; superseded attempts are now rejected with a plain, retriable `KafkaJSConnectionError` rather than `KafkaJSConnectionClosedError`, which several `src/cluster/` branches did not recognise by name (they would otherwise skip seed-broker rotation and metadata refresh on a connect that was merely superseded, not refused); and `connect()` called while a `disconnect()` is still draining now rejects instead of resolving `true` on a connection that is about to end up disconnected. One more overlap window in the same family is closed: `send()`'s connectivity gate (`failIfNotConnected()`) now requires the connection to be fully `CONNECTED`, not merely `isConnected()`-truthy (which also counts `DISCONNECTING`, so `ConnectionPool` doesn't race a reconnect against an orderly teardown) — a `send()` call arriving while a `disconnect()` was draining could previously slip past both of `send()`'s connectivity checks, get written to the socket, and then have its listeners stripped out from under it with no response path, no close path, and (since `disconnect()` had already destroyed the request queue's only timeout timer) no timeout path either, so the request never settled. It now rejects immediately, at the same point it always rejected for an already-`DISCONNECTED` connection; a request already in flight when `disconnect()` starts is unaffected, since it settles via the response, `rejectRequests`, or the timeout interval, none of which route through this gate.
- `BrokerPool` rebuilding a broker's connection pool after `ILLEGAL_SASL_STATE` (`Broker#replaceConnectionPool`) now resets that broker's cached negotiation generation. The replacement pool restarts its own generation count at 0, which can coincide with the generation the stale table was learned at on the old, discarded pool — without the reset, `connect()` would wrongly treat the replacement pool's table as already negotiated and keep applying pre-upgrade/downgrade versions to both of its sockets.
- `Connection#disconnect()` dropped the reply to a request it was itself waiting on: the attempt epoch was ended before the pending-request drain, so the data handler discarded the in-flight response and `consumer.disconnect()` with a fetch in flight hung until the request timed out. The epoch now ends after the drain, and a disconnect superseded by a newer connect during the drain leaves the new socket alone.
- The protocol error table now covers every error code Kafka 4.3.1 defines (90–133, including `PRODUCER_FENCED` 90, `UNKNOWN_TOPIC_ID` 100, `INCONSISTENT_TOPIC_ID` 103, `FETCH_SESSION_TOPIC_ID_ERROR` 106, the consumer-protocol codes 110–113, `INVALID_REGULAR_EXPRESSION` 128 and `REBOOTSTRAP_REQUIRED` 129) instead of stopping at 89. Codes past the end used to surface as the non-retriable `KAFKAJS_UNKNOWN_ERROR_CODE`, so a retriable condition failed outright. The `retriable` flag is now derived from each error's exception hierarchy upstream and checked by `npm run compat:check`; no existing code's name, message or flag changed.

#### Additions
- Protocol primitives for KIP-482 flexible versions: the encoder can write tagged-field sections (`writeTaggedFields`, sorted by tag, empty section = one `0x00`) and the `uuid` type (`writeUuid`/`readUuid`, 16 raw big-endian bytes with the all-zero value as the null sentinel). Internal — `src/**` is not importable.
- Metadata v7 and v8 codecs. The decoded metadata now carries the partition `leaderEpoch` (v7+) and the topic/cluster authorized-operations bitfields (v8+); the client requests neither authorized-operations set (both flags are sent `false`). Nothing routes on these values yet.
- `src/protocol/recordBatch/crc32C/crc32C.js` (used by the new `checkCrcs` check above and, as before, by the producer's batch encoder) now uses the "slicing-by-8" technique instead of a byte-at-a-time table lookup, chosen by benchmark rather than by default: median of 3 runs, 200 iterations each, byte-at-a-time vs. slicing-by-8 — 1 KB: 458 vs. 858 MB/s (1.87x); 64 KB (the size dominating real fetch traffic): 467 vs. 1103 MB/s (2.36x); 1 MB: 467 vs. 1097 MB/s (2.35x). The decision rule was ≥1.5x at 64 KB; 2.36x cleared it. Same output for every input — the existing `index.spec.js` fixtures (including the Java cross-check vector) are unchanged and still pass.

#### Tooling
- New `npm run protocol:generate` / `npm run protocol:check`: `src/protocol/flexibleVersions.js` (the first flexible KIP-482 version of every API key) is generated from the committed Apache message-definition snapshot and checked for drift, so the header-version rule can never silently disagree with the protocol.
- New `node scripts/protocol/index.js scaffold <Api> <version>`: emits a codec skeleton (fields in wire order, per-version gating, classic-vs-compact writers, tag buffers, a JSDoc block quoting the schema, and the machine-checkable `schema` export) from the committed Apache message-definition snapshot. It never overwrites an existing file; codecs stay hand-written and hand-finished.
- New `npm run protocol:check`, part of `npm test`: every codec that declares a `schema` export is compared field by field against the committed Apache message definition for its version — order, type, version range, nullability, tag number, and whether the version is flexible. Codecs without a declared schema are listed as unvalidated so coverage grows API by API.
- New development-only generator `scripts/protocol/javaVectors/run.sh`: compiles a small Java program against the published `kafka-clients` jar and emits golden byte vectors from Apache's own generated codecs, so every flexible codec in this release is checked against the reference implementation as well as against captured broker bytes. The jar is fetched into a temporary directory and is never committed.
- New development-only `node scripts/protocol/capture.js`: records the raw bytes a live broker exchanges (through the public `socketFactory` hook, so it touches no internals), strips the protocol header, normalises the values that vary per run, and writes byte fixtures. The flexible codecs in this release are tested against captures from both Kafka 4.3.1 and 4.1.2.
- The internal version-lookup helper accepts a per-API ceiling, used by tests to pin a request to a specific protocol version. There is no user-facing version pin: the client always negotiates the highest version both sides support.

### Phase 5A — core APIs, part 1

#### Behavior changes

- Metadata requests are now sent at **v13** instead of v12. The only wire change is a top-level error code in the response, which the client now surfaces ahead of any topic- or partition-level error — this is how a broker tells a client its metadata is stale and it should rebootstrap (`REBOOTSTRAP_REQUIRED`, code 129). The decoded metadata gains an additive `errorCode` field; every existing key is unchanged.
- **Client rebootstrap is on by default** (KIP-899 / KIP-1102), matching the Java client: new `Kafka` options `metadataRecoveryStrategy` (`'rebootstrap'` by default, `'none'` to opt out) and `metadataRecoveryRebootstrapTriggerMs` (default `300000`, an integer of at least 1). The client rebuilds its connections and metadata from the configured broker list when (a) metadata has been failing *continuously* for the trigger window, (b) a broker answers `REBOOTSTRAP_REQUIRED` (code 129), or (c) every broker it knows about has become unreachable. "Continuously" is measured from the first failure that follows a success, so an idle client that hits one transient metadata failure does **not** rebootstrap. A rebootstrap waits for each connection's in-flight requests to drain, then closes every connection, so the caller's *next* request goes through its normal retry path against the rebuilt cluster — and until the idempotent producer is on by default, a producer retry after a rebootstrap can duplicate records the broker had already appended. The SASL authentication blackout is deliberately preserved across a rebootstrap, and a SASL authentication failure is never a trigger — a rejected credential means the broker is reachable and fine, only this client's credentials are bad, which no rebootstrap can fix. With `metadataRecoveryStrategy: 'none'` nothing changes from previous behaviour and code 129 surfaces as the non-retriable protocol error it already was.
- **A topic that is deleted and recreated now resets that topic's consumer offsets once.** When a metadata refresh sees a subscribed topic come back with a different topic id, the consumer emits `TOPIC_RECREATED`, drops its cached state for that topic, and resolves its next offsets from the configured boundary (`fromBeginning`) instead of from the coordinator's committed offset — once. Previously the committed offset from the *previous* incarnation was used, and because `__consumer_offsets` cleanup is asynchronous, an offset that happened to fall inside the new topic's range was accepted silently: the consumer skipped every record before it and never raised `OFFSET_OUT_OF_RANGE`. Offsets committed against the *new* incarnation are never discarded. (Superseded later in this release: the reset stays owed until a confirmed commit of the new incarnation, and a recreated topic starts unpaused.)
- Produce requests are now sent at **v11** instead of v7, moving the client's hottest write path onto the flexible (KIP-482) encoding. Two things become visible to callers. The thrown error for a failed produce now carries `topic`, `partition`, the broker's own `errorMessage`, and — when the broker rejected individual records — `recordErrors: [{ batchIndex, record, errorMessage }]`, where `record` is the message object you passed in (KIP-467). Which failure is reported is unchanged: the first failing partition across the response, exactly as before, and there is still no automatic re-batching — the whole batch fails as it always did. On a leadership error the broker now also tells the client which broker took over the partition; see the leader-hint entry below.
- **The producer now follows the leader hint a broker sends with a leadership error** (KIP-951). When a produce fails with `NOT_LEADER_FOR_PARTITION` or `FENCED_LEADER_EPOCH`, the broker also names the node that now leads the partition and, where the client may not know it, that node's address; the client applies both immediately, so its next retry attempt goes straight to the new leader instead of routing to the old one until the metadata refresh completes. Nothing else about producing changes: each partition's batch settles on its own answer, so a batch that succeeded is never sent again because of a hint, and the backoff and the sequence bookkeeping are unchanged.
- FindCoordinator requests are now sent at **v6** instead of v2. From v4 the protocol takes a list of coordinator keys and answers with a list; this client asks for exactly one and reads exactly one, and the decoded result keeps the shape it has always had. v6 changes nothing for this client — it only defines a key format for share groups, which this client does not use.
- OffsetCommit requests are now sent at **v8** instead of v5. A consumer configured with `groupInstanceId` (static membership) now sends it on offset commits too, completing the plumbing started in the previous release — previously it reached JoinGroup, SyncGroup, Heartbeat and LeaveGroup only. The per-partition committed leader epoch the protocol gained at v6 is sent as its default (`-1`): it means the leader epoch of the *consumed record*, which this release does not track, and sending the current metadata epoch instead would be a different value with a different meaning.
- OffsetFetch requests are now sent at **v8** instead of v4. From v8 the protocol takes and returns a list of groups; this client asks for exactly one and reads exactly one, and the decoded result keeps the shape it has always had. Each partition additionally carries `committedLeaderEpoch` — the leader epoch recorded alongside the committed offset — which nothing in this release reads. `RequireStable` is sent `false`, so a transactional producer's in-flight offsets are still returned as they were before.
- ListOffsets requests are now sent at **v9** instead of v3, and each requested partition now carries the leader epoch the client currently believes is in effect (`-1` when it does not know one yet), so a broker can reject a request built on metadata that has since moved. The response's per-partition leader epoch is decoded and returned additively. Versions 10 and 11 are deliberately not implemented: both exist for tiered storage, which this client does not use.
- InitProducerId requests are now sent at **v5** instead of v1. The producer id and epoch fields the request gained at v3 are sent as their defaults (`-1`), since this release does not yet re-initialise a fenced producer with its previous identity. Two error codes can now reach an idempotent or transactional producer's initialisation where the broker previously answered a different one — `PRODUCER_FENCED` and `TRANSACTION_ABORTABLE` — and both surface as the non-retriable protocol errors they already are. Version 6 is deliberately not implemented: it is the two-phase-commit protocol, which upstream still marks unstable.

#### Fixes

- `BrokerPool#refreshMetadata` now resolves its target broker and the seed broker's address *inside* the retry loop rather than once before it, so a reconnect or a seed rotation part-way through a refresh no longer leaves the remaining attempts talking to a disconnected broker, and no longer builds a duplicate `Broker` object for the seed's own node id.
- Four call sites (`Cluster#findBroker`, `Cluster#findGroupCoordinator`, and two in the producer's send retry) that refresh metadata as a best-effort side channel inside a `catch` block no longer let a failure of that refresh replace the original error the caller was already handling — a producer or consumer no longer sees an unrelated `KafkaJSNumberOfRetriesExceeded` (with its own, unrelated `retryCount`/`retryTime`) in place of a retriable send/lookup error when the cluster happens to be unreachable at the same moment.
- The topic-id error codes `UNKNOWN_TOPIC_ID` (100), `INCONSISTENT_TOPIC_ID` (103) and `FETCH_SESSION_TOPIC_ID_ERROR` (106) are now classified as stale-metadata conditions by both the producer and the consumer, so they refresh metadata and retry rather than failing. None of them can occur on the protocol versions this release negotiates; the classification is in place for the fetch-path work that follows.
- A `TOPIC_RECREATED` listener that throws can no longer break the client's metadata path. The event is now emitted only after the client's own state has been updated, and a listener that throws synchronously is logged and ignored instead of propagating out of the metadata refresh — previously it left the topic id un-updated, so the same recreation was re-detected and re-thrown on every later refresh, taking metadata (and, with rebootstrap on, every connection) down with it.
- `admin.fetchTopicOffsets`, `admin.fetchTopicOffsetsByTimestamp` and `admin.fetchOffsets({ resolveOffsets: true })` no longer fail outright when a leader election happens while they run. ListOffsets now carries the client's leader epoch, so a broker can answer `FENCED_LEADER_EPOCH`/`UNKNOWN_LEADER_EPOCH`; those and the other stale-metadata errors (`NOT_LEADER_FOR_PARTITION`, `LEADER_NOT_AVAILABLE`, the topic-id errors) are retriable, and the client now refreshes metadata and retries them instead of surfacing them as a hard failure during a rolling restart, a preferred-leader election or a just-created topic whose leadership has not propagated to every broker.
- The internal metadata cache no longer pins metadata it does not need. A response that describes the whole cluster (a regex subscription or `admin.listTopics()` asks for one) now prunes the topics it does not contain, and any topic missing from a refresh releases its reference to that refresh's decoded partition objects — previously one such call retained a record per topic and per partition, for every topic in the cluster, for the client's lifetime.
- A rebootstrap no longer leaves the client without a seed broker while it runs: the replacement is built and installed before anything is torn down, and the connect path treats a missing seed as a retriable connection error. A connection attempt that landed in that window previously crashed with a non-retriable `TypeError` instead of retrying.

#### Additions
- Internal metadata cache: the client now keeps each topic's id and each partition's leader epoch from the Metadata response, with a monotonic guard so a stale refresh cannot move a partition's leader backwards. Nothing user-visible changes yet; the cache is what the leader-hint, rebootstrap and topic-recreation behaviour described under Behavior changes is built on.
- New instrumentation event `TOPIC_RECREATED` on the consumer, producer and admin clients (`consumer.events.TOPIC_RECREATED`, delivered as `consumer.cluster.topic_recreated`, and the producer/admin equivalents). It fires when a metadata refresh sees a topic name it already knew come back with a different topic id — that is, the topic was deleted and recreated. Payload: `{ topic, previousTopicId, topicId }`.
- New instrumentation event `REBOOTSTRAP` on the consumer, producer and admin clients, payload `{ reason: 'timeout' | 'required' | 'all-brokers-unavailable' }`.
- The `COMMIT_OFFSETS` instrumentation event's payload gains `groupInstanceId` (`string | null`), for every consumer, matching what `HEARTBEAT` already carries.

#### Tooling

- Every protocol codec added in this release is checked against two independent sources as well as its own hand-built fixtures: byte vectors generated from Apache Kafka's own codecs (`scripts/protocol/javaVectors/run.sh`, extended to cover Produce, FindCoordinator, OffsetCommit, OffsetFetch, ListOffsets, InitProducerId and Metadata v13), and bytes captured from a live broker (`node scripts/protocol/capture.js`, extended to drive a producer and a consumer as well as an admin client). Captures are taken on both Kafka 4.3.1 and 4.1.2, within whatever version each broker advertises.
- New development-only `node scripts/benchmarks/produceResponseDecode.js`: measures the classic against the flexible produce-response decoder over the committed fixtures, so the cost of moving the produce path onto compact encoding is measured rather than assumed.

### Phase 5B — core APIs, part 2

#### Behavior changes

- When a broker reports that the client is ahead of it (`UNKNOWN_LEADER_EPOCH`, code 75) the client now forgets its cached leader epoch for the partitions involved instead of defending it. This is most visible on `admin.fetchTopicOffsets` and on consumer offset resets, which previously kept resending the same rejected epoch until the retry budget was exhausted (`KafkaJSNumberOfRetriesExceeded`); the call now converges on the next attempt. `FENCED_LEADER_EPOCH` (74) is unaffected — there the client is behind and a metadata refresh already converges.
- `broker.isConnected()` now also requires that API versions were negotiated on the *current* connection, so a socket the connection pool re-establishes on its own re-negotiates before it serves a request (KIP-35: version information is only valid for the connection it was learned on). This can only turn a previously-optimistic `true` into a correct `false`. It costs one extra ApiVersions round trip the first time a broker's second socket is opened, and — because the group coordinator is re-resolved whenever its broker is not connected — one extra `FindCoordinator` before the next commit after such a reconnect. Both converge immediately.
- Committed offsets now carry the leader epoch. `consumer.commitOffsets` and auto-commit send the epoch of the record whose offset is being committed (OffsetCommit v6+ `CommittedLeaderEpoch`, previously always -1), and read it back on assignment. Offsets committed by an older client have no epoch, so the first assignment after upgrading validates nothing; from the first commit onwards it does. An offset you commit yourself through `consumer.commitOffsets(offsets)`, and any offset resolved to a position with no record behind it, still carries no epoch. The partition entries of `consumer.events.COMMIT_OFFSETS` and of `uncommittedOffsets()` gain a `leaderEpoch` key alongside `partition` and `offset`, so only code that deep-equality-compares the whole payload is affected.
- Fetch and produce requests are keyed by topic id (KIP-516) whenever the client knows the ids, and fall back to topic names for that one request otherwise. This is invisible in the API — the decoded response, the `Batch` handed to `eachBatch`, and the fields of a produce error are unchanged — but it changes which protocol version the compatibility matrix reports for Fetch and Produce.
- Fetch requests now carry the client's cached leader epoch per partition (`CurrentLeaderEpoch`, available since Fetch v9 and previously always -1), so a broker can reject a fetch built on metadata that has since moved instead of serving it. A partition whose epoch the client has never seen still sends -1, which means "do not fence".
- A fetch error that affects one partition — a leader move, an unknown topic id, an offset not yet available on a follower — now skips only that partition for one round; the other partitions in the same response are delivered, and the consumer no longer leaves and rejoins the group over it. A partition that produces an error on five consecutive fetch rounds logs a warning, and another every twenty-five rounds after that, so a partition that is quietly making no progress is visible at the default log level.
- The top-level error code of a Fetch response is now acted on. It was decoded but never read before: the consumer now reads it on every version that carries it (Fetch v7 and up), the three fetch-session codes produce a warning, one metadata refresh and an empty round, and any other top-level code follows the same recovery path a request-level fetch error already followed. Because this client sends only sessionless fetches, the code is reachable only through those three.
- A leader move during consumption is handled by a hint instead of a rebalance. When the broker tells the client which node now leads a partition (KIP-951), the consumer routes the next fetch there directly; consumption of the other partitions is not interrupted and no group rebalance happens. If the hint names a broker the client has never heard of and carries no address for it, the client refreshes metadata instead of trusting the hint.
- Log truncation is detected and acted on. After a leader change the consumer now checks that its position still exists on the new leader, using the leader epoch of the last record it consumed. If the log diverged, the partition moves to the first offset known to diverge; if the divergence point cannot be determined, the partition resets per its `fromBeginning` setting — which, like the existing out-of-range reset, commits that offset to the coordinator even when `autoCommit: false`. Both cases log a warning and emit the new `consumer.events.LOG_TRUNCATION` event. Previously the records were silently skipped or silently redelivered. A paused partition can be repositioned this way and stays paused.
- A leader change sends a rack-aware consumer back to the leader for one round. When a partition's leader epoch changes, the consumer now drops that partition's preferred read replica along with its position validation, matching the Java client. A `rackId` consumer that was reading from a nearby follower reads from the leader until the next fetch response offers a new `preferredReadReplica`; previously it kept the old follower until the entry expired at `metadataMaxAge`. This can briefly move read traffic across availability zones after a leader election, and it also happens on the first fetch round of every new assignment, where no partition has been validated yet.
- A fetch round can now wait for position validation. After a leader epoch change, the consumer checks that partition's position with the new leader before the round's fetch goes out, so a fetch can be delayed by one OffsetForLeaderEpoch round trip per leader. A retriable reply is retried at most twice, on validation's own fixed budget rather than the client's `retry` options, after which the round fetches unvalidated. This only happens around leader elections; a steady round waits for nothing.
- `broker.fetch()` no longer rejects on a fetch error — it returns the codes. `Broker` is a public type and `cluster.findBroker()` hands one to application code. Previously a fetch response's partition errors rejected the promise (the first failing partition won) and its top-level error code was decoded but never read. From Fetch v12 neither rejects: both come back in the response body, so a direct `broker.fetch(...)` caller reads `errorCode` at the top level and `responses[].partitions[].errorCode` per partition instead of catching. The consumer, the only in-tree caller, classifies both — the per-partition classification from v12, where the codec stops throwing, and the top-level one on every version that decodes the field.

#### Fixes

- A partition that loses its committed offset mid-round — which is how recovery from `OFFSET_OUT_OF_RANGE` works — is no longer read by position validation, and a partition with no committed offset no longer leaves an empty entry behind in the resolved offsets. Such an entry made the next auto-commit, and `consumer.commitOffsets()` with no arguments, throw a `TypeError` that crashed the consumer.
- A fetch request keyed by topic ids now refuses to encode a topic whose id is missing at every version that sends ids, not only at v13. A caller that supplied a partial id map would previously have put an all-zero id on the wire and looped on `UNKNOWN_TOPIC_ID`.
- `broker.produce()` called with a `transactionalId` is capped at Produce v11 whatever ids it carries, the same rule the producer applies. From v12 a produce inside a transaction implicitly adds the partition to the transaction, which this client does not do yet.
- A connection resolved by the caller is reconnected before the request is dispatched, so a socket that died between resolving it and sending no longer fails the request with `KafkaJSConnectionClosedError` where the previous code reconnected transparently.
- Version selection now returns a version this client actually implements rather than the broker's maximum bounded by the client's, so an API whose implemented versions ever have a gap cannot select a version with no codec. `broker.negotiatedVersion()` answers `null` before the broker has negotiated anything, as its contract says, instead of throwing.
- The compact array writer can encode an array of plain integers, so a fetch request's `forgottenTopics` partitions are written instead of silently dropped. Nothing sends them yet — every fetch this client makes is a full fetch.
- Position validation costs a steady fetch round nothing: a round where every partition is already validated against the current leader epoch now answers from a single lookup per partition, without reading offsets or building the objects the check used to allocate. This restores the per-batch consume latency the validation gate had added.
- Consumer group version negotiation no longer duplicates the protocol layer: the JoinGroup version behind the "static membership is inactive" warning is now read from the same selection rule every request uses, instead of being recomputed from the broker's advertised maximum. A coordinator that advertises no usable JoinGroup version is still handled silently.
- Decoding a record batch allocates less on the consume path: a record's offset is computed with plain integer arithmetic when both the batch's first offset and the resulting offset are safe integers (falling back to exact 64-bit arithmetic otherwise), and message headers are collected into one object instead of one object per header. The decoded message is unchanged — offsets and timestamps are still strings, and duplicate header keys still become arrays; a header key of literally `__proto__` behaves exactly as it did before.
- A decoded record's offset string is built through the client's 64-bit helper rather than `Number#toString`, which interned one string per record in V8's number-to-string cache and cost the consumer roughly 20% of its per-batch `eachBatch` handling latency. The offsets themselves are unchanged.

#### Additions

- Internal: requests can now be negotiated with a per-request version ceiling, which is what lets a single fetch fall back to topic names, or a single produce stay below the transaction-version-2 semantics, without changing the version every other request uses.
- `SaslAuthenticate` v2 is implemented (flexible encoding, request header v2). Custom authentication mechanisms are unaffected: a provider still returns length-prefixed bytes from `request.encode()` and still receives length-prefixed bytes in `response.decode()` — the framing change is contained inside the codec. A provider that returns a buffer whose length prefix disagrees with its contents now fails with a `KafkaJSSASLAuthenticationError` naming the mechanism, instead of putting a malformed frame on the wire.
- Fetch v12 and v13 are implemented: v12 moves the fetch request and response onto the flexible encoding (compact strings, arrays and records, tagged fields), and v13 keys topics by id instead of by name (KIP-516). **Fetch requests move from v11 to v12 with this change**; v13 and above are only negotiated once the caller supplies topic ids, which the consumer starts doing in a later change in this release. A `broker.fetch(...)` call that supplies no ids stays at v12 permanently.
- Fetch v14 through v18 are implemented, taking the client to the highest fetch version Kafka 4.3 advertises: v14 adds the tiered-storage error code, v15 replaces the top-level replica id with a replica-only tagged field this client never sends, v16 adds the KIP-951 `NodeEndpoints` hint to the response, and v17/v18 add two more replica-only tagged fields. v14, v17 and v18 are wire-identical to the version below them in both directions.
- Produce v12 and v13 are implemented. v12 is wire-identical to v11; v13 keys topics by id instead of by name (KIP-516). The decoded produce response and the fields of a produce error are unchanged at every version — the topic name is restored from the request's own id mapping while the response is decoded, so per-record error details keep attaching as before. A send inside a transaction is deliberately kept at Produce v11, because from v12 a produce inside a transaction implicitly adds the partition to the transaction; that path is not implemented yet.
- New consumer instrumentation event `consumer.events.LOG_TRUNCATION`, with payload `{ topic, partition, offset, divergingOffset, leaderEpoch }`. `offset` is where the consumer was; `divergingOffset` is where it resumes.
- `OffsetForLeaderEpoch` v3 and v4 are implemented (KIP-320), and `broker.offsetForLeaderEpoch()` appears on the `Broker` type. v2 is deliberately not implemented: versions below 3 require CLUSTER permission, which clients are not typically granted. The consumer uses it to detect log truncation; a broker that advertises no usable version is asked nothing and the consumer fetches unvalidated, logging one notice per broker per assignment.

#### Tooling

- The consumer logs its fetch requests and responses at debug level: what it asked each broker for (topics, ids, offsets and leader epochs), what came back per partition (error code, high watermark, message count), and how each batch was handled. The two costly payloads are built only when debug logging is actually enabled, so nothing is allocated for them at the default level. A partition dropped before delivery — because a seek is queued, because it is paused, or because its position is being validated — is logged with its reason whenever it happens.
- The three live scenarios that need a cluster to themselves have npm scripts: `test:e2e:leader-move`, `test:e2e:log-truncation` and `test:e2e:rebootstrap`. Each brings up its own cluster in the foreground and sets the environment variable its suite is gated on; the log-truncation one stops and starts brokers, so it must run alone.
- Two new development-only benchmarks: `node scripts/benchmarks/consumeThroughput.js` measures consume throughput and per-batch handling latency against a live cluster over a fixed corpus, and `node scripts/benchmarks/recordBatchDecode.js` measures the record-batch decoder over a committed fixture.
- Every protocol codec added in this release is checked against two independent sources as well as its own hand-built fixtures: byte vectors generated from Apache Kafka's own codecs (`scripts/protocol/javaVectors/run.sh`, extended to cover Fetch v12–v18, Produce v12/v13, OffsetForLeaderEpoch v3/v4 and SaslAuthenticate v2), and bytes captured from a live broker (`node scripts/protocol/capture.js`, whose version report now covers those APIs too). Versions no broker in the test matrix negotiates, and the SASL codec the capture client cannot reach, are recorded as deliberate capture gaps with the Java vector as the second source.
- The coverage floor enforced by `npm run test:coverage` now ratchets: it is set to the coverage measured at each internal release, rounded down to one decimal (97.1 % statements, 90 % branches, 97.9 % functions, 97.2 % lines at this one), so coverage can only go up.

### Phase 6A — classic-protocol consumer foundation

#### Behavior changes

- **The rebalance timeout default changes from 60 s to 5 minutes.** The JoinGroup rebalance timeout is now `maxPollInterval`, default 300000 ms, matching the Java client. If you never set `rebalanceTimeout`, a member that stops responding now holds up a group rebalance for up to 5 minutes instead of 60 seconds. **To keep the old 60 s rebalance timing, set `rebalanceTimeout: 60000`** — the legacy alias still goes on the wire unchanged, and it never becomes a handler-eviction deadline below 5 minutes. Setting `maxPollInterval: 60000` instead would also shorten your handler deadline to 60 s, which is usually not what you want. The SyncGroup client-side timeout is now explicitly capped at 60 s + 5 s rather than left to follow the rebalance timeout. At the default it is unchanged, but **if you set a rebalance timeout above 60 s it is shortened**: a `rebalanceTimeout: 120000` used to wait 125 s for the assignment and now waits 65 s, matching what the Java client sends for SyncGroup. If your group leader needs longer than that to compute an assignment, raise the client-wide `requestTimeout` instead, which still raises this one with it.
- **A handler that runs longer than the poll deadline now loses its partitions.** If your handler takes longer than `maxPollInterval` (5 minutes by default) to return, the consumer logs a warning, emits `consumer.poll_interval_exceeded`, leaves the group (dynamic members) or resets its generation (static members), discards uncommitted offsets and rejoins. Two details. The deadline is measured **per batch handed to your handler**, not per message: with `eachMessage`, one batch is bounded by `maxBytesPerPartition` rather than by a record count, so a very large batch is measured as a whole — unlike the Java client, which resets per poll of at most `max.poll.records`. And the overrun is detected on the next heartbeat tick after the deadline passes, never while a JoinGroup is in flight. **The guard is weaker than it sounds whenever more than one fetch can make progress**: the deadline is reset on every batch hand-off *and* on every fetch round that comes back empty, and fetching is per broker, so a single stuck handler does not trip it while another broker's fetcher keeps polling or another partition keeps flowing. It fires when *everything* stalls — which in practice means a single-broker assignment with `partitionsConsumedConcurrently: 1`. The batch the running handler finally returns is dropped, so that work is redelivered after the rejoin. Previously a long handler was never evicted as long as it called `heartbeat()`.
- **`rebalanceTimeout` is deprecated, and it does not become your eviction deadline.** It still works, still goes on the wire when it is the only one you set, and `rebalanceTimeout: 0` is unchanged — including its request timeouts, which still fall back to `sessionTimeout + 5000`. A legacy configuration's handler deadline is `max(rebalanceTimeout, 300000)`, so a 20 s or 60 s rebalance timeout never turns into a 20 s or 60 s handler deadline. Set `maxPollInterval` explicitly to make the two one number, as Java does. Setting `rebalanceTimeout` now logs a deprecation warning, once per consumer you construct.
- **Heartbeats now happen on a timer.** They are sent by a background timer at `heartbeatInterval`, so a handler that *awaits* no longer risks a session timeout. A handler that blocks the event loop without awaiting still blocks heartbeats, because Node has one thread; that case is unchanged. The `heartbeat()` callback keeps working exactly as before, and the timer and the callback share one in-flight request and one interval gate, so neither sends twice. The timer is suspended only while a JoinGroup request is in flight.
- **Cooperative rebalancing is available, opt-in, and needs two deploys.** `PartitionAssigners.cooperativeSticky` implements KIP-429. Deploy 1: `partitionAssigners: [PartitionAssigners.roundRobin, PartitionAssigners.cooperativeSticky]` — still eager, because the protocol is the highest one every configured assigner supports. Deploy 2, once every member is on deploy 1: `[PartitionAssigners.cooperativeSticky]` — now cooperative. During deploy 2 the group is briefly mixed: members on deploy 1 compute eager while restarted ones compute cooperative, and the coordinator picks `cooperative-sticky` for everyone because it is the only shared name. That is safe by construction — the eager members revoke everything before rejoining, and cooperative-sticky's withhold rule never hands a partition to a member that still owns it. A one-step upgrade splits the group with `INCONSISTENT_GROUP_PROTOCOL` until the deploy finishes.
- **Java-compatible assigners are available.** `PartitionAssigners.range`, `.sticky` and `.cooperativeSticky` implement the Java algorithms and advertise the Java wire names `range`, `sticky` and `cooperative-sticky`, so a group can mix this client with the Java one. The export key and the wire name are different things: the default assigner keeps the wire name `RoundRobinAssigner`, which no Java client understands — renaming it would split existing groups — and the default assigner list is unchanged at `[roundRobin]`. Rack-aware assignment is not implemented: `rackId` is sent and ignored.
- **Four new instrumentation events, and two existing payloads gain a field.** `consumer.partitions_assigned`, `consumer.partitions_revoked`, `consumer.partitions_lost` and `consumer.poll_interval_exceeded` are emitted on the default eager path as well as the cooperative one; `consumer.rebalancing` gains a `reason` and `consumer.group_join` a `rebalanceProtocol`. Every key those two payloads already had is unchanged, so only code that deep-equality-compares a whole payload is affected. One value moves: the `consumer.rebalancing` raised by an `UNKNOWN_MEMBER_ID` now reports `memberId: null`, the id the rejoin will actually use, because the unrecognized id is dropped before the round is reported rather than after.
- **A new INFO line at consumer construction.** Every consumer now logs one INFO line naming the rebalance protocol it selected and the assigners it selected it from. It changes no behaviour, but it is new output at the default log level.
- A `heartbeatInterval` above a third of `sessionTimeout` now logs a warning at construction. It is not an error, and nothing else changed: the existing hard failure when `heartbeatInterval >= sessionTimeout` is untouched.
- **On the cooperative path, `heartbeat()` no longer throws when a rebalance starts.** With a cooperative assigner configured, a `REBALANCE_IN_PROGRESS` no longer propagates out of the `heartbeat()` callback into your handler: the call resolves and the rejoin runs in the background while your handler keeps its partitions. `consumer.stop()` and `disconnect()` wait for that background round to finish before leaving the group, so shutdown is unaffected. On the default eager path the behaviour is unchanged — the callback still throws and your handler is interrupted. If you catch and act on that error today, note that it will not fire once you opt into cooperative rebalancing.
- **A rebalance now produces exactly one auto-commit.** The heartbeat path and the fetch path both used to commit on a `REBALANCE_IN_PROGRESS`, so the default eager rebalance issued two OffsetCommits. The offset work now happens once, at the single place a rebalance is handled.
- **A rebalance no longer re-delivers records from batches fetched under the previous assignment.** A batch carries the assignment it was fetched under, and one that outlived it is dropped before your handler runs and before its offsets are resolved or committed; those records are fetched again after the group has rejoined. Previously such a batch was handed to `eachMessage`/`eachBatch` while the new assignment was already re-fetching the same offsets, so the records arrived twice.
- **An eager rebalance now waits for in-flight handlers before it rejoins.** On the default eager path — and on any rebalance where this member's generation is gone — the consumer stops fetching and waits for every running `eachMessage`/`eachBatch` to return before it commits or discards offsets and rejoins the group, matching the Java client, which only rebalances between polls. The rejoin is therefore delayed by however long your handler takes to return from the batch it is on, bounded in practice by `maxPollInterval`. On the cooperative path nothing waits, which is the point of it.
- **A batch fetched for a partition the consumer no longer holds is now dropped** instead of being handed to your handler. Under cooperative rebalancing a round runs alongside the fetch loop, so a batch can outlive the assignment it was fetched under; delivering it would give you records another member now owns and auto-committing afterwards would roll that member's position back. The work is redelivered to the new owner. On the eager path this is unobservable, because the fetch layer is stopped for the whole round.
- **`resolveOffset` and `commitOffsetsIfNecessary` are no-ops for a partition the consumer no longer holds.** A handler already running when a cooperative round revokes its partition still runs to completion — it is not interrupted — but its position updates and commits for that partition are ignored. When you pass your own offsets to `commitOffsetsIfNecessary(offsets)` from `eachBatch`, the payload is filtered per partition: the partitions you still hold are committed and the rest are dropped, so one revoked partition in a payload no longer costs you the others.
- **The client-side timeout on JoinGroup is now `maxPollInterval + 5000`** — 305 s at the default, where 2.2.4 gave 65 s. A JoinGroup is held by the coordinator until every member has rejoined, so the client has to be willing to wait the whole rebalance timeout; the Java client sizes it the same way. The practical effect is that a coordinator that accepts a join and never answers now stalls that consumer for about five minutes rather than about one, and holds an in-flight request slot for that long. Lower `maxPollInterval` if you want it back: a client-wide `requestTimeout` does not shorten it.
- **Two ordering details around a rebalance.** The auto-commit a revocation triggers is now always sent before `consumer.rebalancing` is emitted, where the order used to depend on which path noticed the rebalance. And a rejoin caused by a stale assignment — a fetch that finds the member no longer owns what it is fetching — now emits `consumer.rebalancing` and auto-commits like every other revocation; in 2.2.4 it rejoined silently and committed nothing.

#### Fixes

- A subscription that declares `version: 1` or higher now writes the fields that version defines. The shipped codec wrote the same three fields for every declared version, so a `version: 1` subscription carried a v0 body under a v1 header — readable by another kafkajs member, and unreadable by any client that decodes `ConsumerProtocolSubscription` at the declared version, which is what the Java client does. A custom assigner that declares `version: 1` now emits four more bytes (an empty `OwnedPartitions`); one that declares `version: 0` — including the built-in round-robin assigner and therefore the default configuration — is byte-identical.
- Stopping the consumer's fetch layer now actually stops it. The fetch manager rebuilds its fetchers in place whenever the broker set changes, and a stop that arrived during that rebuild awaited a set that had already been replaced — so the manager kept fetching and the call that was waiting for it never returned. A stop now latches, and the internal rebuild path is unaffected: an ordinary broker-pool change still re-creates the fetchers and keeps fetching.
- A consumer that learned of the same rebalance twice — once from a fetch error, once from a heartbeat — no longer rejoins twice or emits two `consumer.rebalancing` events for it.
- A stale assignment detected inside a fetch no longer rejoins from within the fetcher's own call stack. The rejoin is requested and the fetch returns, so the fetch loop is not blocked for the duration of a join.
- A stale assignment detected during a fetch now produces one warning and one rejoin request per pending period, instead of one per fetch round per broker.
- Two consumers built from the same `Kafka` client no longer clear each other's cached committed offsets. That cache is one object per client per group, and building a consumer's offset state emptied it wholesale, so the second consumer of a group lost the first one's entries. Under cooperative rebalancing, where a joining member's first assignment is deliberately empty, this crashed the other member with a non-retriable `TypeError` and silently dropped it out of the group. Each consumer now only ever touches the partitions it holds.
- A cooperative rebalance no longer reports the partitions it kept as lost. During a cooperative round the consumer keeps fetching and committing, so a heartbeat or an offset commit sent before the round could be answered `ILLEGAL_GENERATION` after it — which was read as lost membership, discarded uncommitted offsets, stopped the fetch loop and forced another rebalance, roughly one extra round per join. Such an answer is now matched against the generation the request was sent under and ignored when it is about a generation the consumer has already left, as the Java client does.
- A consumer evicted for overrunning `maxPollInterval` no longer commits offsets for the membership it has just left. The overrunning handler keeps running after the eviction, and when it returned the consumer auto-committed and heartbeated for it — requests the coordinator rejected, whose failure then triggered a second commit. The batch that handler was working on is now dropped as documented: its offsets are neither committed nor heartbeated for on that path, and its records are redelivered after the rejoin.
- A consumer no longer hangs at 100 % CPU when `disconnect()` or `stop()` lands during a cooperative rebalance. Shutdown waited for the in-flight rebalance round before stopping the fetch layer, and in that window the fetch loop spun without ever yielding, so the round it was waiting for could never finish on the wire. The fetch layer is now stopped first, and a fetch round that comes back empty always yields to the event loop before the next one.
- An eager rebalance now reports the whole assignment on both partition events, as documented, instead of the difference between the old one and the new. A member that kept its partitions across an eager round used to be told nothing at all — no `consumer.partitions_revoked`, no `consumer.partitions_assigned` — while the round had in fact rebuilt its offset state underneath, so a listener that reopens per-partition resources on those events silently kept stale ones. An eager member's JoinGroup also advertises no owned partitions now, which is what it means to have given them up.
- A rebalance whose partitions were lost rather than given up no longer reports them twice. Such a round emitted `consumer.partitions_lost` with everything the member held and then `consumer.partitions_revoked` with part of it again, and could end without emitting `consumer.partitions_assigned` at all. It now emits the loss and then the whole new assignment, and no revocation.
- A rebalance that takes most of the rebalance timeout no longer evicts the healthy member running it. The poll-interval deadline and the rebalance timeout are the same number, and the time spent blocked in a member's own JoinGroup was charged to its handler — so a slow group rebalance made every member exceed its poll interval seconds after the join answered, sending LeaveGroup in the middle of its own round and emitting a spurious `consumer.poll_interval_exceeded` and `consumer.partitions_lost` pair. Worse, each eviction lengthened the next round, so it fed on itself. The deadline is no longer evaluated while a rebalance round is in flight; a genuinely overrunning handler is still evicted once the round completes.
- `cooperative-sticky` no longer hands a contested partition to a second consumer. When two members claimed the same partition in the same generation — one of them working from a membership it had already lost — the assignment gave it to one of them immediately, so it could be fetched while the other member was still delivering it. It is now withheld from both for one round and handed over in the follow-up, which is what the Java assignor does.

#### Additions

- New consumer option `maxPollInterval` (default 300000 ms), the Java client's `max.poll.interval.ms`: the rebalance timeout sent on the wire and the deadline a handler has to return within.
- Membership (the group coordinator handle, JoinGroup/SyncGroup/Heartbeat/LeaveGroup, the member id and generation, and assignor selection) moved out of the consumer group into a dedicated classic-protocol object, leaving the fetch loop, offsets, seek and pause where they were. No behavior, no wire bytes and no public API changed — the four group requests are byte-identical to the recorded golden frames.
- `AssignerProtocol.MemberMetadata` now speaks `ConsumerProtocolSubscription` v0 through v3: a custom assigner can send `ownedPartitions` (v1), `generationId` (v2) and `rackId` (v3) alongside the topics it already sent. The wire format is positional, so **the `version` you declare now decides which of those fields are written**, with an omitted value taking its Kafka default (`[]`, `-1`, `null`); previously every version wrote the same three fields. A `version: 0` assigner — including the built-in round-robin one, and therefore the default configuration — emits exactly the bytes it emitted before. A `version: 1` or higher assigner emits the layout it declares, which is what makes it readable by a Java client; if you declared a version whose fields you never sent, either drop to `version: 0` or start sending them. Decoding is unchanged for existing buffers: a `version: 1` subscription written by kafkajs 2.2.4 still reads back as its three fields. `userData` is unchanged in every case — `undefined` or omitted writes an empty byte string and a strict `null` writes the wire null sentinel, exactly as before; both are now pinned by tests.
- The consumer's rebalance-error classification moved into one module with one truth table, derived from the existing error predicates rather than a second list of codes. No error code changed meaning, no error class was added, and the deliberate deviation from the Java client for `NOT_COORDINATOR_FOR_GROUP` (16) — which this client treats as a revocation rather than only re-discovering the coordinator — is unchanged.
- A partition assigner may now declare `supportedProtocols()` (`['eager']` when absent) and `onAssignment(assignment, metadata)`. The rebalance protocol is chosen once at consumer construction as the highest protocol every configured assigner supports, and logged at INFO; configuring assigners that share none is a construction-time error. `protocol()` now receives `ownedPartitions`, `generationId` and `rackId` beside `topics` — an assigner that reads only `topics` emits exactly the bytes it emitted before.
- Under cooperative rebalancing the consumer now applies a rebalance incrementally: a partition it keeps across the round keeps its position, its committed offset, its tracked leader epoch, its pending seek and its paused state, and only the partitions it lost are pruned. A group leader running a cooperative round with an assignor other than `cooperative-sticky` now fails the round with a non-retriable error rather than handing a partition to a member while another still owns it.
- TypeScript definitions for everything this release added: `maxPollInterval` and the deprecated `rebalanceTimeout` on `ConsumerConfig`, the four new events with typed `consumer.on()` payloads, `reason` on `ConsumerRebalancingEvent`, `rebalanceProtocol` on `ConsumerGroupJoinEvent`, `groupInstanceId` on `GroupMember`, the three new `PartitionAssigners` keys, and the optional `supportedProtocols`/`subscriptionUserData`/`onAssignment` members and widened `protocol()` argument on `Assigner`. Every addition is optional, so an assigner or listener written against 2.2.4 still type-checks unchanged.
- Ideas from upstream PR #1778 (a background heartbeat thread for kafkajs) informed this release's heartbeat timer; the implementation here is independent.

#### Tooling

- New development-only benchmark `scripts/benchmarks/rebalanceLatency.js`, measuring the time from a member joining a group to the next batch delivered on a partition the existing member keeps across the round. Its eager baseline, measured on the previous release, is committed at `scripts/benchmarks/baselines/rebalanceLatency.json` so later runs are comparable. Not part of `npm test`.
- The four classic group requests (JoinGroup v5, SyncGroup v3, Heartbeat v3, LeaveGroup v3) now have committed golden request frames, recorded through a real broker over a fake socket with a pinned ApiVersions table, so a refactor of the membership path is proved byte-for-byte rather than argued.

The vectors pin each assignment's contents, not every tie-break: on a shape where more than one balanced assignment is correct — an over-quota incumbent tie-break during a scale-up — Kafka and this client can pick different, equally valid ones, because Kafka visits members in hash order and this client in a deterministic member order. One vector records both outputs so the difference stays visible; the practical effect is that a leader change between a Java member and a member of this client may move one more partition than Java alone would. Coverage did not drop; the population changed.

### Phase 6B — KIP-848 consumer protocol, admin group visibility, fetch prefetch

#### Behavior changes

- **A classic consumer whose group is deleted rejoins instead of crashing, and the broker's code for it changed.** `OffsetCommit` is negotiated up to v9 against a Kafka 4.x broker, and from v9 Apache Kafka's `OffsetMetadataManager.validateOffsetCommit` answers `GROUP_ID_NOT_FOUND` (69) where v8 answered `ILLEGAL_GENERATION` (22) for a commit from a member whose group no longer exists — after `admin.deleteGroups`, or after `offsets.retention.minutes` expiry. This client maps a 69 **on the commit path** to exactly the verdict 22 has always taken: discard the uncommitted offsets, rejoin, keep running. Nothing else about 69 changes — it is still a non-retriable "no such group" for `admin.fetchOffsets`, and still the routing signal that sends a describe to the classic API. Code that matches the error code in a `CRASH` handler or a log filter should expect 69 rather than 22 for this case.

- **`consumer.describeGroup()` returns the unified description.** It is routed through the same describer `admin.describeGroups` uses, so a `groupProtocol: 'consumer'` group describes itself correctly instead of coming back as a fabricated `Dead` row with `errorCode: 69`. Every field 2.2.4 returned keeps its name and meaning; the row also carries `errorMessage`, `groupType`, `groupEpoch`, `assignmentEpoch` and `assignorName`, and each member carries `groupInstanceId`, `rackId`, `memberEpoch`, `assignment`, `targetAssignment`, `memberType`, `subscribedTopics` and `subscribedTopicRegex`. One value changed: `authorizedOperations` is `null` rather than the raw `-2147483648` sentinel when authorized operations were not requested, which is what `admin.describeGroups` has always reported and what the `GroupDescription` type declares. A deep-equality assertion against a whole row needs updating; reading individual fields does not.

- **`admin.listGroups()` rejects with the retrier's error class.** Every per-broker call runs inside the configured retrier, so a caller catches `KafkaJSNonRetriableError` — or `KafkaJSNumberOfRetriesExceeded` once the budget is spent — with the broker's error on `cause`, where 2.2.4 surfaced the raw `KafkaJSProtocolError`. `.type` and `.code` survive; `e.name === 'KafkaJSProtocolError'` no longer matches. A filter the broker's version cannot serve is the one exception: it bails out of the retrier with the `KafkaJSServerDoesNotSupportApiKey` instance itself, so its `apiKey` and `apiName` reach the caller.

- **`admin.listGroups()` rows always carry `groupState` and `groupType`.** Against a broker whose `ListGroups` version has neither field (v0–v2) both are decoded as `''` rather than being absent, so one row shape reads at every version. A deep-equality assertion against a pre-v3 row needs the two keys.

- **A cooperative rebalance now commits the partitions it gives up, before it gives them up.** With `autoCommit: true` and a cooperative assigner (`CooperativeStickyAssigner`, or any assigner selecting the cooperative protocol), a round that revokes partitions now commits whatever your handler resolved on those partitions before they are pruned, using the generation the round just established. Previously those offsets were dropped, so a partition moving between members redelivered everything since the last periodic commit. The commit is best-effort: any failure — including a lost membership — is logged at warn and the rebalance proceeds, exactly as the Java client does. With `autoCommit: false` nothing changes: your `eachBatch` commits stay yours. Eager rounds are unaffected — they already committed everything before joining.

- **Under `groupProtocol: 'consumer'` a stale member epoch is handled per commit.** When the coordinator answers an `OffsetCommit` with `STALE_MEMBER_EPOCH` (113), an interval or threshold auto-commit — and `commitOffsetsIfNecessary()` called without arguments, which is the same primitive — is logged at error and skipped, and the next interval commit goes out under the epoch the heartbeats have installed; `consumer.commitOffsets(offsets)` and `commitOffsetsIfNecessary(offsets)` with your own payload reject with a non-retriable error whose message begins `OffsetCommit failed with stale member epoch.` and whose `type` is `STALE_MEMBER_EPOCH`. An `OffsetFetch` rejected the same way is re-sent under whatever epoch the heartbeats have installed by then, for up to the rebalance timeout, and is abandoned as soon as the consumer is asked to stop. Classic consumers still see `ILLEGAL_GENERATION` for a stale generation.

- **A static member under `groupProtocol: 'consumer'` sends a leave on close and on poll expiry.** A static classic member (`groupInstanceId` set) sends nothing when it stops. A static consumer-protocol member sends one heartbeat carrying member epoch −2, so the coordinator learns about the departure at once while keeping the assignment reserved for that `groupInstanceId`; because the member still holds a live epoch, closing it emits `PARTITIONS_REVOKED` and, with `autoCommit: true`, commits the offsets its handlers resolved first — where a static classic member emits neither.

- **Under `groupProtocol: 'consumer'` a topic you are not authorized to read is logged, not raised.** When the coordinator answers `TOPIC_AUTHORIZATION_FAILED` for part of the subscription the member stays in the group, keeps serving the partitions it can, and reports the failure as an error-level log line once per distinct message. The Java client raises it to the application; this client does not.

- **Poll-overrun detection is less immediate under `groupProtocol: 'consumer'`.** The deadline is still `maxPollInterval` and an overrun still costs the member its partitions, but the expiry is noticed on a heartbeat tick and never while a reconciliation is in flight, so detection can lag the deadline by up to one server-driven heartbeat interval rather than the `heartbeatInterval` you configured.

- **A broker-regex subscription's resolved names follow its applied target.** Under `subscribe({ regex })` a name the coordinator no longer assigns is retired after the target applies, unless a literal retains it. It no longer accumulates for the life of the membership. Final handlers, eligible commits and revoke work still see the old applied state.

- **`admin.describeGroups` and `consumer.describeGroup()` now negotiate `DescribeGroups` up to v6, and a group that does not exist is reported differently.** Against a 4.x broker the request used to be capped at v2, where a missing group came back as a row in state `Dead` with `errorCode: 0`. At v6 the broker answers `GROUP_ID_NOT_FOUND` (69) with a message. The row keeps the shape it has always had — `state: 'Dead'`, `members: []`, `protocol: ''`, `protocolType: ''` — and now also carries `errorCode: 69` and the broker's `errorMessage`: the call still resolves, is not retried (69 is not a retriable error), and still returns one row per requested group id. Code that tested `state === 'Dead'` keeps working; code that treats `errorCode: 0` as "the group exists", or that compares a whole row for deep equality, needs updating. Every other group-level error still fails the call and is still retried exactly as before. Rows also gain `errorMessage` and `authorizedOperations`, and members gain `groupInstanceId` (static membership).

- `admin.describeGroups()` still sends one request per coordinator, and an error the newer API reports for a single group no longer fails that whole request: it is carried on that group's row as `errorCode`/`errorMessage` while the other groups come back normally. Missing-group and unsupported-version answers from the newer API are routing signals and are never raised. A coordinator that is loading or has moved is retried on the configured retry budget as before, and a transport or coordinator error that outlives the budget still fails the call. Results are not returned in the order you passed the ids in — they were not before either, and it is now stated.

- A crash caused by a membership error the group protocol will answer identically forever — an unsupported server assignor, an invalid subscription regex, an unreleased static instance id, a group at its configured size limit, a revoked group ACL (`GROUP_AUTHORIZATION_FAILED`, 30), a request the coordinator called malformed (`INVALID_REQUEST`, 42), or a cluster that does not implement the consumer protocol — now emits `CRASH` with `restart: false` and does not restart, overriding `retry.restartOnFailure`. This matches the existing rule for a fenced static member (`FENCED_INSTANCE_ID`, 82). Only consumers using `groupProtocol: 'consumer'` reach this: a classic consumer keeps restarting on 30 and 42 as it always has.

#### Fixes

- Under `groupProtocol: 'consumer'`, `consumer.stop()`/`disconnect()` no longer leaves a heartbeat chain armed. A reconciliation still settling when the runner stops could ask the heartbeat timer for an immediate tick — through an acknowledgement, a first-membership arm or a coordinator move — and that request re-armed a chain `stop()` had just cancelled, so real heartbeats kept racing the member's own leave and a non-`unref`'d timer held the Node process open after `disconnect()` resolved. The timer now distinguishes a cancellation the poll-interval guard makes, which the recovery round is meant to re-arm, from the terminal shutdown the runner makes, which nothing may re-arm.

- Under `groupProtocol: 'consumer'`, an `OffsetFetch` answered `STALE_MEMBER_EPOCH` (113) is now genuinely re-sent under a fresh epoch. The retry re-read the offset manager's own construction-time epoch on every attempt, so every re-send carried the rejected epoch and drew the same answer — up to 3000 guaranteed-to-fail round trips over the five-minute default rebalance timeout, inside the fetch loop, with no stop check, so `disconnect()` waited it out. The manager now reads the membership live before each attempt and abandons the loop the moment a stop is requested.

- `groupRemoteAssignor: null` — the value the types and the documentation both call the default — no longer throws at construction. `null` and `undefined` read as "not set" under both protocols, so writing the documented default, or threading an optional configuration value that is `null` when absent, constructs a consumer. A non-null value still has to be a non-empty string, and is still rejected under `groupProtocol: 'classic'`.

- `admin.describeGroups(['a', 'b'])` recovers when a `__consumer_offsets` leader move splits two group ids across different coordinators. The moved-coordinator retry re-resolved the first id only and re-sent the whole batch there, so the ids that had moved elsewhere burned the retry budget and failed the call. The batch is now regrouped by coordinator on each such retry, and each sub-batch retries on its own.

- An errored `ConsumerGroupDescribe` row is no longer shaped as a described *consumer* group. A group the caller lacks a Describe ACL for came back with `groupType: 'consumer'` and `protocolType: 'consumer'` whatever its real type, so a dashboard reading `groupType` reported a classic group as KIP-848. When `errorCode` is non-zero both fields are now reported as unknown (`''`).

- `consumer.stop()` is no longer delayed by up to five seconds by the consumer-protocol reconciliation yield. The pause between reconciliation rounds checked for a requested stop before arming its timer but not after, so a stop landing one tick later waited the whole yield inside the chain `stop()` awaits. The yield is now raced against the stop signal.

- A fatal membership error learned while a consumer-protocol member is `FENCED` or `STALE` now ends the membership instead of being recorded and dropped. The error was stored but the member stayed out of `FATAL`, so the next round rejoined straight back into it and the stale error outlived a successful rejoin. `FENCED` and `STALE` are legal predecessors of `FATAL` in this client's state table — one documented widening of Java's, because this client can also learn a fatal error on the commit or fetch path, where Java only ever learns one from a heartbeat response.

- Metadata is no longer requested by topic id at versions the server does not read it at. `MetadataRequest.json` states that versions 10 and 11 must not use `TopicId` or a null topic name, and that v12 is the first version the server implements it at; the by-id codecs at v10 and v11 refuse a topic id rather than putting a uuid on the wire that the broker ignores, and `Cluster#refreshMetadataForTopicIds` falls back to a full refresh by name below v12 instead of below v10. Unreachable against a 4.x broker, whose Metadata maximum is 13.

- `ConsumerGroupHeartbeat` can no longer serialize its non-nullable `TopicPartitions.Partitions` as the null compact array, which Kafka's generated reader rejects with "non-nullable field Partitions was serialized as null" — failing the whole heartbeat rather than one topic. A missing partition list is written as the empty compact array.

- `requests.ConsumerGroupHeartbeat.protocol({ version })()` and `requests.ConsumerGroupDescribe.protocol({ version })()` build a shape-only request instead of throwing, matching `ListGroups` and the JSDoc that says the default exists so the protocol map can read an api key, name and version without building a real request.

- The withdrawn one-deep fetch prefetch left unreachable machinery behind it: a per-request fetch override the fetch layer never passed, a `prefetched` stamp on every batch that could never be true, and the two runner predicates that read them. All of it is removed, along with the JSDoc that described it as shipped. `maxPrefetchBatches` is still accepted, still validated, and still inert.

- `subscribe()`'s three shapes are now mutually exclusive in TypeScript: `{ regex, topics }`, `{ regex, topic }` and `{ topic, topics }` are compile errors, matching a runtime that has always thrown for them.

- Under `groupProtocol: 'consumer'`, a member now asks the cluster for the metadata of a newly assigned topic it has never seen **at once**, instead of waiting up to `metadataMaxAge` (5 minutes by default) to discover its name. A topic that starts matching a broker-evaluated `subscribe({ regex })` after `run()` — or any topic the coordinator assigns by id that the client has not resolved — was silently excluded from the assignment until the next metadata refresh came due, so it was never consumed at the default `metadataMaxAge`. The by-id refresh is still bounded: it is asked for only when the coordinator has just named an id the client cannot resolve and no reconciliation step is already about to resolve it, an id the cluster twice fails to name stops being asked for, and every other retry stays spaced by `metadataMaxAge`. Found by the live regex scenario.

#### Additions

- New consumer options: `groupProtocol: 'classic' | 'consumer'` (default `'classic'`), `groupRemoteAssignor` (consumer protocol only — the server-side assignor to ask for; `null` lets the coordinator choose), and `maxPrefetchBatches` (`0` or `1`, default `0`). Options the broker owns under the consumer protocol — `partitionAssigners`, `heartbeatInterval`, `sessionTimeout` — are rejected at construction rather than silently ignored, and so is `groupRemoteAssignor` under the classic protocol. `rebalanceTimeout` and `maxPollInterval` keep their meaning under both. `maxPrefetchBatches` above 1 is rejected rather than clamped, so a deeper prefetch can be added later without changing what an accepted configuration does.

- `consumer.subscribe({ regex, fromBeginning })` subscribes to a broker-evaluated RE2 pattern (consumer protocol only). The pattern is sent to the coordinator verbatim and matched there, so topics created later join the subscription without the client polling metadata. A JavaScript `RegExp` in `topics` keeps its 2.2.4 behaviour under both protocols: it is matched client-side once, at `subscribe()` time. A consumer subscribes to names or to a regex, never both.

- The heartbeat timer can now be asked for an immediate tick (`requestTick()`), and reads its delay from the group membership on every schedule instead of once at construction. With the classic protocol the membership's answer is the configured `heartbeatInterval`, so the cadence and the wire are unchanged; with the consumer protocol it is the `HeartbeatIntervalMs` the coordinator returned on the last heartbeat.

- The rebalance error contract now takes the membership protocol it is classifying for. Under the classic protocol every answer is unchanged except that `FENCED_MEMBER_EPOCH` (110), which a classic member never receives, now counts as a lost membership; under the consumer protocol a loading coordinator is not a rebalance, a coordinator that moved is re-found rather than rejoined, a fenced member reports `fenced` rather than `lost`, and the errors a member can never rejoin after are classified as fatal. `FENCED_MEMBER_EPOCH` is recognised as a lost membership, and a new internal predicate names the membership errors that override `retry.restartOnFailure`.

- Added the member state machine and the member-id generator the new consumer group protocol is built on: the ten states and their legal predecessors are the Java client's table, an illegal transition raises an invariant violation rather than being silently allowed, and a member id is 16 random bytes rendered as 22 unpadded base64url characters, re-drawn on the reserved uuid values.

- Added the heartbeat send-if-changed state for the new consumer group protocol: a joining heartbeat carries the full subscription, rack, rebalance timeout, assignor and owned partitions, and every later heartbeat carries only what changed. A partition set re-acked under a bumped local assignment epoch is re-sent, a regex subscription always sends an empty topic-name list rather than a null one, and a cleared regex is sent as an empty string.

- Metadata requests can now identify a topic by its id instead of its name, from Metadata v10 upward, and the cluster can refresh metadata for a set of topic ids. This is what lets a topic that arrives in a broker-computed assignment as a uuid be resolved to a name and consumed. Asking by name is byte-for-byte unchanged; a request that identifies every topic by id never asks the broker to auto-create anything, because a topic with no name cannot be created. A by-id refresh feeds a narrow metadata-cache entry point that records only the topics it names, so it cannot disturb the leader-hint write-through of any other topic; and because a Metadata response fails on its first errored topic, a batch holding one id the cluster will never resolve is re-asked one id at a time, so a single dead id cannot block the rest.

- The client speaks `ConsumerGroupHeartbeat` (API key 68), the single request the KIP-848 consumer group protocol is built on, at versions 0 and 1 — v1 being the one that carries a broker-evaluated subscription regex. API key 69 (`ConsumerGroupDescribe`) is declared alongside it. Nothing uses either yet; the consumer still speaks the classic protocol.

- `ConsumerGroupDescribe` (API key 69) v0–v1 is implemented, so a KIP-848 consumer group can be described with its real state, epochs, assignor and members — including each member's current and target assignment and, at v1, whether it upgraded from the classic protocol. Group-level errors are reported per group rather than failing the call, because `GROUP_ID_NOT_FOUND` on this API means "that is a classic group" rather than "no such group". The admin client starts using it later in this release.

- `ListGroups` (API key 16) v3–v5 are implemented, so a 4.x broker answers with each group's state (v4, KIP-518) and type (v5, KIP-848) instead of only its id and protocol type, and a caller can ask for one state or one type rather than filtering client-side. Rows report the empty string for a field the negotiated version does not carry, so one row shape reads at every version. The admin surface for the filters and the two new fields lands with the rest of the group-visibility work later in this release.

- `DescribeGroups` (API key 15) v3–v6 are implemented: v3 can request a group's authorized operations, v4 reports each member's `groupInstanceId` (static membership), v5 is the flexible framing, and v6 carries an error message per group. v6 also makes a KIP-848 consumer group recognisable — below v6 a broker reported one as `Dead`, from v6 it answers `GROUP_ID_NOT_FOUND` for a group of another type — which is what lets the admin client fall back to `ConsumerGroupDescribe` for it.

- `consumer.rebalancing` and `consumer.group_join` now carry `membershipProtocol: 'classic' | 'consumer'`, saying which group protocol produced the round. `groupProtocol` on `group_join` keeps its existing meaning — the selected assignor protocol name. `consumer.rebalancing`'s `reason` gains `'assignment-changed'` and `'fenced'`.

- Added the KIP-848 consumer group membership behind the existing rebalance seam: a member generates its own id, heartbeats on the interval the coordinator asks for, reconciles towards the target assignment one step at a time and acknowledges each step by sending back the partitions it owns. Fencing, a fatal membership error and a poll-interval overrun each move the member through the Java client's state machine, and a leave sends its own heartbeat with the leave epoch (−1 dynamic, −2 static) rather than going through the heartbeat timer. Nothing constructs it yet.

- Both membership implementations now answer `kind`, `heartbeatInterval()`, `needsReconciliation()`, `onMembershipError()`, `onStopRequested()` and `leaveForPollExpiry()`, so no caller has to branch on which protocol is in use. The classic implementation's behaviour is unchanged.

- `OffsetCommit` v9 and `OffsetFetch` v9 are implemented. Both are the versions the KIP-848 consumer protocol needs: at OffsetCommit v9 the generation field carries a member epoch that the coordinator validates, and OffsetFetch v9 sends the member id and epoch alongside the group. OffsetCommit v9's request bytes are identical to v8's, and OffsetFetch v9 sends the "no membership" defaults (`null` and `-1`) that mean what v8 meant by not having the fields at all. The v9 bytes are the same, but the broker's answer for one case is not: see the `GROUP_ID_NOT_FOUND` behaviour change above.

- `admin.listGroups()` now reports `groupState` and `groupType` on every row and accepts `admin.listGroups({ states, types })` to filter server-side — for example `{ types: ['consumer'] }` for KIP-848 groups only. Filters are lower-case; the client maps them to the wire names. Against a broker too old for a filter the call follows the Java client's rules: asking for states needs ListGroups v4 and fails otherwise, and asking for types needs v5 except where the request can be answered correctly by ignoring the filter; a filter a broker's version cannot serve fails on the first attempt. A broker that answers that its coordinator is loading or not yet available is asked again on the configured retry budget. The fan-out is still all-or-nothing across brokers, as it has always been.

- `admin.describeGroups()` now describes both classic and KIP-848 consumer groups. Each group id is described through ConsumerGroupDescribe where the broker offers it and through DescribeGroups otherwise, in one result shape that keeps every field the call returned before — `errorCode` included — and adds `groupType`, `groupEpoch`, `assignmentEpoch`, `assignorName`, `authorizedOperations`, `errorMessage`, and per member `groupInstanceId`, `rackId`, `memberEpoch`, `assignment`, `targetAssignment`, `memberType`, `subscribedTopics` and `subscribedTopicRegex`. A consumer-group member's `memberAssignment` buffer is produced by this client from the assignment the broker sent, so tooling that decodes it keeps working.

- The consumer runner drives the KIP-848 membership: a shutdown cancels a join that is still waiting on the coordinator instead of hanging on it, a lost membership learned on the commit or fetch path is routed into the membership state machine so the recovery round rejoins, a fatal membership error (unsupported assignor, invalid subscription regex, duplicate instance id, group at capacity) is never retried, and the background heartbeat follows the interval the coordinator asked for. It also accepts `maxPrefetchBatches`, which is stored and inert.

- Offset commits and fetches follow the group protocol: under `groupProtocol: 'consumer'` the commit carries the member epoch (OffsetCommit v9's `GenerationIdOrMemberEpoch`) and the fetch carries `MemberId`/`MemberEpoch` (OffsetFetch v9). Classic consumers and the admin client send neither and are byte-compatible with 2.2.4. A `STALE_MEMBER_EPOCH` (113) answer is handled per call site, as the Java client does: an interval auto-commit is logged and skipped (the next one carries the fresh epoch), the commit a rebalance issues before releasing partitions is re-sent under the new epoch within the rebalance timeout, and a deliberate `commitOffsets()` fails with the protocol error. 113 remains non-retriable, matching `Errors.java`.

- The consumer group is built from a `groupProtocol` option: `'classic'` (the default, unchanged) or `'consumer'` (KIP-848). Under `'consumer'` it also accepts `groupRemoteAssignor` and a regex subscription, and forwards the membership's kind, epoch and heartbeat interval to the components that need them.

- The consumer option `maxPrefetchBatches` is accepted with a value of `0` or `1` and is inert in this release: it changes nothing at either value. The one-deep fetch prefetch it was to control measured **+2.45 %** throughput against the **≥ +10 %** acceptance the design set for it, and was withdrawn on that number. The option stays accepted, and rejects anything but `0` or `1`, so a later release can turn the prefetch on without asking you to change your configuration.

- Types and documentation for the consumer group protocols: `groupProtocol`, `groupRemoteAssignor` and `maxPrefetchBatches` on `ConsumerConfig`, the `{ regex }` subscribe form, `ListGroupsOptions`, the new `GroupOverview`/`GroupDescription`/`MemberDescription` fields (`errorCode` now declared as well as returned), `'Assigning'`, `'Reconciling'` and `'NotReady'` on `ConsumerGroupState`, and `membershipProtocol` on the group-join and rebalancing event payloads. `ConsumerGroupJoinEvent.leaderId` widens to `string | null`, because a KIP-848 group has no leader; that widening is source-breaking under `strictNullChecks` and is one of four TypeScript changes the migration guide now lists. A new "Consumer group protocols" section in `docs/Consuming.md` covers both protocols, the configuration rejections, regex subscriptions, fencing semantics and the current limitations, and a "Prefetching" section covers `maxPrefetchBatches`.

### Phase 7 — Transactions TV2, the KIP-1050 taxonomy and producer performance

#### Behavior changes

- **Producers are idempotent by default** (KIP-679). `kafka.producer()` creates an idempotent producer unless `idempotent: false` is passed: it allocates a producer id at `connect()` (`InitProducerId`), numbers its batches so a retried request cannot write a record twice or out of order, and needs `acks: -1` — the default — on every send. The retry budget does not change: every producer keeps its retry budget, `retry.retries` from the client or the producer (5 unless set); the `Number.MAX_SAFE_INTEGER` default the code held for `idempotent: true` was never reachable through `kafka.producer()` and is gone. `producer.isIdempotent()` now reports `false` once one of the settings below has turned idempotence off. Pass `idempotent: false` for a producer without a producer id or sequence numbers, as in 2.2.4; it shares the send path every producer has (the accumulator and per-partition retries below).

- A `send()`/`sendBatch()` asking for `acks` 0 or 1 on a producer created with `idempotent: true` still rejects with the same message, now as `KafkaJSInvalidConfigurationError`, a `KafkaJSNonRetriableError` subclass. On a producer that did not pass `idempotent` it instead logs one warning, turns idempotence off for the rest of the producer's life and sends exactly what an `idempotent: false` producer sends.

- `maxInFlightRequests` above 5, or `null`, turns idempotence off with one warning for a producer that did not pass `idempotent`, and makes `kafka.producer()` throw `KafkaJSInvalidConfigurationError` for one created with `idempotent: true`. The Java client refuses the combination whether or not idempotence was asked for; this client keeps a 2.2.4 configuration with `maxInFlightRequests: null` working and says once that it runs non-idempotent.

- **`producer.connect()` can now fail on a cluster that grants the principal neither `IDEMPOTENT_WRITE` on the cluster nor `WRITE` on any topic**, because an idempotent producer sends `InitProducerId` at `connect()`. The broker answers `CLUSTER_AUTHORIZATION_FAILED` (31), and the producer rejects — at `connect()`, or when a later `send()` tries the initialization again — with `KafkaJSInvalidConfigurationError` reading "The broker refused InitProducerId: the principal needs IDEMPOTENT_WRITE on the cluster (or WRITE on any topic, from Kafka 2.8), or create the producer with idempotent: false", `category` `'invalidConfiguration'`, the broker's `KafkaJSProtocolError` as its `cause`, where it used to reject with that protocol error itself. Grant the ACL, or create the producer with `idempotent: false`; code that matched `error.type === 'CLUSTER_AUTHORIZATION_FAILED'` reads `error.category`, or `error.cause.type`.

- `retry: { retries: 0 }` turns idempotence off with one warning for a producer that did not pass `idempotent`, keeping its fail-fast behaviour, and makes `kafka.producer()` throw `KafkaJSInvalidConfigurationError` — with the message `Idempotent producer must allow retries to protect against transient errors` it threw before as `KafkaJSNonRetriableError` — for one created with `idempotent: true`. A still-idempotent producer with `retries` between 1 and 4 logs the "limiting retries" warning, which 2.2.4 logged only for a producer created with `idempotent: true`.

- A producer created with a `transactionalId` counts as having asked for idempotence, whatever `idempotent` says: it never turns idempotence off, and `acks` 0 or 1 on any of its sends — its own or its transactions' — or `maxInFlightRequests` above 5 or `null`, or `retries: 0`, throws `KafkaJSInvalidConfigurationError`. `maxInFlightRequests: 1`, the common 2.2.4 work-around, is below the cap and unaffected.

- **Every producer gathers its sends into batches, so a `send()` may wait up to 5 ms before its request leaves.** The accumulator is on for every producer, idempotent or not, with the Java client's 4.x defaults: `linger` 5 ms (`linger.ms`, whose default moved from 0 to 5 in Kafka 4.0) and `batchSize` 16384 bytes of keys and values. Where 2.2.4 sent every `send()`/`sendBatch()` as its own request, the records of sends made within `linger` of each other to one topic-partition now share a batch, and one `send()` or `sendBatch()` usually makes one Produce request per broker: when one of its partitions fills a batch, its other partitions go in the same request, but its records that join a batch an earlier send began leave with that batch, so one call can reach a broker in two requests. `linger: 0` sends at once, with no timer, yet still merges the sends made in the same tick and, on an idempotent producer, those that queue behind a partition's batch in flight. No option restores one request per `send()`, as in the Java client.

- **Sends to one topic-partition can share a batch, and then succeed or fail together**: a batch the broker rejects rejects every send whose records it carries; each send still resolves with the `baseOffset` of its own first record. Sends to different partitions that share a request settle on their own partition's answer.

- **A record whose key, value, header values or timestamp cannot be encoded rejects its own send with `KafkaJSInvalidConfigurationError`** (`category` `'invalidConfiguration'`) before it joins a batch, instead of a `TypeError` that failed every send of its request; inside a transaction such a send leaves the transaction as it was.

- **The producer's per-broker lock is gone.** An idempotent or transactional producer no longer sends one request at a time to each broker: batches of different partitions are pipelined, at most 5 Produce requests per broker without an answer (fewer when the connection's `maxInFlightRequests` is lower), while the rest wait unnumbered; within one partition a batch is numbered as it is sent and waits for the previous batch's answer, so the order within a partition holds even when a request fails before it reaches the broker; the accumulator gathers a busy partition's sends into fewer, larger batches. A transactional producer pipelines exactly like an idempotent one, so `maxInFlightRequests: 1` on it is no longer needed and now costs throughput. `producer.events.LOCK_TIMEOUT` can no longer be emitted: the producer no longer waits on a per-broker lock, though a `send()` can still raise `KafkaJSLockTimeout` while registering its topics with the cluster, as connecting to a broker can; both stay exported. This retires Countly patch 2e (the per-broker EOS mutex and its 65.5 s `KafkaJSLockTimeout`).

- **On an idempotent producer (the default) a failed send no longer cancels the partitions still going, and `retry.retries` is counted per partition batch.** Each topic-partition of a `send()` keeps its records, its partition and its sequence across retries — the partitioner never runs twice for the same records — and is retried and fails on its own: a non-retriable error fails that partition's batch and leaves the others alone, so a rejected `send()` may have written the partitions whose batches succeeded, and a multi-partition send can take up to `retries` attempts per partition. The promise still settles once, after every batch has settled, and rejects with the first error a batch failed with; a retriable error that runs out of retries rejects with `KafkaJSNumberOfRetriesExceeded`, as before. An empty send resolves `[]` at once without fetching metadata. An `idempotent: false` producer now settles and retries each partition on its own too (below), with one `retry.retries` budget for the partitions that went out together.

- **An `idempotent: false` producer settles and retries each partition on its own**, as the Java producer does, where 2.2.4 retried a `send()` as a whole call: a failed request went out again with every partition it carried, written ones included, and an error that is not retriable bailed the call. Now a partition answered OK resolves at once and is never sent again, so a retriable error on one partition no longer writes the others twice; a partition refused with an error that is not retriable rejects alone; and only the partitions whose answer was retriable go out again, within one `retry.retries` budget shared by the partitions that went out together. A topic or broker that cannot be looked up holds back only its own partitions, and each attempt waits for every broker's answer, so the slowest broker paces the retries, by at most `requestTimeout` per attempt. Sends to different partitions that share a request no longer share each other's failure, and a rejected `send()` may have written its other partitions. Records are assigned to partitions once, before they are sent, under a retry budget of their own, so waiting for a topic's metadata no longer spends the send's retries.

- **`send()`/`sendBatch()` resolve their `RecordMetadata[]` sorted by topic name, then partition, on every producer**, where 2.2.4 grouped them by the broker that led each partition, in the order the call listed its topics, so a multi-broker send, or one listing its topics out of name order, returns the same entries in a different sequence; a single-partition send is unaffected. Every entry still carries `topicName` and `partition`; sorting changes no request.

- **`deliveryTimeout` counts from the moment a send is made**, on every producer, as in the Java client: the wait for `linger`, and on an idempotent producer the wait for the producer id, count against it, and a non-idempotent batch whose deadline passed before it could be sent rejects without being sent; its floor is `linger + requestTimeout`, 30005 ms with both defaults.

- **`producer.disconnect()` delivers before it disconnects**: it sends every waiting batch, its own and its transaction's, and waits for every send begun before it - retries included, up to `deliveryTimeout` or the retry budget - refusing new sends meanwhile, where 2.2.4 disconnected at once and failed the sends still under way.

- **Transactions use the transaction protocol version 2 on Kafka 4.x clusters** (KIP-890). The producer reads the cluster's `transaction.version` feature from the transaction coordinator at the start of every transaction. Under version 2 a produce and a transactional offset commit add their partition and offsets to the transaction themselves (Produce v12, `TxnOffsetCommit` v5), so `AddPartitionsToTxn` and `AddOffsetsToTxn` are no longer sent, and every commit and abort (`EndTxn` v5) moves the producer to a new epoch, which it adopts before the next transaction; a partition leader that offers no Produce v12 fails the send with `KafkaJSServerDoesNotSupportApiKey` and makes the producer unusable, as the Java client treats an unsupported version; under version 1 the producer keeps the version 1 requests (`AddPartitionsToTxn` v3, Produce at most v11, `AddOffsetsToTxn` v4, `EndTxn` and `TxnOffsetCommit` at most v4). A cluster moving from version 1 to 2 costs one `InitProducerId` before the next transaction, retried by the next `producer.transaction()` if it fails. A transaction in which nothing was produced and no offsets were sent still ends without an `EndTxn`. `EndTxn` is now retried while the coordinator moves or is busy.

- `producer.transaction()` now finds the transaction coordinator before it resolves: a lookup that fails rejects `transaction()` itself and leaves the producer ready for the next call, where the failure used to surface on the transaction's first request. Each transaction sends one more FindCoordinator request, when it begins.

- **A send or `sendOffsets` that fails inside a transaction ends that transaction, as its error's category decides** (KIP-1050). An `abortable` error, a retriable one that ran out of retries — which now reaches you as a `KafkaJSTransactionAbortableError` with the `KafkaJSNumberOfRetriesExceeded` as `cause` — and every `invalidConfiguration` code except `CLUSTER_AUTHORIZATION_FAILED`, `TRANSACTIONAL_ID_AUTHORIZATION_FAILED` and `UNSUPPORTED_VERSION` make the transaction abort-only: `commit()`, `send()`, `sendBatch()` and `sendOffsets()` then reject with a `KafkaJSTransactionAbortableError` without contacting the broker, `abort()` works, and `producer.transaction()` rejects with that error until it has. An `applicationRecoverable` error and those three codes make the producer unusable: every later call rejects with a `KafkaJSApplicationRecoverableError`. A batch dropped because the producer was disconnecting or disconnected ends the transaction's chance to commit the same way; a fault in the client's own send loop makes the producer unusable; and an error the client raised itself rather than the broker — a `TypeError` while encoding an offset, say — makes the transaction abort-only as a `KafkaJSTransactionAbortableError` whose `cause` is that error, leaving the producer usable. A batch that had been sent before it gave up may have been written all the same, so its partition's sequence stays unresolved: `commit()` and `abort()` check every partition's sequence before `EndTxn`, a gap nothing else reported makes the transaction abort-only ("The client hasn't received acknowledgment for some previously sent messages and can no longer retry them. It is safe to abort the transaction and continue."), and no `EndTxn` is sent while a batch of the transaction is still in flight — which only a send-loop fault, having already made the producer unusable, can leave behind. `commit()` and `abort()` first wait for the transaction's own sends and `sendOffsets` to settle, and accept no new ones; an `abort()` called while a `commit()` is under way waits for it and ends the transaction only if the commit failed; `abort()` rejects the batches still waiting to go out, always ends the transaction — a failure inside it is logged unless it leaves the producer unusable — and bumps the producer epoch (KIP-360) under transaction version 1 after a failed send or when one of the batches it rejected had already been sent once, and under either version when its own `EndTxn` failed. A send refused before any record was queued — for its own arguments, a record that cannot be encoded, or by a custom partitioner that threw — leaves the transaction as it was.

- **`transaction.sendOffsets()` takes the consumer's group membership** (KIP-447): `sendOffsets({ consumerGroupMetadata: consumer.groupMetadata(), topics })` puts the generation, member id and group instance id on the `TxnOffsetCommit`, so the group coordinator rejects a commit from a member a rebalance replaced. `{ consumerGroupId, topics }` still works and still commits without group fencing; passing both, or neither, throws `KafkaJSNonRetriableError`. The cluster cache is still marked as soon as the offsets are sent.

- **`ILLEGAL_GENERATION`, `UNKNOWN_MEMBER_ID`, `FENCED_INSTANCE_ID` and `STALE_MEMBER_EPOCH` from a transactional offset commit make the transaction abort-only** — abort, let the consumer rejoin, reprocess — where they used to fail the call alone. `sendOffsets` rejects with a `KafkaJSTransactionAbortableError` whose `cause` is the broker's error. A classic-protocol member sees code 22 and a `groupProtocol: 'consumer'` member 113 for the same condition. On every other request these codes keep their category.

- **Every error carries a `category`, naming the remedy** (KIP-1050). Each error this client raises through a KafkaJS error class has an own, enumerable `category` — `retriable`, `refreshRetriable`, `abortable`, `applicationRecoverable` or `invalidConfiguration`: retry it, refresh metadata or the coordinator and retry it, abort the transaction and keep the producer, create a new producer, or fix the configuration, record or ACL. It is stamped on the error the client already produced and nothing is re-wrapped, so `name`, `instanceof` and every attached field (`type`, `code`, `topic`, `partition`, `recordErrors`, the leader hint) are unchanged, and `error.retriable` keeps its meaning: it is `true` exactly when the category is `retriable` or `refreshRetriable`, for every code in the protocol error table. A protocol error carries the category its code has on every request, and the transactional producer refines it for the request that failed — `INVALID_TXN_STATE` is abortable on Produce, a stale generation on a transactional offset commit means abort and rejoin. An error built from another one keeps its category when the two agree on `retriable`, as it already kept `type` and `code`, and so does one built from a message and a `cause`. Because the field is enumerable it appears in `JSON.stringify(error)` and in structured logs, so a snapshot of a serialized error gains one key.

- **A consumer asks for stable committed offsets** (KIP-447). Every `OffsetFetch` a consumer sends to resolve its position sets `RequireStable`, under both group protocols and whatever the isolation level, as the Java consumer does: a partition whose committed offset is held by a transaction that is still open answers `UNSTABLE_OFFSET_COMMIT` instead of an offset the transaction may yet roll back, and the consumer asks again — after 100 ms, backing off to once a second — until the transaction commits or aborts, for at most its rebalance timeout (`maxPollInterval`, 300 000 ms by default). While it waits it still counts as polling, and it stops waiting within a second for a `stop()` or for a rebalance that pauses fetching. A transaction left open longer than that fails the position lookup with `UNSTABLE_OFFSET_COMMIT` (retriable), which 2.2.4 never raised here because it read the unstable offset; the consumer's retry policy then retries the lookup. `admin.fetchOffsets` still reads without it, and a broker below `OffsetFetch` v7 is not asked.

- `AddPartitionsToTxn` requests are now sent at **v3** and `AddOffsetsToTxn` at **v4** instead of v1, the versions the Java client sends while the `transaction.version` feature is below 2; v3 is the first flexible version of both, and `AddPartitionsToTxn` stops there because the protocol keeps v4 and v5 for brokers. Responses decode to the same shape as before. Two error codes change for a transactional producer: a broker now reports a fenced producer epoch on either request as `PRODUCER_FENCED` (90) where it answered `INVALID_PRODUCER_EPOCH` (47) to v1, and `AddOffsetsToTxn` may answer `TRANSACTION_ABORTABLE` (120); both are non-retriable, so the transaction fails exactly as before, with a different `type` and `code` on the error. Code that matched `INVALID_PRODUCER_EPOCH` (47) for a fenced producer should match `error.category` or both codes.

- `EndTxn` and `TxnOffsetCommit` are now sent at **v4** instead of v1, the highest versions a transaction may use while its coordinator's `transaction.version` feature is below 2; the client can also encode v5 of both, which it sends only under transaction version 2. Responses decode to the same shape as before. What a transactional producer can notice: a fenced producer epoch on `EndTxn` now arrives as `PRODUCER_FENCED` (90) where v1 got `INVALID_PRODUCER_EPOCH` (47), and either request may answer `TRANSACTION_ABORTABLE` (120) — both non-retriable, so the transaction fails as before, with a different `type` and `code` on the error; and a `leaderEpoch` given on a `sendOffsets` partition — as `consumer.uncommittedOffsets()` hands one out — is now committed with the offset (KIP-320), where v1 committed none, so a consumer that resumes from that offset can validate its position against it.

#### Fixes

- A consumer's tracked leader epoch is no longer overwritten by a late committed-offset reply. Every broker a consumer fetches from resolves the group's committed offsets for the whole assignment, so after a join several `OffsetFetch` requests can be in flight at once; one answered after the consumer had already moved — consumed a record, or applied a `seek()` — replaced that position's epoch with the committed one, which is −1 for an offset committed without an epoch. `uncommittedOffsets()` then reported `leaderEpoch: -1` for a position that had a real epoch, the next commit carried it, and position validation (KIP-320) was off for that partition until it consumed again. A committed epoch now seeds a position only while that position is still the committed offset or has not been resolved yet, and an unknown committed epoch (−1) never replaces a known one.

- Keyed partitioning no longer allocates for every four bytes of a key. `murmur2`, which `DefaultPartitioner` runs for every keyed record, emulated Java's 32-bit `int` arithmetic with a 64-bit value object per 4-byte block; it now uses plain 32-bit integer operations, which compute exactly the same hash — every key still lands on the partition the Java client picks, checked against the Java-generated fixtures and against the previous implementation over 6,564 keys.

- Two `producer.transaction()` calls made before the producer has a producer id now acquire it once: they share the first `InitProducerId`, and a retry after a coordinator error keeps the producer id the other call already received. Each call used to send its own `InitProducerId`, and the later answer could fence a transaction the first call had already begun. The call that loses that race now rejects with "There is already an ongoing transaction for this producer. Please end the transaction before beginning another.", as a later second call does, instead of a transaction-state error.

- An idempotent producer that had written 2^31 records to one partition under one producer epoch numbered the next batch from 0 instead of continuing the broker's count past `2147483647`, so that batch was refused with `OUT_OF_ORDER_SEQUENCE_NUMBER`. Sequences now wrap exactly as the broker computes them (`DefaultRecordBatch.incrementSequence`).

- A request that took longer to encode — a Produce with more partitions, say — could reach the broker after a later request on the same connection, because each request was queued only once its own encode finished. Requests now reach a broker connection in the order they were sent (the SASL exchange that authentication itself runs excepted).

- The `retry` options of the client and of the producer now bound the producer's own transaction retries, which ignored them: `InitProducerId` while the coordinator is still aborting another transaction for the same `transactionalId` (`CONCURRENT_TRANSACTIONS`), and the `EndTxn`, `AddOffsetsToTxn` and `TxnOffsetCommit` retries. They always ran the default budget (5 retries, about 9 s), so a producer that set a larger `retry.retries` still gave up on `CONCURRENT_TRANSACTIONS` after about 9 s; they now run the producer's merged `retry` options, so a smaller `retries`, a shorter `maxRetryTime` or a `maxTotalTime` now shortens them too. Unchanged on the default retry options. kafkajs 2.2.4 had the same defect.

- Closing a broker connection that the broker had already closed no longer leaves a listener behind each time. `producer.disconnect()`, `consumer.disconnect()` and the client's own reconnects call it several times per connection, and each call used to queue a `connect` listener on the dead socket, so a long-lived client printed `MaxListenersExceededWarning: Possible EventEmitter memory leak detected. 11 connect listeners added to [Socket]` and left them on the dead socket, where they never fire. kafkajs 2.2.4 had the same defect.

- `producer.connect()` no longer fails because a partition the producer does not use has no leader. An idempotent producer — every producer by default — and a transactional one asked for the metadata of every topic in the cluster before `InitProducerId`, and that request failed then on any leaderless partition, so one partition anywhere without a leader made `connect()` reject with `KafkaJSNumberOfRetriesExceeded` (`LEADER_NOT_AVAILABLE`). As in the Java client, a non-transactional `InitProducerId` now goes to any connected broker, and a transaction or group coordinator the client does not know yet is reached at the address `FindCoordinator` returns, with no metadata request first. A broker whose rack alone changes now keeps its connection. kafkajs 2.2.4 had the same defect for `idempotent: true`; idempotence on by default made it reach every producer.

#### Additions

- Five error classes, exported from the package root: `KafkaJSTransactionAbortableError` (`abortable`), `KafkaJSApplicationRecoverableError` (`applicationRecoverable`), `KafkaJSInvalidConfigurationError` (`invalidConfiguration`) and `KafkaJSDeliveryTimeout` (`abortable` — a send that ran out of its delivery deadline), all subclasses of `KafkaJSNonRetriableError`, and `KafkaJSRefreshRetriableError` (`refreshRetriable`), a retriable `KafkaJSError`. `KafkaJSAggregateError` and `KafkaJSFetcherRebalanceError`, which extend `Error` directly, carry `category` too; the latter keeps its `name` of `'Error'`.

- `Partitioners.UniformStickyPartitioner({ stickyBytes = 16384, ignoreKeys = false })`, the strictly uniform sticky partitioner of KIP-794, opt-in through `createPartitioner`. A record without a key goes to its topic's sticky partition until `stickyBytes` of key and value have been assigned to it, then the next one goes to a partition picked at random among those with a leader (among all of them when none has one), so the keyless records of one `send()` fill fewer, larger batches (and across `send()` calls, in the accumulator); a keyed record goes exactly where `DefaultPartitioner` puts it unless `ignoreKeys` is set. The Java client's adaptive partitioning is not implemented. `DefaultPartitioner` stays the default.

- The `Broker` object the client's types describe gains what transactions on Kafka 4.x need, and every new parameter defaults to the request it sent before, byte for byte. `broker.finalizedFeatures` (`{ [name]: { minVersionLevel, maxVersionLevel } }`) and `broker.finalizedFeaturesEpoch` keep the finalized features of the `ApiVersions` response its last connection negotiation received — `{}` and −1 when it sent none — and are refreshed with its version table at every re-negotiation. `initProducerId()` takes the `producerId` and `producerEpoch` a KIP-360 re-initialization sends (InitProducerId v3+); `offsetFetch()` takes `requireStable` (OffsetFetch v7+, KIP-447); `txnOffsetCommit()` takes the consumer's `generationId`, `memberId` and `groupInstanceId` (KIP-447); and `produce()`, `endTxn()` and `txnOffsetCommit()` take a `transactionVersion`, 1 by default or 2, that decides the versions a transactional request may use (KIP-890): under 1 a transactional Produce stays at v11 or below and EndTxn and TxnOffsetCommit at v4 or below, under 2 a transactional Produce goes at v12, never v13.

- `consumer.groupMetadata()` returns `{ groupId, generationId, memberId, groupInstanceId }`, the membership a transactional offset commit needs so the group coordinator can fence a stale or zombie member (KIP-447); it is what `transaction.sendOffsets({ consumerGroupMetadata, topics })` takes. Under `groupProtocol: 'consumer'` `generationId` is the member epoch. Before the consumer's first join it reports generation −1 and an empty member id, as the Java client does, and under the classic protocol it keeps reporting the last joined generation and member id after the membership is lost — a poll-interval overrun or an unknown member id — including across `stop()`/`run()` and a crash restart until the next join, so a commit built from a stale snapshot is rejected rather than accepted unfenced. It is a snapshot: read it again after every rebalance. Like `seek()` and `pause()`, it throws before `run()` and after `stop()`.

- The retrier behind every retried operation accepts an optional `maxTotalTime` (ms), a deadline measured from the first attempt: when the wait before the next attempt would end past it, the operation rejects with `KafkaJSDeliveryTimeout`, whose `cause` is the last attempt's error, instead of waiting; running out of `retries` first still rejects with `KafkaJSNumberOfRetriesExceeded`. It is the mechanism behind the producer's `deliveryTimeout`. Because the client's `retry` option is handed to every retrier, `retry: { maxTotalTime }` set there bounds producer sends and transaction retries, `consumer.commitOffsets()`, the consumer group's join and sync, admin calls, and the client's connect, metadata and coordinator lookups — except the consumer's fetch loop and the auto-commits inside it, which run as one operation for as long as `run()` runs and keep retrying in place, the consumer-protocol heartbeat backoff, and position validation, which has its own fixed budget; leaving it unset changes nothing. It must be an integer from 1 to 2147483647, the longest delay a Node.js timer takes: any other value (`0`, a negative or fractional number, a string, a larger number) throws `KafkaJSInvalidConfigurationError` when the retrier is built. Every retry delay is also clamped at zero, so a `factor` above 1 or a negative `multiplier` can no longer hand Node a negative timer, which Node 24 and later warn about and run after 1 ms; for the documented ranges the attempts and delays are exactly as before.

- `deliveryTimeout` (ms), a new opt-in producer option (KIP-91), bounds one `send()`/`sendBatch()`, retries included: past it the send rejects with `KafkaJSDeliveryTimeout`, whose `cause` is the last error, and running out of `retry.retries` first still rejects with `KafkaJSNumberOfRetriesExceeded`. A request already sent settles on its answer or on `requestTimeout`, so a send can end up to `requestTimeout` after the deadline; the Java client fails such a batch at the deadline. It has no default; `kafka.producer()` refuses a value that is not an integer from `linger + requestTimeout` to 2147483647, the longest delay a Node.js timer takes. Without it, a `retry.maxTotalTime` set on the client still bounds the producer's sends.

- `transaction.sendOffsets()` accepts `consumerGroupMetadata` — the object `consumer.groupMetadata()` returns — in place of `consumerGroupId`, and each offset entry may carry the `leaderEpoch` of the consumed record, which `consumer.uncommittedOffsets()` already reports; `docs/Transactions.md` describes both, the two transaction versions, the error categories with what to do about each, and the transaction timeout.

- The accumulator, as in the Java client, on for every producer: `linger` (ms, default 5) and `batchSize` (bytes, default 16384) on `kafka.producer()` gather the records of several `send()`/`sendBatch()` calls to one topic-partition into one batch, in the order their records reach the accumulator, normally the order the sends were made. A batch goes out `linger` ms after its first records - at once, with no timer, at `linger: 0` - as soon as its keys and values reach `batchSize` bytes, or before records with a different `acks`, `timeout` or `compression` start the next one; a send larger than `batchSize` goes out on its own, never split; a send that fills a batch takes its other batches along, and batches of different partitions that are due together go out together. On an idempotent producer, which keeps one batch of a partition in flight at a time, a batch keeps gathering records past its `linger` while the batch before it is in flight, so a busy partition sends batches as large as its round trip allows. `kafka.producer()` refuses a `linger` that is not an integer from 0 to 2147483647 and a `batchSize` that is not an integer of at least 1. A send resolves once the batch carrying its records is acknowledged, each `RecordMetadata`'s `baseOffset` being that of the send's own first record. A send with `acks` 0 or 1 that turns idempotence off first sends the waiting batches, still numbered under the producer id; a transaction's `commit()` sends its waiting batches at once and `abort()` drops them. It works with and without idempotence; `docs/Producing.md` describes it, and the behavior changes above list what differs from 2.2.4.

- TypeScript declarations for the additions of this release: `linger`, `batchSize` and `deliveryTimeout` on `ProducerConfig` and `maxTotalTime` on `RetryOptions`; `Partitioners.UniformStickyPartitioner(options?)`; `ConsumerGroupMetadata` and `consumer.groupMetadata()`; `TransactionOffsets`, whose partitions take an optional `leaderEpoch`, and `transaction.sendOffsets()` taking exactly one of `consumerGroupMetadata` and `consumerGroupId` - the 2.2.4 `{ consumerGroupId, topics }` still compiles; `KafkaJSErrorCategory` and the `category` of `KafkaJSError`, `KafkaJSAggregateError` and `KafkaJSFetcherRebalanceError`, which is now declared; the five new error classes; and on `Broker` the finalized features, `initProducerId`, `endTxn`, `txnOffsetCommit` and the new `produce` and `offsetFetch` parameters, `produce` also taking a string `producerId`. Code that builds these types by hand gains required members; the migration guide lists them.

### Phase 8 — Admin expansion, observability, the OTel fork and 3.0.0 gate preparation

#### Behavior changes

- A consumer with `groupProtocol: 'consumer'` commits and fetches offsets by topic id on Kafka 4.2 and later (`OffsetCommit` and `OffsetFetch` v10, topic ids, KIP-848), when it knows the id of every topic in the request; a request for any topic whose id is unknown, every classic consumer and every admin offset call keep sending topic names, and Kafka 4.0 and 4.1 do not advertise v10. `UNKNOWN_TOPIC_ID`, which a deleted and recreated topic answers, is retried after a metadata refresh. `Broker#offsetCommit` and `Broker#offsetFetch` accept an optional `topicId` on each topic entry. The `COMMIT_OFFSETS` payload is unchanged.

- `JoinGroup` v7 and `SyncGroup` v5 now check the protocol the coordinator reports: the consumer sends its protocol type (`consumer`) on `JoinGroup` and, on `SyncGroup`, the protocol type and name the join answer reported, and an answer that names another protocol type or name fails the rebalance with `INCONSISTENT_GROUP_PROTOCOL` (23, not retriable), as the Java client does; a missing value is not a mismatch, and a correct broker never answers one. Every classic consumer now sends `SyncGroup` at v5 against a 4.x broker.

- When one producer batch's `linger` timer fires, the other waiting batches for the same broker that ask for the same `acks`, `timeout` and `compression` now leave with it, possibly before their own `linger`: six sends a millisecond apart to partitions of three brokers used to make six Produce requests and now make three. Only a firing `linger` timer pulls batches that are not yet due; a full batch and `linger: 0` do not, and a flush hands every batch on. The Java client readies a broker on more triggers (a full batch, a flush, a transaction that is completing) and stops a request at `max.request.size` (1 MB by default); this client has no such cap, so one request can carry every batch its broker has waiting. A batch held behind its partition's batch in flight stays held, and a partition whose leader is not known is never merged. Pulling a batch forward adds no batching delay, but `linger` does not bound when a `send()` settles. Without idempotence, a batch whose own `deliveryTimeout` (or `retry.maxTotalTime`) has already passed when its request is made rejects alone with `KafkaJSDeliveryTimeout`; the other batches in that request are sent.

- A producer with a `transactionalId` whose `InitProducerId` the broker refuses with `CLUSTER_AUTHORIZATION_FAILED` (code 31) is now told which ACL to grant — `IDEMPOTENT_WRITE` on the cluster, or `WRITE` on any topic from Kafka 2.8 — and no longer told to create the producer with `idempotent: false`, which a transactional producer cannot do; the message of a producer without a `transactionalId` is unchanged.

- `admin.describeCluster()`, `admin.listTopics()` and `admin.fetchTopicMetadata()` with no topics no longer fail while a partition anywhere in the cluster has no leader, and neither do the admin calls that refresh the metadata first (`createTopics` and `describeConfigs` among them), unless the partition belongs to one of the admin's target topics: a topic it has read or reset offsets of, or deleted records from, which their refresh names. A Metadata answer for every topic now keeps each topic's and each partition's error code as data, as Java's `Admin#listTopics` reads it, and only its top-level error code (`REBOOTSTRAP_REQUIRED` at v13) still fails it; a request that names topics is parsed as before. `fetchTopicMetadata()` with no topics returns such a partition with its `partitionErrorCode` and `leader: -1` instead of waiting for a leader or failing with `LEADER_NOT_AVAILABLE`; name the topics to wait for their leaders. `fetchTopicMetadata({ topics, useDescribeTopicPartitions: true })` as the first call of an admin no longer fails on such a partition either.

- A regex subscription, `consumer.subscribe({ topics: [/re/] })`, no longer fails while a partition of a topic it does not match has no leader: it reads the metadata of every topic, which used to fail with `LEADER_NOT_AVAILABLE` until the cluster's retries ran out. The topics it matches are then asked for by name, so one of theirs without a leader still holds `subscribe()` up within the `retry` budget.

- `admin.deleteTopicRecords` retries a retriable error that names no partition, such as a lost connection, within the `retry` budget, and ends in success or in `KafkaJSNumberOfRetriesExceeded` whose `cause` is that error; it used to fail at once with `KafkaJSNonRetriableError`, whose `cause` was a `TypeError` raised by its own error handling. A broker that already deleted its partitions is not asked again. It also works as an admin's first call now, where 2.2.4 failed with `KafkaJSTopicMetadataNotLoaded`.

- A `commit()` whose `EndTxn` outcome is unknown — its retries ran out on a retriable answer, a request timed out, or a connection failed — now leaves the commit pending and rejects with the last retriable error itself (`retriable: true`, `category` `retriable` or `refreshRetriable`), as Java's `commitTransaction()` may be retried after a timeout. Calling `commit()` again sends the same `EndTxn`, with the same producer id and epoch, which a coordinator that already committed answers with success (under transaction version 2 with the epoch the producer then adopts); until the commit settles, `abort()`, `send()`, `sendBatch()`, `sendOffsets()` and `producer.transaction()` throw a `KafkaJSNonRetriableError` saying it did not complete. A commit sent again after the coordinator aborted the transaction on its timeout rejects with `KafkaJSApplicationRecoverableError`, the broker answering 48 or 90, depending on the transaction version and on whether the broker has KAFKA-20785 (fixed in 4.3.2 and 4.5.0): replace the producer. Such a commit used to reject with a `KafkaJSTransactionAbortableError` and let `abort()` run, which the coordinator refused when the commit had landed; kafkajs 2.2.4 rejected it with `KafkaJSNumberOfRetriesExceeded` and refused both `commit()` and `abort()` afterwards, so a catch keyed on that class no longer matches. A `commit()` called while another commit of the transaction is under way joins it, and `producer.disconnect()` waits for a commit still under way, or sends a pending one once more through one more retry budget, then disconnects whatever the answer, logging a warning that names the transactional id when the commit did not succeed; a transaction object whose commit `disconnect()` completed has ended, as the next `producer.transaction()` makes sure.

- `@opentelemetry/instrumentation-kafkajs` does not instrument this package: it hooks the package `kafkajs` below version 3 only. `@countly/opentelemetry-instrumentation-kafkajs`, the package in `otel/`, does, with the same span names, metric names and attributes except `messaging.kafka.cluster.id`, which it never sets, whether the library is installed as `@countly/kafkajs` or, through an npm alias, as `kafkajs`. ESM applications start Node.js with `--experimental-loader=@opentelemetry/instrumentation/hook.mjs`, as with the upstream package. Its instrumented `transaction.commit()` returns a distinct promise to each caller, even where this library returns one promise to two calls made while a commit is under way, and an `ERROR` `transaction` span after a retriable `commit()` rejection means that the outcome of the commit is unknown, not that the transaction aborted.

- `roundRobin`, the default assigner, gives each partition only to a member that subscribes to its topic when the members of a group subscribe to different topics, as Java's `RoundRobinAssignor` does: it walks the partitions in its usual order and hands each to the next member, in sorted member-id order, that subscribes to the partition's topic, carrying on after that member. A topic no member subscribes to is skipped, and a member that sent no subscription is taken to subscribe to every topic. 2.2.4 dealt every partition over all the members, so a member that did not subscribe to a topic was dealt its partitions, dropped them with a `RECEIVED_UNSUBSCRIBED_TOPICS` warning, and nobody consumed them until the next rebalance, which a deploy that changes a subscription made routine. When every member subscribes to every topic the assignment is unchanged. The consumer's handling of an assignment from another leader is unchanged: it warns, emits the event and drops the partitions.

#### Fixes

- The idempotent producer's per-partition batch queues no longer use `Array#shift`, whose cost grows with the queue once it holds more than about 16 000 elements (a few microseconds per shift at 17 000 and about 30 µs at 128 000 on Node 26); a dependency-free O(1) queue replaces them with the same order and the same results.

- A `send()` at `linger: 0` spends less time in the client: the accumulator hands a send's batches to the send path with no grouping work when they share their `acks`, `timeout` and `compression`, and the per-partition results of a Produce answer are read in one pass. Nothing else changes: batches, requests and the order in which sends settle are the same.

- The documentation no longer says that retrying a send after `KafkaJSNumberOfRetriesExceeded` is safe on an idempotent producer. The client's own retries keep the batch's producer id, epoch and sequence, so the broker drops a duplicate; after that error the outcome is unknown and a new `send()` may write the records again: deduplicate in the application, or use a transaction where that matters. Documentation only; behaviour is unchanged.

- A record batch's header timestamps now agree with its records. Timestamps given as `Date`s or of different digit lengths (`999` and `1000`) could write a header whose first timestamp came after its max, and a batch mixing `BigInt` with other timestamp forms threw a `TypeError`. The header's first and max are now the lowest and highest record timestamps, a record without a timestamp counts at the send time, and a timestamp of `0` still means the send time, as in 2.2.4. Timestamps are kept exactly as int64: a numeric string, `BigInt` or `Long` beyond `Number.MAX_SAFE_INTEGER` is written to the header and to every record without rounding, as 2.2.4 wrote the header.

- A producer can send to a topic named like an inherited object property again: `toString`, `constructor` and `__proto__` are valid Kafka topic names. The send path kept its per-topic bookkeeping in plain objects, so a non-idempotent `send()` to `toString` or `constructor` found a bucket that did not exist and ran out of retries without sending a Produce request, a send to `__proto__` also wrote a partition entry onto `Object.prototype`, and an idempotent send to `__proto__` never left the queue and hung until its delivery deadline. The bookkeeping, and the round-robin counters of `DefaultPartitioner` and `LegacyPartitioner` (which always chose partition 0 for such a topic, as in kafkajs 2.2.4), now live in prototype-free maps.

- `UniformStickyPartitioner` counts a string key or value in the bytes it encodes to (UTF-8), as its `stickyBytes` option documents and as a `Buffer` of the same text already was. It counted characters, so text outside ASCII (`'€€'` is two characters and six bytes) filled a partition's sticky quota too slowly.

- A send no longer lets one partition without a leader hold back the other partitions of its topic. Since the cluster's leader lookup refuses a whole topic when any requested partition has no leader, a keyed record or an explicit `partition` aimed at a partition in a leader election made every other ready batch of that topic wait out its backoff with it, and with `retry.factor: 0` none of them was ever sent. The producer now looks each partition up on its own when the topic's lookup fails: the partitions with a leader are produced, and only the leaderless one waits or is rejected, on the idempotent and the non-idempotent path.

- A leader hint that moves a broker to a new address no longer waits for the old broker's outstanding requests before the producer drains again: the old broker closes in the background, its requests still finishing or timing out on the old socket, so one moved broker no longer holds back every other broker's sends for up to `requestTimeout`. A hint that moves the seed broker no longer lands on a seed that a rebootstrap replaced while the hint was building its connection.

- A partition the metadata cache holds without a leader keeps its leader epoch against an older metadata response, as a partition with a leader already did, as the Java client does, so a lagging response during an election no longer points sends back at the previous leader.

- A transactional producer whose coordinator could not be found while it ended a transaction, the lookup's own retries spent on a refused connection, a missing broker or an unavailable coordinator, is no longer made unusable: `commit()` leaves the commit pending, as for any `EndTxn` whose outcome is unknown, and `abort()` ends the transaction and owes the next one an epoch bump, as for any failed `EndTxn` of an abort. Both rejected with `KafkaJSApplicationRecoverableError` before.

- A transactional producer no longer becomes unusable when the broker rejects a record as too large (`MESSAGE_TOO_LARGE`) or with an out-of-range timestamp (`INVALID_TIMESTAMP`). Both now carry `category: 'invalidConfiguration'` (still `retriable: false`), so `abort()` succeeds and the producer carries on once the record is fixed; before, `abort()` rejected with `KafkaJSApplicationRecoverableError` and the producer had to be replaced.

- Under transaction version 2, `transaction.sendOffsets()` with an offset collection that holds no partition (an empty `topics`, or topics whose `partitions` are all empty) no longer marks the transaction as started. Committing such a transaction sent an `EndTxn` for a transaction the broker never opened, which answered `INVALID_TXN_STATE` and made the producer unusable. The call is now skipped, as the Java producer skips it, and `commit()` resolves. Under transaction version 1 the call behaves as in KafkaJS 2.2.4.

- `broker.produce()` under transaction version 2 now refuses, before anything is sent, a transactional request whose `maxVersion` leaves it below Produce v12, with `KafkaJSServerDoesNotSupportApiKey`. A caller cap of 10 or 11 sent the request at that version, without the implicit partition add. The high-level producer never passes such a cap.

- A classic group whose leader assigns with the `sticky` or `cooperative-sticky` assigner no longer stalls that leader past `sessionTimeout` when its members subscribe to many topics in narrow, different sets. The assignment's balance check rescanned every member's partitions for each partition it considered moving: twenty members on topics of 150 partitions took 12 to 20 seconds, and three hundred did not finish in ten minutes. It now keeps the last move it found possible and rescans only once that move is gone, and keeps the members' load order by binary search, so three hundred such members take about a second. Assignments are unchanged byte for byte wherever the old output was valid: `node scripts/benchmarks/stickyAssign.js --check --baseline-tree <older tree>` compares them on fixed and seeded random group shapes, and without `--check` it times the shapes against the older tree.

- `sticky` and `cooperative-sticky` no longer hand a partition back to its previous owner once that member has left the partition's topic. The balancing pass of their general path, taken when members subscribe to different topics, moved a partition back to its previous owner on a load check alone, as Java 4.3's `AbstractStickyAssignor` does, so a member that no longer subscribed to the topic was given the partition, dropped it with the `RECEIVED_UNSUBSCRIBED_TOPICS` warning, and nobody consumed it until the next rebalance. The assignment is computed as before and returned unchanged whenever every partition goes to a subscriber of its topic; only when it would give one to a member that does not subscribe is it computed again with the check, which sends such a partition to the least loaded subscriber.

- `consumer.groupMetadata()` now returns the new generation and member id to every observer of `GROUP_JOIN`, both the `kafkajs.consumer.group_join` channel and `on()` listeners. A channel subscriber read the previous pair (generation -1 and an empty member id on the first join), so a snapshot passed to `sendOffsets` could skip membership fencing or fail it spuriously.

- A consumer no longer applies an OffsetFetch or ListOffsets answer that arrives after its topic was deleted and recreated. With one fetcher per broker resolving the whole assignment, a late answer for the old topic could overwrite the recreated topic's position with the old topic's committed offset, so the consumer skipped the new topic's first records. Such an answer is now dropped when the topic's id provably changed or when a recreation signalled itself while the request was in flight, and the topic is resolved again on the next fetch round.

- `consumer.commitOffsets()` honours the client's `retry.maxTotalTime` and rejects with `KafkaJSDeliveryTimeout` once the deadline passes. It shared the fetch loop's retrier, which leaves the deadline out because the loop runs as one operation for as long as `run()` runs, so only `retries` bounded it. The fetch loop stays exempt; with `maxTotalTime` unset nothing changes.

- A consumer whose poll deadline passed while a heartbeat failed no longer drops out of its group without rejoining. A rejoin verdict that arrived while the fetch loop sat between two starts (in its backoff after a heartbeat failure that carried no verdict) was never taken, so the member stayed out of the group, stopped heartbeating and kept fetching; it is now taken before the loop starts again. A leave sent by the poll guard no longer clears a membership that a rebalance installed while the leave was in flight (classic members lost their new member id and stopped heartbeating, consumer-protocol members their assignment), a stale lost-membership verdict no longer swallows a fresh one, and a stale one met by a revocation still discards the uncommitted offsets instead of committing them. Present since Phase 6A.

- `describeConfigs` with a resource whose `configNames` is `null` no longer fails with a `TypeError` while the request is built: the admin check accepted `null` but the encoder of `DescribeConfigs` v1 and v2 did not. Against a 4.x broker the request is built at v4, where `null` and an empty list both ask for every config.

- `admin.createTopics({ waitForLeaders: true })` keeps waiting while the broker it asks still answers `UNKNOWN_TOPIC_OR_PARTITION` for a topic the controller has just created, within `timeout`, as Java's `Admin` documents a KRaft cluster needs a few seconds for; any other error still fails the call at once, and a `validateOnly` request, which creates nothing, does not wait. It removes a spurious code-3 failure on a freshly started cluster; a code 3 that never clears now ends as a `KafkaJSTimeout` (after `timeout`, or 10 s when it is not set) where it failed at once.

- `DeleteGroups` v1 reported `clientSideThrottleTime` as `undefined` instead of the broker's throttle time (it read a key that v0 names `throttleTimeMs`), so a throttled broker was never waited out on that connection. v1 and the new v2 report the number.

- A `BROKER` resource with the empty name, the cluster-wide default broker config, can be described and altered: `describeConfigs` and `alterConfigs` refused it with `KafkaJSNonRetriableError` ("Invalid resource name"), and the routing they share would otherwise have looked for a broker whose id is `''`. All three config methods now send it to the controller, like every other resource that names no broker; every other resource type still needs a non-empty name.

- `createTopics`, `deleteTopics` and `createPartitions` send again the topics that a controller-mutation quota refused with `THROTTLING_QUOTA_EXCEEDED` (KIP-599), within the `retry` budget and after the broker's throttle time, as Java's `Admin` does by default (`retryOnQuotaViolation`); the topics the broker did process are not sent again, and a refusal that outlives the budget rejects with `KafkaJSNumberOfRetriesExceeded` whose `cause` is the quota error. Against Kafka 4.x these calls negotiate CreateTopics v7, DeleteTopics v6 and CreatePartitions v3, at or above the versions from which a broker with quotas refuses a request that 2.2.4's v3, v1 and v1 only slowed, so without the retry a cluster with quotas would have begun to reject calls that used to succeed. A failed `deleteTopics` or `createPartitions` call now carries the failed rows on its error as `topicErrors`. A partial `deleteTopics` answer no longer strands the topics the broker did delete: they leave the admin's target topics at once, so the next metadata refresh does not ask for them and fail with `UNKNOWN_TOPIC_OR_PARTITION`, and the refused topics are sent again.

- `admin.deleteTopicRecords` reads the topic's offsets before it looks its partitions' leaders up, so it no longer fails with `KafkaJSTopicMetadataNotLoaded` as the first call of an admin (kafkajs 2.2.4 had the same defect). A partition without a leader is waited for within the `retry` budget, by the offsets read and by the leader lookup, which now runs inside the call's retrier; one that stays without a leader rejects as `fetchTopicOffsets` does, with a `KafkaJSNonRetriableError` whose `type` is `LEADER_NOT_AVAILABLE`, before anything is deleted. A partition the topic does not have still rejects at once with `KafkaJSDeleteTopicRecordsError`, once the offsets read has succeeded: on a topic that stays without a leader, that read fails first, as above.

- A request still encoding when its connection was replaced no longer blocks the new connection's requests or gets written to it. The order in which requests reach a connection outlived a disconnect or a closed socket, so an asynchronous encoder that stalled (compression, say) held every later request on the reconnected connection outside `requestTimeout`, then wrote its stale frame to the new socket. Each connection attempt now orders its own requests: a request sent under an earlier attempt rejects with `KafkaJSConnectionError` ("Not connected") once its encoder returns and is never written, and `connect()` starts a fresh order. Order within one attempt is unchanged.

#### Additions

- `Broker#leaveGroup` accepts a list of members, `{ groupId, members: [{ memberId, groupInstanceId, reason }] }`, and resolves every member's own error code instead of throwing the first (the single-member form still throws, as the consumer's own leave relies on it); `reason` travels from `LeaveGroup` v5. The consumer's own leave sends the reason `the consumer is being closed`, which the coordinator logs.

- `consumer.disconnect({ leaveGroup })` (KIP-1092, Kafka 4.1) chooses whether a member tells its group it is leaving; called without an argument, or with anything but an options object, nothing changes. `{ leaveGroup: true }` makes any member leave at once, which is how a static member that is not coming back hands its partitions over: a classic static member sends LeaveGroup with its member id and its `groupInstanceId`, where the Java client sends the member id alone, so a member id that is no longer the instance's current one answers `FENCED_INSTANCE_ID` instead of removing someone else's membership, and a consumer-protocol static member sends member epoch -1, which removes it, instead of -2, which keeps its slot. `{ leaveGroup: false }` sends nothing for a dynamic member, which the group then keeps, with its partitions, until its session expires; under the consumer protocol the consumer still commits what it owns and reports the revocation, and for a static member `false` is what the default does. An options object whose `leaveGroup` is not a boolean throws `KafkaJSNonRetriableError` before anything is stopped; any other argument is ignored, as 2.2.4 ignored every argument, so `process.on('SIGTERM', consumer.disconnect)` keeps working. A `disconnect()` that joins a stop already running keeps the first call's choice; `stop()` takes no option and a crash restart keeps the default. A close timeout is not part of it. It gives the static-membership bullet of Phase 2 the override it said was missing.

- The configuration APIs reach the versions Kafka 4.3 offers. `IncrementalAlterConfigs` (KIP-339) v0 and v1 are implemented and `Broker#incrementalAlterConfigs({ resources, validateOnly })` sends them: each config entry names an operation (`AlterConfigOpTypes` `SET`, `DELETE`, `APPEND` or `SUBTRACT`), so the entries a request leaves out are untouched, a DELETE is always written with a null value, an entry with an unknown operation or without a value (other than a DELETE) is refused before anything is sent, and a resource that fails comes back as a result carrying its `errorCode` instead of throwing. `DescribeConfigs` v3 (KIP-569) and v4 (the same fields in flexible framing, KIP-482) and `AlterConfigs` v2 are implemented and negotiated, so `describeConfigs` and `alterConfigs` use them against every 4.x broker: every `describeConfigs` entry keeps all its keys and gains `configType` (the raw byte of `ConfigTypes`) and `documentation`, which is `null` unless `Broker#describeConfigs` is given `includeDocumentation: true`. The compatibility matrix lists the three APIs as current.

- Four enums for the new wire values, exported from `index.js` and `index.mjs`: `ConfigResourceTypes` gains `CLIENT_METRICS` (16) and `GROUP` (32), `ConfigSource` gains `CLIENT_METRICS_CONFIG` (7) and `GROUP_CONFIG` (8), and `AlterConfigOpTypes` (`SET` 0, `DELETE` 1, `APPEND` 2, `SUBTRACT` 3) and `ConfigTypes` (`UNKNOWN` 0 to `PASSWORD` 9) are new frozen objects.

- The topic, partition, record and group administration APIs reach the versions Kafka 4.3 offers: `CreateTopics` v4 to v7 (KIP-464, KIP-525), `DeleteTopics` v2 to v6, `CreatePartitions` v2 and v3, `DeleteRecords` v2 and `DeleteGroups` v2 are implemented and negotiated, so `createTopics`, `deleteTopics`, `createPartitions`, `deleteTopicRecords` and `deleteGroups` use them against every 4.x broker. Every decoded result keeps all its keys and gains the new ones: `Broker#createTopics` reports `numPartitions`, `replicationFactor`, `configs` and `topicConfigErrorCode` from v5 (a topic that was created but whose configs could not be read back is decoded, never thrown) and `topicId` from v7, and `Broker#deleteTopics` reports `errorMessage` from v5 and `topicId` from v6; `admin.createTopics()` still resolves `true`, or `false` when every error is `TOPIC_ALREADY_EXISTS`. A `DeleteTopics` v6 request sends each topic name with the zero uuid, as the Java client does when it is given names, and a `CreatePartitions` request never sends an empty list of assignments, which the 4.3 controller reads as an explicit and wrong assignment: an absent or empty `assignments` is the null list. The compatibility matrix lists the five APIs as current and its floor-watch row for `DeleteTopics` is gone.

- `DescribeAcls`, `CreateAcls` and `DeleteAcls` v2 and v3 are implemented and negotiated (every Kafka 4.x broker offers v1 to v3), and `AclResourceTypes.USER` (7), the resource type v3 adds, is accepted by `admin.createAcls`, `admin.describeAcls` and `admin.deleteAcls`; every decoded key is unchanged. The compatibility matrix lists the three APIs as current, its floor-watch table is empty, and it no longer reports the pre-2.4 name `ElectPreferredLeaders` for key 43 (the API itself is still unimplemented).

- `admin.incrementalAlterConfigs({ resources, validateOnly })` (KIP-339, upstream issue #1517) changes individual config entries: each entry names an operation (`SET`, `DELETE`, `APPEND` or `SUBTRACT`), so the entries a request leaves out are untouched, unlike `alterConfigs`, which replaces the whole dynamic config of the resource (its documentation now says so). It resolves one result per resource, in the order given, and does not reject for a resource that fails, only for an invalid argument, a transport failure, or `NOT_CONTROLLER` outliving the retries (the one result code it retries, as Java's client does). Before anything is sent it refuses a missing or unknown operation, a SET, APPEND or SUBTRACT without a string value, and a repeated resource or config name. Resources go to the broker named by the resource, or to the controller, one request per broker. `GROUP` and `CLIENT_METRICS` resources work, and `describeConfigs` gains `includeDocumentation` (default `false`), which fills the `documentation` of each entry.

- `DescribeTopicPartitions` (API key 75, KIP-966) is implemented: `Broker#describeTopicPartitions({ topics, responsePartitionLimit, cursor })` sends v0, the paginated describe that also reports each partition's eligible leader replicas, and resolves one page with the `nextCursor` to resume from. A topic the broker cannot describe comes back as a row with its own `errorCode` and a `null` topic id, not as an error. `apiKeys` gains `DescribeTopicPartitions: 75` and the compatibility matrix lists the API as current.

- `admin.fetchTopicMetadata({ topics, useDescribeTopicPartitions: true })` reads the named topics through DescribeTopicPartitions (KIP-966), which the `Metadata` request cannot match for topics with many partitions and which alone reports each partition's eligible leader replicas (`eligibleLeaderReplicas`, `lastKnownElr`; `null` when the cluster does not track them). It asks any broker (a failed request is asked again on the `retry` budget after a metadata refresh) and follows the broker's pages to the end the way Java's `Admin#describeTopics` does (names sorted by UTF-16 code unit, finished topics dropped, a topic cut off by a page continued at the number of partitions read, the loop ended by the broker's null cursor, and failed rather than left to ask for ever when a broker repeats a page or leaves a topic unanswered), returns a partition without a leader at once, as `leader: -1` (Kafka 4.1.2 and 4.3 brokers leave its `partitionErrorCode` at 0), instead of waiting for one, fails a topic that does not exist (it never creates one) after every page is read, and asks through Metadata instead when no topic is named or the broker does not offer the API. `fetchTopicMetadata` topics gain `topicId` (`null` when the broker sends none) and `isInternal` on both paths.

- `admin.removeMembersFromConsumerGroup({ groupId, members, reason })` (KIP-345) removes members from a consumer group of either protocol: with `members: [{ groupInstanceId }]` it removes those static members, a repeated instance id once; without `members` it removes every member `describeGroups` reports (a group with none resolves `[]` without a request, and a group of another protocol type, a Kafka Connect group say, is refused). It resolves one `{ memberId, groupInstanceId, errorCode, error }` per member sent, so a member that could not be removed (`UNKNOWN_MEMBER_ID` for an unknown instance id or a group that does not exist) is a result and not a rejection, and only a failure of the request itself rejects, after asking a coordinator that is moving or loading again. It is meant for instances that are already gone: a member that is still running rejoins on its next heartbeat. `reason` (default `member was removed by an admin`, which a `null` or empty `reason` also means, at most 255 characters) is logged by the coordinator.

- Every public instrumentation event is also published on `node:diagnostics_channel`, on the channel `kafkajs.<event name>` (42 channels, for example `kafkajs.consumer.network.request`), so a metrics layer or tracer can observe every client in the process without holding one. The message is the same event object an `on()` listener receives; with both, channel subscribers run first. Nothing is allocated for an event that has neither a subscriber nor a listener. `docs/InstrumentationEvents.md` lists the channels and the rules a subscriber must follow, and now gives the `nodeId` that `FETCH_START` and `FETCH` carry; its line on how listeners run is corrected (they are called synchronously, by the code that emits the event).

- `docs/InstrumentationEvents.md` gains a tested prom-client recipe built only on the `node:diagnostics_channel` channels: request count and duration per API, consumed messages and handler time per topic, offset commits, group joins and their duration, and consumer crashes, with the units, the `acks: 0` caveat and the label rules. There is no runtime metrics API; a unit spec runs the recipe as written against a fake registry, and a gated live spec runs it against a produce and consume round trip.

- The OpenTelemetry instrumentation for this library, `@countly/opentelemetry-instrumentation-kafkajs` 0.1.0 in `otel/`, derived from `@opentelemetry/instrumentation-kafkajs` 0.32.0 (Apache-2.0): `KafkaJsInstrumentation`, with the same `producerHook` and `consumerHook` options, gives a span per sent and per processed message, a `transaction` span, context propagation through the message headers and the `messaging.process.duration`, `messaging.client.consumed.messages`, `messaging.client.operation.duration` and `messaging.client.sent.messages` metrics, and patches only the public API (`Kafka#producer` and `Kafka#consumer`, `send`, `sendBatch`, `transaction`, `run` and the `REQUEST` event). ### Phase 9A — Foundations: test infrastructure, correctness and durability

#### Behavior changes

- **A response frame that is negative, shorter than a correlation id, or larger than `maxResponseSize` (default 100 MiB, the length prefix excluded) now closes the connection with `KafkaJSInvalidFrameError` (retriable).** It used to be buffered without bound or to throw from the socket listener; the partial frame of a dead socket is also no longer carried into the next connection. The size is the response-frame bound that the `maxResponseSize` option sets, and a consumer whose `maxBytes` is above it logs one warning.

- **A request that exceeds its `requestTimeout` now closes the connection and fails every request in flight or queued on it**: `KafkaJSRequestTimeoutError` for the one that timed out, a retriable `KafkaJSConnectionClosedError` for the others. Queued requests are never written to the stalled socket; the next request reconnects. A closed connection no longer makes its broker wait behind a healthy long Fetch: the sibling connection retires in the background.

- **No offset commit is sent once the consumer has learned it lost its membership, and none by a handler or retry that outlived a rejoin.** `consumer.commitOffsets()` and the explicit form of `eachBatch`'s `commitOffsetsIfNecessary(offsets)` reject with `KafkaJSCommitFailedError` (a `reason` of `membership-lost`, `poll-interval-exceeded` or `stale-assignment`; a broker-reported loss keeps its `type` and `code`). Automatic commits are skipped, a handler's own error is no longer replaced by a failed commit, and a failed pre-rebalance commit no longer delays the rejoin.

- **`transaction.sendOffsets()` no longer marks offsets committed in the client's shared cache; they are published only after the transaction's commit is confirmed, once.** An abort, a fatal state or an unconfirmed commit publishes nothing; a commit confirmed during `disconnect()` still publishes, while one whose outcome is still unknown at close, or a transaction still open at close, forfeits its publication: a commit confirmed after a reconnect does not publish the offsets sent before the close. Calls on one transaction now run one at a time in call order.

- `KafkaJSAggregateError`, the error `admin.createTopics()` and `admin.alterPartitionReassignments()` reject with when topics fail, now has `retriable`: `true` only when it holds at least one child and every child is retriable, so a string child, a plain `Error` child, a missing child, an empty list and no list at all make it `false`; building one never throws, as in 2.2.4. Its `category` follows: `refreshRetriable` when every child is, `retriable` when every child is retriable, else `applicationRecoverable`. It carried no `retriable` flag before, which a retrier reads as retriable, so a retrier of your own around those calls repeated a rejection that held a failure that cannot succeed, such as an existing topic's `TOPIC_ALREADY_EXISTS`, until its budget was spent; it now stops at once with `KafkaJSNonRetriableError`, the aggregate as its `cause`, and still retries an aggregate whose children are all retriable. Code that tests `if (e.retriable)` by truthiness saw `undefined` before and treated every aggregate as not retriable; it now sees `true` for an aggregate whose children are all retriable, and may start retrying it.

- `admin.createTopics` and `admin.alterPartitionReassignments` no longer end the call at the first answer that names a failed topic or partition. Each retry sends only the items the broker marked retriable (a partition keeps its original replicas), an item the broker confirmed is never sent again, and an item it refused for good is kept across the retries and, when those attempts end in failure, listed in the final `KafkaJSAggregateError`, even when a later attempt fails differently. `createTopics` resolves `false` only when every topic that did not go through already exists, and with `waitForLeaders` it waits, after the last attempt, for the leaders of the topics the call created (a call whose attempts fail does not enter that wait; if the wait itself fails, its metadata error or timeout rejects the call directly). A failure that lists no items (other than `NOT_CONTROLLER`, which is still retried) still ends the call at once. A partition of a topic that does not exist (`UNKNOWN_TOPIC_OR_PARTITION`, which Kafka marks retriable) is now retried until the budget is spent and the call rejects with `KafkaJSNumberOfRetriesExceeded`, whose `cause.errors` lists it, where 2.2.4 rejected at once with the aggregate. `alterPartitionReassignments` no longer sends a topic whose `partitionAssignment` is empty. Pass `retry: { retries: 0 }` for a single attempt that reports every failure it saw.

- Connections replaced by a rebootstrap, a metadata refresh or a leader hint, and a broker removed after a connection failure, are retired: they drain in the background for at most `requestTimeout`, the rest of their requests fail with a retriable `KafkaJSConnectionClosedError`, the socket is destroyed, and a retired broker object can no longer reconnect. Recovery no longer waits for the drain, and a public `disconnect()` waits at most `requestTimeout` for requests in flight.

- **A RECORDS field of 1 to 16 bytes is a truncated tail, not a `RangeError`, and a corrupt Fetch record batch is no longer swallowed as one.** The decoder judges every batch before decoding it, with Java's rules: a length below the minimum or negative, a magic outside 0 to 2, an impossible record count, a record whose length is -1 and a malformed control record raise `KafkaJSCorruptRecordError` (non-retriable) inside the decoder, which returns the records before the batch and a `corruption` marker on the partition; a batch cut where `maxBytes` ended still returns what it has. A data record keyed `00 00 00 00` no longer ends an aborted transaction's filter, so the rest of the transaction is hidden from a `read_committed` consumer. A CRC mismatch still throws, as before.

- **A corrupt Fetch record batch now halts only its partition.** The records before it are delivered, the partition is no longer fetched, and offsets the client derives itself and automatic commits never cross the batch (an offset you pass to `commitOffsets` keeps its ordinary meaning). `consumer.partition_halted` fires once per halt and one error is logged; a listener or logger that throws changes neither. `consumer.seek` resumes the partition (a seek made inside the listener works, and like any seek also drops the records ahead of the batch that are not yet processed), as does a rebalance that revokes it, a recreation of its topic or a restart. A CRC mismatch still crashes the consumer.

- **Timestamps outside `[0, 2^63−1]` are rejected with `KafkaJSInvalidConfigurationError`** (they used to wrap silently, and a batch spanning the int64 range wrote a corrupt record). The exact value of a number, string, `BigInt`, `Date` or `Long` is checked before it can wrap.

- **Topics named `__proto__`, `constructor`, `toString`, `hasOwnProperty` or `valueOf` work end to end, and `transaction.sendOffsets` no longer writes into `Object.prototype`.** The consumer's, the built-in assigners' and the client's internal tables keyed by topic have no prototype: such a topic is subscribed, assigned by every built-in assigner, fetched, paused, sought, committed and published like any other, where it used to be dropped, crash the consumer or, for `__proto__`, pollute `Object.prototype` with its partition offsets. Public return shapes stay ordinary objects; `AssignerProtocol.MemberAssignment.decode()` keeps every topic, `__proto__` included, as an own entry of its `assignment`.

- **Bootstrap brokers may be written `[::1]:9092`; an unbracketed IPv6 literal or an invalid port is a configuration error.** A broker address is `host:port` or `[ipv6]:port` with a port from 1 to 65535; anything else, every entry of the list included, makes the first connect fail with `KafkaJSNonRetriableError` naming the address, where it used to connect to the wrong host or to port `NaN`.

- **`admin.fetchTopicMetadata({ useDescribeTopicPartitions: true })` has one overall deadline of 60 s and re-reads a topic that was recreated between pages.** At the deadline the call rejects with `KafkaJSTimeout`, whatever request is stalled and whether or not `enforceRequestTimeout` is on, retries included; a topic whose id changes between two pages fails the attempt retriably and the read starts again. Work already in progress at the deadline is not cancelled, and its result is ignored: a metadata refresh may finish its own retries (bounded by `retry`, shared with other calls on the client), a broker selection may go on to connect to the next broker, and a queued page may still be sent; the call itself starts no new attempt or page request after the deadline.

- **A throwing `POLL_INTERVAL_EXCEEDED` listener no longer prevents the consumer from leaving and rejoining; its error is logged.** Cleanup continues even if another cleanup step or its logger throws.

- `Cluster#getNodeIds()` is typed `string[]`, which is what it has always returned (the keys of the broker table); TypeScript code that compared an element with a number now fails to compile, and the comparison never matched at runtime.

- **Offset operations are ordered: a stale resolution, seek or commit no longer overwrites a newer one, a failed `ListOffsets` or a crash restart no longer loses a topic-recreation reset, and an answer that predates a recreation is not written.** A dropped answer is resolved again at once instead of after one empty fetch wait. The recreation-generation map is gone, so a consumer subscribed to many recreated topic names no longer retains an entry per name.

- **A stale transactional offset publication no longer overwrites a newer seek, reset, commit or topic recreation.** Publication is fenced per partition and topic incarnation; a newer consumer value is never cleared to force a broker read.

- OpenTelemetry instrumentation failures are contained: a meter, tracer, span, context manager or logger that throws no longer changes an operation's result or rejection, and the wrapped operation runs exactly once. `otel/README.md` is widened accordingly.

- With the OpenTelemetry package enabled, a traced `producer.transaction()` returns a derived promise, wrapped transaction operations turn synchronous throws into rejections with the same reason, and wrapped `commit()` preserves the client's fulfillment value.

- `Cluster#metadata()` rejects with the last broker's error instead of resolving `null` when every broker is connected to and every Metadata request fails. In 2.2.4 the `null` made `admin.listTopics()`, `admin.describeCluster()`, `admin.fetchTopicMetadata()` and a regex `consumer.subscribe()` fail with a `TypeError`, and a custom assigner's `cluster.metadata()` call got `null`. Now all of them reject, after one pass over the brokers, with the broker's error object itself, its class, `type`, `code` and `cause` intact. A broker that cannot be found or connected to is still retried within the client's `retry` budget and ends in `KafkaJSNumberOfRetriesExceeded` (`KafkaJSDeliveryTimeout` when `retry.maxTotalTime` ends it first). New for `admin.fetchTopicMetadata()` on the Metadata path: while the broker it asks last answers `LEADER_NOT_AVAILABLE` it asks again every 50 ms, and if that path is still unsettled 10 s after it is entered it rejects with `KafkaJSTimeout`, whether no leader appeared or no broker could be reached within the `retry` budget (`useDescribeTopicPartitions` has no such cap, and time spent there before a fallback to Metadata is additional); when the broker it asks last answers anything else, an authorization failure for example, it rejects at once and unchanged. The refresh pre-step, broker selection and snapshot contract is documented and pinned by tests.

- **A late accepted join under the consumer protocol is counted, and no redundant rebalance round follows a fenced join or a stale loss.** Stored loss notifications are also compared with their ownership token when the numeric generation is reused.

- **A consumer-protocol rejoin waits for the leave of its current membership to settle.** Overlapping reconciliation no longer attempts an illegal member-state transition.

- Seeking to offset `-2` or `-1` now resolves that partition's earliest or latest offset independently of `fromBeginning` and `autoCommit`. Sentinel seeks are local position requests and no longer send negative offsets through OffsetCommit; concrete-offset seeks retain their existing commit behavior. `admin.setOffsets()` and `admin.resetOffsets()` still store `-1` and `-2` as the group offset.

- **Concurrent `send()` calls to one partition made in the same tick are now written in the order they were made.** The last two used to leave the client's target-topics lock swapped, so a burst of two or more sends was numbered and written with the last two sends' records in reverse order. Inherited from 2.2.4. Order is still not promised across a send that retried its partitioning, or across topics.

- **A classic consumer no longer crashes on a lost broker connection (refused, reset, closed, a request timeout) or a moved group coordinator while it lasts less than `sessionTimeout`.** The join, and the Fetch, heartbeat and automatic commit requests of the fetch loop, are retried after `retry.initialRetryTime` without spending `retry.retries`, and the consumer looks the coordinator and the partition leaders up again. Each kind of request has its own outage, which ends only when a request of that kind succeeds and ends the ride `sessionTimeout` after its first failure, however long each attempt takes. A join used to crash at once on a bare connection error, and the fetch loop once `retry.retries` failures had accumulated over its whole life, so a broker that was killed and not yet fenced crashed and restarted the consumer. A longer outage still ends in `consumer.crash` as before; while some leader still answers, a lost connection to another leader is retried until its partitions move, as the Java client does. Errors thrown by your handler keep counted retries, except that a classic member retries an OffsetCommit `COORDINATOR_LOAD_IN_PROGRESS` (14) propagated from `eachBatch`'s `commitOffsetsIfNecessary` as a commit outage until `sessionTimeout`, and rides out a `NOT_COORDINATOR` (16) that a handler propagates from its `heartbeat()` or `commitOffsetsIfNecessary()` callback like the request that raised it, until `sessionTimeout`, without spending `retry.retries`. Consumers with `groupProtocol: 'consumer'` keep their counted retries.

- **A classic member answered `NOT_COORDINATOR` (16) looks the coordinator up again and keeps its membership, as the Java client does; it no longer rejoins.** It used to emit `REBALANCING` with reason `coordinator-changed`, commit and rejoin, and a group leader's rejoin forced a rebalance of the whole group. It no longer rejoins on `COORDINATOR_LOAD_IN_PROGRESS` (14) either, which the new coordinator answers while it loads the group after a move. A cooperative member's `heartbeat()` callback still resolves on 16 until its heartbeats have failed for `sessionTimeout`.

- **A response that carries a null array where the message definition does not allow one is now refused with a `KafkaJSPartialMessageError` (non-retriable) naming the field, such as `CreateAclsResponse.Results`; it is no longer read as an empty list.** It applies to every list the Kafka 4.3.1 definition marks non-nullable in the flexible AddPartitionsToTxn, AlterConfigs, AlterPartitionReassignments, CreateAcls, DeleteAcls, DeleteRecords (partitions), DescribeConfigs, DescribeGroups (v5, v6), ListOffsets, OffsetCommit, OffsetFetch, Produce, TxnOffsetCommit and Fetch (v12 and later) answers. A broker that follows the protocol never sends one; a malformed answer used to stand for "nothing to report", and `admin.createAcls()` resolved `true` on it with no ACL confirmed, a DENY ACL included. The call now rejects.

- **A consumer with `groupProtocol: 'consumer'` caps its heartbeat retry backoff at 1 000 ms after jitter, as the Java client does (`retry.backoff.max.ms`).** The cap limits the delay between a failed attempt and its retry; coordinator lookup and request duration can still make the time between heartbeat requests longer. Before, the retry backed off up to `retry.maxRetryTime` (30 s by default), and a member could be fenced, and keep processing partitions already reassigned, after a broker failover. **A consumer that learns its membership is lost** (fenced, an unknown member id, a poll-interval overrun) **now delivers no further record from the batches it holds**, before `PARTITIONS_LOST`, as kafkajs 2.2.4 did when its heartbeat ran between messages.

#### Fixes

- Eight option checks no longer throw a `TypeError` while building their message when the value is a `Symbol` or another value with no string form. `maxInFlightRequests`, `metadataRecoveryStrategy`, `metadataRecoveryRebootstrapTriggerMs`, `maxPollInterval` and the `stickyBytes` of `Partitioners.UniformStickyPartitioner` now refuse it with `KafkaJSNonRetriableError`, and `linger`, `batchSize` and `deliveryTimeout` with `KafkaJSInvalidConfigurationError`: the class the same check already throws for every other value it refuses. Each message shows the rejected value as the `maxResponseSize` message does, so the string `'5'` appears as `got '5'`.

- Fixed consumer seeks to `-2` and `-1` so each partition requests its exact earliest or latest ListOffsets timestamp regardless of subscription defaults or auto-commit, then fetches from the broker's returned offset. Newer offset operations fence stale answers, and pending sentinel seeks are released on use, revocation, reset, rebuild and stop.

- Corrected documentation for the consumer's five-request default, background heartbeats and processing deadline, permanent restart exceptions, retry jitter, Kafka group roles, and the preserved API with documented semantic differences. Assignment-output equivalence is qualified to inputs whose previous output was valid.

- A Fetch record batch of more than about 125 000 records (a highly compressed batch can hold that many) no longer fails with `RangeError: Maximum call stack size exceeded` while it is decoded: its records are appended one at a time, not passed to `push` as call arguments; a legacy compressed message set (magic 0 or 1) of that many messages, which a 4.x broker can still return from data written before an upgrade, is decoded the same way.

- A record header named `__proto__`, `constructor`, `toString` or `hasOwnProperty` no longer decodes to an array that holds the inherited property of that name: it is the header's value, and a repeated key still makes an array.

- Forty-three places in the response decoders no longer fail with a `TypeError` on a body the definition does not allow. Thirty-five compact list reads in the AddPartitionsToTxn, AlterConfigs, AlterPartitionReassignments, CreateAcls, DeleteAcls, DeleteRecords, DescribeConfigs, DescribeGroups, ListOffsets, OffsetCommit, OffsetFetch, Produce and TxnOffsetCommit codecs now refuse a null list with `KafkaJSPartialMessageError`, where the definition does not allow null, instead of failing with a `TypeError`; an OffsetFetch answer with no group raises the invariant violation it always raised. A topic-name sort in the CreateTopics, CreatePartitions, DeleteRecords and DeleteTopics answers no longer fails on a topic without a name, and a DeleteRecords failure for a partition the request did not name no longer fails reading the requested offset.

- Consumers keep topic-recreation resets observed during crash cleanup and do not restart after a public disconnect that completes during cleanup or while `restartOnFailure` is deciding.

- Group offset-cache and operation-ledger entries are released after the last participant, attached reset table and open ticket finish. Disconnecting one participant preserves active peers and unfinished transaction fences.

- `admin.resetOffsets()` and `admin.setOffsets()` store `-1` and `-2` as the group's offset again, as in 2.2.4. Since sentinel seeks became local position requests, `resetOffsets` left the group's old offset in place; `setOffsets` now commits its `-1` and `-2` entries itself, as its joined member, and, as 2.2.4 ignored a seek to a partition the topic does not have, drops an entry for one. A rejected sentinel commit now rejects `setOffsets` after the internal consumer stopped; in 2.2.4 it surfaced inside that consumer's fetch loop.

- `admin.setOffsets()`, `admin.resetOffsets()` and `admin.fetchOffsets({ resolveOffsets: true })` release their temporary consumer on every exit: it is stopped and gives up its `cluster.topic_recreated` subscription on the admin's cluster. Disposal does not itself disconnect the shared cluster; the temporary consumer's existing crash handler can still disconnect it. A call that failed while that consumer was still joining its group left a member heartbeating in the group in 2.2.4; it now leaves.

- A classic consumer whose heartbeat cannot reach its group coordinator (a lost connection, a timeout, `COORDINATOR_NOT_AVAILABLE` or `NOT_COORDINATOR`), or whose connection to it is no longer open, looks the coordinator up again before its next heartbeat. It no longer heartbeats a dead or former coordinator until a rejoin, and a consumer sharing a `Cluster` that another client disconnected no longer leaves a coordinator connection open after its own disconnect.

- A sentinel seek (`'-2'` or `'-1'`) no longer settles a topic recreation's reset before it has a boundary. The reset is settled when the sentinel's concrete boundary is published (in every consumer of the group that owes it, as before) or by another applied seek or commit (superseded later in this release: only a confirmed current-incarnation commit settles the reset); a sentinel cancelled first, by `consumer.stop()`, an assignment rebuild or a revoke, leaves the reset owed (a failed ListOffsets keeps both the pending sentinel and the owed reset for the next resolution), so the next `run()` resets the partition instead of resuming from the old incarnation's committed offset and skipping the new topic's records. A stop also ends the repeated resolution passes of its fetch round: it is checked before each pass and after each pass returns, so a stopping consumer starts no further pass (a pass already in flight is not cancelled).

- Cancelling a consumer's pending sentinel seeks (`consumer.stop()` or an assignment rebuild) no longer fences other participants of the group. The barrier it put on the group's shared offset ledger could make a producer's confirmed transactional publication, or another consumer's commit, skip its write to the shared committed-offset cache. The consumer now fences only its own in-flight resolutions, and the boundary a cancelled sentinel was waiting for is still dropped.

- A null compact array in a response, where the definition does not allow null, no longer reads as an empty list. The 42 non-nullable list fields of the AddPartitionsToTxn, AlterConfigs, AlterPartitionReassignments, CreateAcls, DeleteAcls, DeleteRecords, DescribeConfigs, DescribeGroups, ListOffsets, OffsetCommit, OffsetFetch, Produce, TxnOffsetCommit and Fetch (v12 and later) decoders are read through `Decoder.requireArray`, which throws `KafkaJSPartialMessageError` naming the field, as Kafka's generated reader does ("non-nullable field ... was serialized as null"); an empty list still reads as empty, and a list the definition allows to be null (Fetch `AbortedTransactions`) still reads as empty. The `scripts/protocol` schema check also refuses a string, bytes or array length below -1, and -1 where the field is not nullable at the version, where it used to read them as empty.

- **Two metadata refreshes that overlap leave the broker table on the topology published last.** When the replies of two refreshes arrive together (one read of the socket), the older reply used to install its broker endpoint and the newer reply discarded its own pool, so the client's metadata named the new endpoint while connections still went to the old one; a lookup after the old endpoint went away failed with `KafkaJSConnectionError` until a recovery refresh repaired the table. Each response now takes a publication number when it becomes the client's metadata, and a refresh stops changing the broker table (installs, racks, removals) once a newer response has been published; a pool it had already built for the older topology is closed unused.

- `admin.fetchTopicMetadata({ topics, useDescribeTopicPartitions: true })` no longer starts choosing a broker after its 60 s deadline. A metadata refresh that finished late let the call connect to a broker the late answer advertised, and send it ApiVersions, after the call had already rejected with `KafkaJSTimeout`; the deadline is now checked before a broker is chosen. Work already in progress at the deadline is not cancelled (see the 60 s deadline bullet above).

- The TypeScript declarations now include `KafkaJSConnectionClosedError`, `KafkaJSMemberIdRequired`, `KafkaJSInvariantViolation`, `KafkaJSInvalidVarIntError`, `KafkaJSInvalidLongError`, `KafkaJSCreateTopicError` and `KafkaJSNoBrokerAvailableError`, which the package already exported at run time: a TypeScript caller can import them, `KafkaJSConnectionClosedError` among them, to handle the connection closure that a request timeout causes. Their inheritance, constructor parameters and fields match the run-time classes. No run-time change.

#### Additions

- `KafkaJSInvalidFrameError`, `KafkaJSCorruptRecordError` and `KafkaJSCommitFailedError` are exported from the package and its ES module entry, with their types: a refused response frame (a retriable connection error), a structurally corrupt Fetch batch (non-retriable) and a refused offset commit (non-retriable, with the loss as its `cause`). `KafkaJSAggregateError` gains `retriable`. The `Kafka` constructor accepts and validates `maxResponseSize`, the response-size limit passed to every connection, an integer from 4 to 2147483647 that defaults to 104857600 (100 MiB); it takes effect with the response-frame bound.

- `KafkaJSConnectionError` accepts an optional `cause`, preserving the original failure by identity.

- `consumer.events.PARTITION_HALTED` (`consumer.partition_halted`), the 43rd public instrumentation event, also on the channel `kafkajs.consumer.partition_halted`, with `{ groupId, memberId, topic, partition, offset, reason, error }` and its TypeScript payload type `ConsumerPartitionHaltedEventPayload`. The `node:diagnostics_channel` channels now number 43; the 42 given where the channels were introduced was the count at that time.
